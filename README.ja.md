# regied

1 台の Linux ホストのネットワーク政策を、1 つの YAML の宣言から組み立てるデーモン。

名前は仏語の régie（調整室）から。**自分では演じず、演者にキューを出す。**
リンクと経路の層は systemd-networkd が、DHCP と DNS は dnsmasq が、PPPoE は pppd が持つ。
regied はそれらに指示を出し、誰も持っていない層（nftables のファイアウォール、NAT、
ポリシールーティングの判定）を自分で持ち、全体を 1 つの宣言に束ねる。

ルーターは regied の適用先の一種であって、唯一の適用先ではない。

> **状態: 実装済み、実機未投入。** 適用エンジン、常駐の調整ループ、確認付き適用は
> 実装され、テストを通っている。実際の回線を持つ実機の上ではまだ動かしていない。
> 設定スキーマは形が決まっており、個々のフィールド名は最初のリリースまでに動くことがある。

## 何を自分で持ち、何を委譲するか

ここがこのプロジェクトの要点なので最初に書く。理由は
[ADR 0008](docs/ja/adr/0008-delegate-to-existing-implementations.md) にある。

| 領域 | 持ち主 |
|---|---|
| インターフェース、アドレス、MTU、ブリッジ | systemd-networkd |
| 静的ルート（IPv4 / IPv6、テーブル指定込み） | systemd-networkd |
| ルーティングポリシールール（マーク → テーブル） | systemd-networkd |
| ip6tnl トンネル（DS-Lite） | systemd-networkd |
| DHCPv6-PD、RA / SLAAC の配布 | systemd-networkd |
| DHCP サーバー、RA のオプション、条件付き DNS フォワード | dnsmasq |
| PPPoE セッション | pppd |
| **nftables のファイアウォール（IPv4 / IPv6）** | **regied** |
| **NAT（masquerade / ポートフォワード / hairpin）** | **regied** |
| **ポリシールーティングの判定（送信元レンジ、宛先の除外、集合）** | **regied** |
| **pppd と dnsmasq の設定生成と監督** | **regied** |
| **上記すべてを束ねる 1 つの宣言。dry-run、受け入れた宣言の記録、そこへ保ち続ける調整ループ、期限つきの適用** | **regied** |

この分担から出てくる帰結を 2 つ、先に書いておく。

**regied は自分が宣言したものだけを所有する。** nftables はルールセット全体を flush せず
自分のテーブルだけを作り替え、経路は自分が入れたものだけを消す。ルーティングデーモンが
学習した経路や、コンテナランタイム・CNI が持つ状態には触らない
（[ADR 0009](docs/ja/adr/0009-ownership-boundary.md)）。

**配布は regied の仕事ではない。** regied は 1 ノードを見るデーモンであり、
設定ファイルをどう配るかは別の仕組みが持つ。

## 対象とする構成

regied は、次の 7 領域を持つ実際に動いている構成を相手に作っている。

- **PPPoE** — メインの上位回線
- **DS-Lite** — ipip6 トンネル、IPv4 over IPv6
- **ポリシールーティング** — 送信元レンジで出口を選ぶ。宛先の除外つき
- **NAT** — masquerade、ポートフォワード、hairpin
- **nftables ファイアウォール** — IPv4 / IPv6、名前付きアドレス集合
- **DHCP と DNS** — 静的割り当て、RA / DHCPv6、条件付きフォワード
- **静的ルート** — IPv4 / IPv6

HTTP API は無い。読み取り専用の API の設計は記録した上で保留になっている
（[ADR 0007](docs/ja/adr/0007-resident-process.md)）。ホストがいま何をしているかは、
最後の周回の報告とジャーナルが答える（[運用](#運用) を参照）。

想定する構成は**上位回線が 1 本、機材が 1 台**である。冗長構成は無く、運用者は
自分が組み替えている回線越しにホストへ届いている。この前提が安全性の要件を決めている
（[ADR 0016](docs/ja/adr/0016-converging-on-the-accepted-declaration.md)）。

- **適用は冪等である。** 変えるものが無い周回はコマンドを 1 つも実行しない
- **`--dry-run` で、触る前に何が変わるかを見せる**
- **自動では何も巻き戻らない。** 失敗した提出は失敗した段で止まり、そこまでに済んだ分を
  ホストに残し、そう報告する。どの途中段階も安全な状態である。転送を有効にする前に
  ファイアウォールが入る。戻すのは人であり、前のファイルを適用する
- **ホストはファイルではなく、受け入れた宣言へ収束する。** 設定ファイルを読むのは
  `regied apply` だけ。ループも起動時ユニットもホストが受け入れた宣言を読むので、
  書きかけの編集がタイマーでホストに届くことは無い
- **期限を付けて適用できる。** `regied apply --confirm` は、ホストに届き続けている運用者が
  確定しない限り前の宣言へ戻る。設計の中で唯一の自動の復帰であり、締め出しのためにある

意図的にやらないことは [docs/ja/scope.md](docs/ja/scope.md) にまとめてある。

## プラットフォーム

regied は **Debian 13（trixie）** の上で作り、動かす。何も導入しない。
systemd-networkd、dnsmasq、pppd、nftables はディストリビューションのものを使い、
networkd は有効にしておく必要があり、ルーターのリンクを他の何かに持たせてはならない。
前提にするバージョンと、trixie の networkd にまだ無い指定 1 つは
[ADR 0011](docs/ja/adr/0011-target-platform.md) にある。

## 設定

設定はリソースを並べた 1 つの YAML ファイルで、Kubernetes のカスタムリソース風の書式を取る。
`kind: NetworkConfig`、ホスト全体のスイッチを `spec.global`、11 個のリソース kind を
`spec.resources[]` に並べる。

- [`docs/ja/spec/configuration.md`](docs/ja/spec/configuration.md) — 文書の形、
  リソース間の参照、どのバックエンドに落ちるか
- [`docs/ja/spec/kinds.md`](docs/ja/spec/kinds.md) — kind ごとのフィールド
- [`config/example.yaml`](config/example.yaml) — 回線 2 本のホストの実例

kind の一覧と持ち分は確定している（[ADR 0002](docs/ja/adr/0002-configuration-schema.md)）。
個々のフィールド名は最初のリリースまでに動くことがあり、`v1alpha1` はその意味である。

読む前に知っておく価値のある性質が 2 つある。

**秘密情報を入れられるフィールドが 1 つも無い。** 認証情報は、それを収めたファイルの
パスとして名指す。だから設定ファイルは、検閲なしに公開したりバグ報告に貼ったりできる
（[ADR 0003](docs/ja/adr/0003-secrets-out-of-configuration.md)）。

**回線側のグローバルアドレスを書けるフィールドも無い。** NAT とポートフォワードは
アドレスではなく回線のリソースを参照し、ポリシールーティングのマークを打つチェーンは
宛先変換より後ろに置く。この 2 つによって、変わりうるアドレスをどこにも書かないまま
hairpin が成立する。

## ビルド

```sh
make build              # ホスト向けにビルドする
make build-arm64        # arm64 の SBC 向けにクロスビルドする
```

投入先は Debian 13 を動かす arm64 のシングルボードコンピュータである
（[ADR 0011](docs/ja/adr/0011-target-platform.md)）。開発と試験は amd64 Linux で行う。
クロスビルドは静的リンク（`CGO_ENABLED=0`）なので、バイナリをそのまま投入先へ
コピーすればよく、実行時の依存は無い。

## 運用

以下はすべて、プラットフォームの前提を満たしたホストを想定する。Debian 13 で
`systemd-networkd` が有効、リンクを他の何かに持たせていない
（[ADR 0011](docs/ja/adr/0011-target-platform.md)）。regied は root で動かし、
以下のコマンドもすべて root で実行する。

### 何がどこに置かれるか

| 何 | どこ | 書くのは誰 |
|---|---|---|
| バイナリ | `/usr/bin/regied`。同梱のユニットはここにある前提 | 運用者 |
| 設定ファイル | `/etc/regied/config.yaml`。`regied apply` と `regied render` の既定。`--config` で別の場所を指せる | 運用者 |
| 認証情報 | `/etc/regied/secrets/` 以下。設定ファイルが名指すパスに置く | 運用者 |
| systemd ユニット 2 本 | `/etc/systemd/system/`。[`dist/systemd/`](dist/systemd/) からコピーする | 運用者 |
| 受け入れた宣言 | `/var/lib/regied/accepted/declaration.yaml` | regied。提出が受け入れられた時点 |
| 最後の周回の報告 | `/var/lib/regied/turn/report.yaml` | regied。内容が変わるとき |
| 制御ソケット | `/run/regied/control.sock` | 常駐プロセス |
| networkd / dnsmasq / pppd の設定と pppd のフック | ディストリビューションのディレクトリに、regied の名前と所有マーカー付きで | regied |

regied は自分のディレクトリを自分で作る。運用者が用意するのは上の 4 行である。

**認証情報。** 設定ファイルには秘密を書けない。秘密を収めたファイルのパスを名指すだけである
（[ADR 0003](docs/ja/adr/0003-secrets-out-of-configuration.md)）。それらのファイルは
root 所有、モード `0600`、root しか入れないディレクトリに置く。regied は必要な周回で
読み、記録にも dry-run の出力にも差分にもログにも書かない。ここから出てくる
使うべき性質が 1 つある。**設定ファイルはバージョン管理に入れて安全である。** そして
後述する「戻す手順」は、それが入っていることのすべてに乗っている。

### systemd ユニット

`dist/systemd/` に 2 本ある。パッケージができるまでは `/etc/systemd/system/` にコピーして
reload し、両方を有効にする。

```sh
cp dist/systemd/regied-reconcile.service dist/systemd/regied.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now regied-reconcile.service regied.service
```

| ユニット | 動かすもの | 役割 |
|---|---|---|
| `regied-reconcile.service` | 起動時に `regied reconcile` を 1 回。終わったら抜ける | 再起動後にファイアウォールその他を記録から戻す。周回が failing で終われば、見える形で失敗する |
| `regied.service` | `regied serve`。常駐 | 調整ループ、確認試行、制御ソケット |

どちらも受け入れた宣言だけを読む。常駐ユニットは起動時ユニットの後ろに並ぶが、
それを要求しない。起動時の周回が失敗したときこそ、ループの再試行が要る。タイマーは
無く、パッケージも出荷しない。**ループは `regied.service` の中にしか無く、だからこそ
止めるのが 1 操作で済む**
（[ADR 0016](docs/ja/adr/0016-converging-on-the-accepted-declaration.md)）。

ユニットを有効にする前に、ホスト側で満たしておくことが 2 つある。

- **ディストリビューションの `nftables.service` を無効にしておく。** あのユニットは
  起動時にルールセット全体を flush するので regied のテーブルごと消える。ルールセットの
  持ち主が 2 人いれば、ループは毎分それと取り合いになる。有効なままだった場合に備えて
  ユニットは後ろに並べてあるが、それは保険であって容認ではない
  （[ADR 0007](docs/ja/adr/0007-resident-process.md)）
- **networkd が有効で、リンクを持っている。** `/etc/network/interfaces` は空にし、
  NetworkManager は入れない（[ADR 0011](docs/ja/adr/0011-target-platform.md)）

```sh
systemctl disable --now nftables.service
systemctl enable --now systemd-networkd.service
```

### コマンド

verb は 6 つ。表に「何を読むか」を書いてあるのは、それが設計の乗っている性質だからである。
**設定ファイルを読むのは `regied apply` だけ。** フラグ込みの表は
[`docs/ja/spec/configuration.md`](docs/ja/spec/configuration.md#宣言がホストに届くまで) にある。

| コマンド | 読むもの | すること |
|---|---|---|
| `regied render` | 設定ファイル | 各バックエンドに渡るものを印字する。ホストには触らない |
| `regied apply --dry-run` | 設定ファイルとこのホスト | 適用したら何が変わるかを印字し、何も変えない |
| `regied apply` | 設定ファイルとこのホスト | 宣言を受け入れたものとして記録し、そこへ 1 周回す |
| `regied apply --confirm <duration>` | 設定ファイルとこのホスト | 記録を書かずに、期限つきの試行を始める。`regied.service` が動いている必要がある |
| `regied reconcile` | 記録とこのホスト | 受け入れた宣言へ 1 周回す。failing で終われば非ゼロで抜ける |
| `regied serve` | 記録とこのホスト | ループ。再同期の間隔ごと、およびカーネルのアドレス変化ごとに 1 周 |
| `regied confirm` | 制御ソケット | 試行を受け入れた宣言にする。時計が止まる |
| `regied cancel` | 制御ソケット | 試行を捨て、直前の宣言へ今すぐ収束させる |

各 verb は `-h` でフラグを答える。

### ループが何をして、何をしないか

常駐プロセスは 1 分ごと（`--resync`）に**周回**を 1 回走らせ、どれかのリンクで
アドレスが増減したとカーネルが報せればもっと早く走らせる。周回は受け入れた宣言から全バックエンドを
描画し、ホストが持っているものを読み、違うところだけを動かす。違いの無い周回はコマンドを
1 つも実行しない。

運用者が知っておくべきこと:

- **無人の周回は、上がっているものを決して落とさない。** ファイルを書き、regied の
  nftables テーブルを置き換え、カーネルのスイッチを設定し、宣言されていて動いていない
  ユニットを起動する。動いている PPPoE セッションは、たった今そのオプションを書き換えた
  ものであっても再起動しない。宣言から消えたものも止めない。それらは報告して、人を待つ。
  頼む方法は `regied apply` をもう一度走らせること。apply は冪等なので、残っている段だけを
  やり、それ以外はやらない
- **見るのはドリフトであって、健全性ではない。** 宣言されたユニットが active でなければ
  ドリフト。active なら、何をしていようと宣言どおりである。上がっているのにパケットの
  流れないセッションを、ループは気にしない。セッションを生かし続けるのは pppd 自身の
  `persist` と systemd の `Restart=` であって、regied ではない
- **対象ごとにバックオフしながら再試行する。** 起動しない dnsmasq のせいでテーブルの
  修復が止まることは無い。コマンドが抑えられている間も比較は続くので、報告は最新のまま
- **収束できないという理由では終了しない。** 上がったまま、何が悪いかを言い続ける
- **受け入れた宣言が無いホストでは何もせず、そう言う。** 記録がこの版の regied で
  受け入れられなくなったホストでも同じ。どちらも空へは収束しない

周回は 3 つの状態のどれかで終わり、読むべきはその状態である。

| 状態 | 意味 | `apply` / `reconcile` の終了コード |
|---|---|---|
| `converged` | ホストが宣言全体を持っている | 0 |
| `waiting` | できることはすべてやった。適用時にしか存在しない値（まだ解決しない AFTR 名など）を待って、何かを省いている。何を待っているかは名指される | 0 |
| `failing` | 何かを試して失敗したか、この周回には直す権限が無い差がある。何が、なぜ、が名指される | 非ゼロ |

`waiting` は起動直後のホストの普通の状態である。手を打つべきなのは、続く `failing`。
どちらも最後の周回の報告とジャーナルに出る。

### 初めてホストに投入する

手順は、このプロジェクトの前提どおり**既存のルーターをそのまま残し、その横に新しい
ホストを立てる**形を想定する。以下のどこで失敗しても、配線を戻せば復旧する。だからと
いって期限を省かないこと。期限が守るのは、配線が手の届かないところにある場合である。

1. **ホストを用意する。** ビルドし（`make build-arm64`）、バイナリを `/usr/bin/regied` に
   置き、設定を `/etc/regied/config.yaml` に、認証情報のファイルを `/etc/regied/secrets/`
   以下に書き、上の前提を満たし、ユニット 2 本を入れて有効にする。宣言が受け入れられる
   までは、どちらのユニットも「無い」と報告して何も変えない。それで正しい
2. **触る前に見る。** `regied render` は各バックエンドに渡るものを印字する。
   `regied apply --dry-run` はホストで何が変わるかをファイル単位・コマンド単位で印字し、
   何もしない。認証情報は「このモードで書かれる」とだけ報告され、中身は出ない
3. **期限を付けて適用する。**

   ```sh
   regied apply --confirm 10m
   ```

   `regied.service` が動いていなければ拒否され、理由が表示される。時計を持つ者が
   いないからである。試行は daemon のメモリに置かれ、記録は触られない
4. **変更が壊したかもしれない経路から、まだ入れることを確かめる。** ネットワーク越しに
   ホストへ新しいセッションを開く。LAN 側のクライアントがアドレスを受け取り、外へ届くことを
   確かめる。`/var/lib/regied/turn/report.yaml` と `journalctl -u regied` を読む。窓は
   このために使う。daemon は周回がどの状態でも確定を受け付けるので、AFTR 名を待つ
   *waiting* のまま確定してもよいが、それは意識して決めること
5. **確定するか、手放す。** `regied confirm` で試行が記録に書かれる。`regied cancel` か
   期限切れで、前にあったものへ戻る。これは提出された周回であり、セッションの再起動も
   許される。確定はネットワーク経路から行い、シリアルコンソールからはしない。変更の
   影響を受けない経路で届いた確定は何も証明しない
6. **確定したファイルをバージョン管理にコミットする。** そのコピーが戻す手段である
7. **クライアントを移す前に 1 度再起動する。** `regied-reconcile.service` が、ファイルを
   一切読まずに記録からファイアウォールその他を戻すはずである。試行は再起動を生き延びない。
   生き延びるのは確定した宣言だけ

試行の最中に素の `regied apply` を打つと、試行は終わり、その宣言が記録に書かれ、期限は
残らない。コマンドはそう告げる。それは網を持たない選択である。

### 何かがおかしいとき

ループは修復の仕組みである。障害の最中に手を動かすなら、それが動き続けているのは
いちばん困る。だから手順は daemon で始まり、daemon で終わる。

**手で触る前に daemon を止める。終わったら起動する。**

```sh
systemctl stop regied     # ループが止まる。他には何も起きない
# ... 見る、nftables を手で直す、セッションを再起動する。障害対応に要ることをする ...
systemctl start regied    # ループが再開し、手直しを巻き戻す
```

daemon を止めると収束が止まり、それ以外は何も起きない。ファイルは回収されず、テーブルは
消されず、セッションは止まらず、カーネルのスイッチも戻らない。ホストは今載っているものを
そのまま動かし続け、記録も設定ファイルも触られず、手直しは daemon を止めている間ずっと
残る。**再び起動すれば、手直しは巻き戻される。受け入れた宣言こそがホストの持つべき
ものだからである。** それが正しい。手直しが本当の修正なら、ファイルに書いて提出する。
daemon が動いている間の手直しはドリフトであり、1 分以内に消える。それはループが
仕事をしているだけである。

daemon を止めたとき試行が走っていたなら、試行は消える。次の周回は、daemon の再起動からで
あれ起動時ユニットからであれ、試行の前に受け入れられていた宣言へ収束する。それが安全な
方向であり、そうなるものと思っておく。

**戻すとは、前のファイルを適用することである。** ロールバックのコマンドは無い。戻る先は
ファイル以外に無く、ファイルはバージョン管理にあるからである。

```sh
regied apply --config /path/to/the/previous/config.yaml
```

これは普通の提出である。提出された周回なのでセッションの再起動も許される。だから
タイミングは選ぶ。新しい宣言が既にやったことは、これでは取り消されない。再起動された
セッションは新しいセッションであり、dnsmasq が配ったリースは配られたままで、新しい
ルールセットが落とした接続は落ちたままである。前のファイルを適用して得られるのは
前の宣言であって、前の瞬間ではない。`apply` は記録したリビジョンを毎回印字する。
リビジョンはファイルのバイト列のダイジェストなので、バージョン管理にあるコピーと
ホストが受け入れたものは regied 無しで突き合わせられる。

**途中で失敗した提出。** 記録は新しい宣言を持ち、ホストは失敗した段までに済んだ分を持つ。
どの段かはコンソールが言い、報告も同じことを言う。ループはやってよいことを片付ける。
足りないファイルを書き、テーブルを置き換え、宣言されていて動いていないものを起動する。
やってはいけないことは報告する。古いオプションで動いているセッションの再起動、宣言から
消えたものの停止。先へ進む道は 2 つで、どちらも普通の提出である。

- ファイルを直して `regied apply` する
- 前のファイルを `regied apply` する

同じ `regied apply` をもう一度走らせることが、ループに許されていない半分の再試行でもある。
apply は冪等なので、残っている段だけをやり、それ以外はやらない。

**締め出されたとき。** `--confirm` 付きで入れた変更なら、待つ。期限が来れば、提出された
周回として前の宣言へ戻り、セッションも含めてホストは帰ってくる。`--confirm` 無しで
入れたなら、ホスト側で取り消すものは何も無い。変更の影響を受けない経路、つまり
コンソールからホストに入って前のファイルを適用するか、配線を前からあるルーターに戻す。
再起動は記録へ収束するので、記録が望みの宣言であるときだけ役に立つ。試行は再起動を
決して生き延びず、受け入れた宣言は必ず生き延びる。

**failing のとき、何を読むか。** API は無い。何が悪いかを言う場所は 3 つあり、どれも
気分ではなく物を名指す。

| どこ | 何を言うか |
|---|---|
| `journalctl -u regied` | 状態が変わるたびに 1 行。ドリフトごとに、現れたときと消えたときに 1 行ずつ。バックオフの段階も。周回ごとには出ない。静かなログは収束したホストである |
| `/var/lib/regied/turn/report.yaml` | 最後の周回が終わった状態と、その状態に入った時刻。何を待っているか、何が失敗しているか。リビジョン、警告、試行が有効かとその期限。内容が変わるときだけ書き直されるので、daemon を再起動しても失われない |
| `systemctl status regied-reconcile` | 起動時の周回が failing で終わったかどうか。`regied reconcile` はそのとき非ゼロで抜ける |

まず状態を読む。`waiting` は届いていない値を名指す。まだ解決しない名前、読めなかった
DUID ファイル。たいてい勝手に解消する。`failing` は失敗したコマンドか、周回に直す権限の
無いドリフトを名指し、あなたを待っている。受け入れた宣言が無いと報告するホストは、まだ
何も提出されていないか、状態ディレクトリを失っている。どちらも答えは `regied apply`。
記録がこの版の regied で受け入れられないと報告するホストは、宣言を置き去りにして
更新されている。今あるものを動かし続けたまま、新しい版が受け入れる宣言を求めている。

シェルから `regied reconcile` を打つと、記録へ 1 周回して同じ状態を印字する。何も提出せずに
「ホストをあるべき場所に戻せ」と頼むコマンドであり、できたかどうかは終了コードが答える。

## テスト

テストは必要な権限で分かれている。

| 対象 | コマンド | 要るもの |
|---|---|---|
| ユニットテスト | `make test` | Go ツールチェインだけ |
| netns 統合テスト | `make test-netns-docker` | Docker（特権コンテナを起動する） |
| netns 統合テスト（直接） | `make test-netns` | root / CAP_NET_ADMIN と nft / pppd / pppoe-server / socat |

netns 統合テストは network namespace で擬似 WAN（PPPoE サーバー、DS-Lite の
AFTR、到達確認用のサーバー）を組み、その中でルーターを動かして次の 7 点を
外側から確かめる。

1. PPPoE 経由で外向き疎通ができる
2. DS-Lite 経由で外向き疎通ができる
3. PBR が送信元レンジごとに経路を振り分ける
4. ポートフォワードが外から内に通る
5. hairpin NAT が内から自分のグローバル宛に通る
6. ファイアウォールが許可していない通信を落とす
7. NAT のマッピングが endpoint-independent である

root と、開発環境には入っていない外部コマンドが要るので、build tag `netns` の
後ろに分離してある。`go test ./...` はこれを拾わない。通常は
`make test-netns-docker` を使う。必要な道具を入れた特権コンテナを用意し、
その中で `make test-netns` を呼ぶ。

道具が揃った環境なら `make test-netns` で直接走る。前提が欠けているときは、理由を述べて
**失敗する**。飛ばした結果が `ok` と表示されるなら、通ったものと見分けが付かないからである。
`go test -tags netns` を素で叩いた場合は飛ばす。ターゲットに同じことをさせたいときは
`make test-netns REGIED_NETNS_REQUIRE=` と書く。

### 被試験体を差し替える

ルーターを組み立てる処理は 1 つのスクリプトに閉じ込めてあり、環境変数
`REGIED_NETNS_ROUTER_SETUP` で差し替えられる。既定は手書きの `ip` と `nft` で
組んだ参照実装である。受け渡しの約束は `docs/adr/0010-netns-testbed.md` にある。

別の実装を掛けるときは、同じ約束を満たすスクリプトを 1 本書いて
`REGIED_NETNS_ROUTER_SETUP` に指す。テスト側は変えなくてよい。

### 調べる

`REGIED_NETNS_KEEP=1` を付けて走らせるとトポロジを残す。`make netns-shell` で
同じコンテナのシェルに入り、`hack/netns/topo.sh up` で組み立て、
`hack/netns/topo.sh status` で各 netns のアドレスと経路を見られる。片付けは
`hack/netns/topo.sh down`。

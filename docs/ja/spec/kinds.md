# リソース kind

12 個の kind。これを収める文書の形は [`configuration.md`](configuration.md)、
なぜこの顔ぶれなのかは、最初の 11 個を決めた
[ADR 0002](../adr/0002-configuration-schema.md) と、12 個目についての
[ADR 0019](../adr/0019-uplink-address-in-dns-records.md) にある。

英語が正である。[docs/spec/kinds.md](../../spec/kinds.md) を参照。

以下、**リンクリソース**とはホストにリンクを作る 3 つの kind
（`Interface` / `PPPoESession` / `DSLiteTunnel`）を、**回線**とは
`PPPoESession` または `DSLiteTunnel` を指す。

| kind | バックエンド | 参照される名前 |
|---|---|---|
| [`Interface`](#interface) | systemd-networkd | `interfaceRef`、`underlayRef`、`linkRefs` |
| [`PPPoESession`](#pppoesession) | pppd | `egressRef`、`linkRefs` |
| [`DSLiteTunnel`](#dslitetunnel) | systemd-networkd | `egressRef`、`linkRefs` |
| [`EgressRoutePolicy`](#egressroutepolicy) | nftables + systemd-networkd | — |
| [`IPAddressSet`](#ipaddressset) | nftables | `addressSetRefs` |
| [`FirewallZone`](#firewallzone) | nftables | `from`、`to` |
| [`FirewallPolicy`](#firewallpolicy) | nftables | — |
| [`SourceNAT`](#sourcenat) | nftables | — |
| [`PortForward`](#portforward) | nftables | — |
| [`DHCPServer`](#dhcpserver) | dnsmasq | — |
| [`DNSForwarder`](#dnsforwarder) | dnsmasq | — |
| [`DNSRecordSet`](#dnsrecordset) | 事業者の HTTP API | — |

## Interface

両端を regied が持つリンク。物理 NIC か、複数をまとめたブリッジ。そのリンクの属性で
あるものをすべて持つ —— アドレス、MTU、そこから出ていく静的ルート、プレフィックス委譲の
クライアントを走らせるか、下のセグメントに広告するか。

バックエンド: `/etc/systemd/network/` の下、regied の接頭辞を持つ `.network`（ブリッジなら
`.netdev` も）。

| フィールド | 必須 | 値 |
|---|---|---|
| `ifname` | はい | カーネルのインターフェース名。ブリッジなら作る名前 |
| `bridge.members` | いいえ | 束ねるカーネルのインターフェース名。あればこれはブリッジ |
| `mtu` | いいえ | バイト。既定はカーネルのもの |
| `addresses` | いいえ | アドレスの一覧。後述 |
| `routes` | いいえ | 静的ルートの一覧。後述 |
| `dhcpv6` | いいえ | DHCPv6 クライアントの設定。後述 |
| `ipv6.advertise` | いいえ | ルーター広告の設定。後述 |

`bridge.members` に書くのは**カーネルのインターフェース名**であって、リソース名ではない。
メンバーに `Interface` リソースは要らない —— 従属させるファイルは regied が書く。
`Interface` として宣言するのは、MTU のようにそのメンバー自身の属性を与えたいときだけで、
そのときアドレスを持ってはならない。アドレスはブリッジのものであり、`FirewallZone` が
名指す名前もブリッジのものである。

`ifname` と `bridge.members` の各名前は、カーネルが保持できる名前である。上限は 15 文字
（`IFNAMSIZ` が 16 で、最後の 1 バイトは終端）。これを超える名前は検証エラーにする。
適用の途中でカーネルに撥ねられて分かるのでは遅い。

ブリッジはスパニングツリー無効・VLAN フィルタ無効、残りのタイマーはカーネルの既定で作る。
どれにもフィールドは無く、**これは意図的な省略である。** ここでスキーマが引き受けるのは
複数のポートを 1 つのセグメントにまとめることだけで、スパニングツリーを走らせる、あるいは
タグ付き VLAN を通すブリッジは別の要求である。それを必要とする構成が現れた時点で
フィールドを足すのであって、先回りしては足さない。

ブリッジは、メンバーにリンクがあってもなくても設定される。クライアントが 1 台も
挿さっていなくてもアドレスと、それにぶら下がるすべてを持ち、最後の 1 台が抜かれても
保つ。carrier を待つという networkd の既定は物理ポートには正しく、ブリッジには誤りで
ある。ブリッジの carrier が無いとは、まだクライアントが居ないという意味でしかない
（[ADR 0018](../adr/0018-loopback-forwarder-is-the-host-resolver.md)）。

### `addresses[]`

各要素は、プレフィックス長付きのアドレスのリテラル、委譲プレフィックスから導く指定、
このリンクで受け取るルーター広告のプレフィックスから導く指定のいずれか。マッピングで
書くときは `fromDelegatedPrefix` と `fromRouterAdvertisement` のちょうど 1 つを書く。

| フィールド | 必須 | 値 |
|---|---|---|
| *(文字列)* | — | リテラル。例 `192.0.2.1/24`、`2001:db8::1/64` |
| `fromDelegatedPrefix.interfaceRef` | はい | PD クライアントを走らせているインターフェース |
| `fromDelegatedPrefix.subnetID` | はい | 委譲されたプレフィックスのどのサブネットを取るか |
| `fromDelegatedPrefix.token` | いいえ | ホスト部。例 `::1`。既定はインターフェース識別子 |
| `fromRouterAdvertisement.token` | はい | ホスト部。例 `::153`。上位 64 ビットは 0 で、`::` は不可 |

導いたアドレスは委譲が変われば変わり、その上に建っているもの —— トンネルのローカル
アドレス、広告するプレフィックス、DNS が待ち受けるアドレス —— も一緒に変わる。
**結果を書き留めるのではなく導出を宣言するのは、この追随のためである。**

`fromRouterAdvertisement` は、ルーターではないホストにとっての同じ考え方である。
プレフィックスはリンクで受け取った広告から取り、ホストが自分で選んだ部分であるトークン
だけを持つ。ルーターが広告するプレフィックスを、もう 1 か所に書き写さずに済む。
このリンクはルーター広告を受け入れるので、広告が運ぶデフォルトルートも受け取り、
広告の other-configuration フラグが立っていれば残りを DHCPv6 に問い合わせる。
どちらも networkd の既定どおりで、必要とする構成が現れるまでフィールドは設けない。

`fromRouterAdvertisement` は Interface ごとに 1 つまでで、2 つ目は検証エラーになる。
networkd がリンクごとにトークンを 1 つしか取らないうえ、アドレスの出どころは 1 か所で
読めるべきだからである。リテラルのアドレス（典型的には IPv4）と並べて書いてよい。
これで得たアドレスは `ipv6.advertise` で下に広告されない。広告するのはリテラルの
プレフィックスと委譲プレフィックスだけである。

### `routes[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `destination` | はい | CIDR。ファミリは推論する |
| `via` | いいえ | next hop。省略するとこのインターフェースの on-link |
| `metric` | いいえ | 小さいほうが勝つ |

**テーブルを指定するフィールドは無い。** regied が作る追加のルーティングテーブルは
`EgressRoutePolicy` が必要とするものだけで、その中身は regied が自分で入れる。

### `dhcpv6`

上流（事業者に面する）インターフェースに置く。`prefixDelegation` を持つ限り、クライアントは
事業者のルーター広告に依らずプレフィックスを要求する。広告が届くかどうかにも、
届いた広告に M / O フラグが立っているかどうかにも左右されない。要求にはプレフィックス
（IA_PD）と一緒にアドレス（IA_NA）も載せる。プレフィックスだけの要求には答えない事業者が
あるからである。返事にアドレスが入らずプレフィックスだけ入るのが普通で、事業者がアドレスを
出してきた場合はその上流インターフェースに付く。

| フィールド | 必須 | 値 |
|---|---|---|
| `prefixDelegation.duidFile` | いいえ | 送る DUID を収めたファイルのパス。委譲を DUID に紐づける事業者がある |
| `prefixDelegation.iaid` | いいえ | プレフィックス要求に載せる IAID。委譲を DUID と IAID の組に紐づけ、違う IAID の要求には答えない事業者がある。入れ替える側のルーターの設定から値を持ち越す。未指定なら networkd がインターフェースから導いた値を送る |
| `prefixDelegation.prefixLength` | はい | 要求するプレフィックス長。例 `56` |
| `prefixDelegation.rapidCommit` | いいえ | 既定 `true` |
| `useDNS` | いいえ | 既定 `false`。事業者からリゾルバを受け取るか |

DUID ファイルには、DUID を型のプレフィックスごとコロン区切りの 16 進で、
**移植元の設定に現れる文字列のまま**書く。DUID-LL なら `00:03:00:01:` に 6 オクテットが
続く 29 文字であり、たとえば `00:03:00:01:00:00:5e:00:53:01` となる。regied は先頭 2 バイトを
DUID の型として切り出し、型と残りを分けて受け取りたがる networkd に渡す。

**`duidType` のようなフィールドは意図的に作らない。** この値は普通、入れ替える側の
ルーターの設定から丸ごとコピーしてくるものであり、手で分割させる形式は
**1 バイト落としても何も言われずに通る**経路を作る。そのとき失うのは委譲プレフィックスで、
損失が見えるのは下のセグメントの IPv6 アドレスがすべて変わった後である。

`duidFile` の省略は許され、エラーにもならない。networkd が machine-id 由来の DUID を
自前で送る。新規に引く回線ではそれが正しい。**既に委譲を受けている機器を入れ替える構成では、
それが委譲プレフィックスを変えるものの正体**であり、しかも派手に失敗してはくれない。

`iaid` も同じである。違うのは損失の見え方だけで、委譲を DUID と IAID の組に紐づける
事業者は、IAID の違う要求に別のプレフィックスを委譲するのではなく黙る。クライアントは
要求を繰り返すだけになる。入れ替える側のルーターが送っていた値はたいてい `0` であり、
`0` は宣言した値であって省略とは別物である。省略すると選択は networkd に渡り、networkd は
IAID をインターフェースから導くので、入れ替えられる側の値と偶然一致することはない。

DUID は認証情報ではなく、認証情報と違って `--dry-run` の出力にも差分にも状態 API にも
出す。[ADR 0003](../adr/0003-secrets-out-of-configuration.md) の唯一の例外であり、
委譲プレフィックスが変わった理由に答えるのが、いま効いている DUID だからである。

### `ipv6.advertise`

下流インターフェースに置く。**ルーター広告は dnsmasq ではなく systemd-networkd のもの
である。** プレフィックスは委譲から来るもので、networkd が既にそれを追っている。
インターフェースに置いてあるので、**同じリンクに 2 人目の広告者を頼む場所が
スキーマのどこにも無い。**

| フィールド | 必須 | 値 |
|---|---|---|
| `mode` | はい | `slaac` —— ステートレス自動設定のためにプレフィックスを広告する |
| `otherInformation` | いいえ | 既定 `false`。O フラグを立て、残りは DHCPv6 に聞けと伝える |
| `dnsServers` | いいえ | RDNSS として広告する |
| `validLifetime` | いいえ | 既定 `24h`。リテラルのプレフィックスにだけ効く。後述 |
| `preferredLifetime` | いいえ | 既定は `validLifetime` の半分。リテラルのプレフィックスにだけ効く |

広告するプレフィックスはこのインターフェースが持っているものである。ここに書かないので、
実際に設定されているアドレスとずれようが無い。

**この 2 つの寿命が効くのは、リテラルのアドレスとして書いたプレフィックスだけである。**
委譲で来たプレフィックスを広告するのは委譲そのものであり、networkd はその寿命を委譲から
取る。事業者がどれだけ有効と言っているかを下流の広告が延ばしてよいはずもなく、
上書きする指定も無い。IPv6 アドレスがすべて導出であるインターフェースでどちらかを
書くと、レンダリング時に警告する。書いたものがどこにも行かないからである。

## PPPoESession

PPPoE の回線。systemd-networkd に PPPoE は無いので、regied が pppd の設定を生成し、
プロセスを監督する。

バックエンド: pppd の peer ファイル、権限を絞った secrets ファイル、監督下の `pppd`。

| フィールド | 必須 | 値 |
|---|---|---|
| `interfaceRef` | はい | この回線を載せる `Interface` |
| `userIDFile` | はい | アカウント名を収めたファイルのパス。認証情報として扱う |
| `passwordFile` | はい | パスワードを収めたファイルのパス |
| `mtu` | いいえ | 既定 `1492`。Ethernet 上の PPPoE で取れる最大 |
| `persist` | いいえ | 既定 `true`。切れたら掛け直す |
| `holdoff` | いいえ | 既定 `5s`。掛け直す前に待つ時間 |
| `useDNS` | いいえ | 既定 `false`。相手からリゾルバを受け取るか |
| `defaultRoute.install` | いいえ | 既定 `true`。main テーブルにデフォルトルートを入れる |
| `defaultRoute.metric` | いいえ | 既定 `0`。上げるとこの回線は待機側になる |
| `routes` | いいえ | `Interface` と同じ |

リンク名は `metadata.name` から付ける。掛け直しをまたいで、他のリソースと
ファイアウォールから見える名前が変わらない。つまりこの名前はカーネルの
インターフェース名であり、`ifname` と同じ 15 文字の上限が掛かる。

`defaultRoute.metric` は、回線が 2 本あるホストが「**自分自身の通信**はどちらを使うか」
を言う場所である。ルーター起点の通信はポリシールーティングに掛からないので、
これだけが決め手になる。

認証情報のファイルは `--dry-run` の出力にも差分にも状態 API にも現れない
（[ADR 0003](../adr/0003-secrets-out-of-configuration.md)）。

## DSLiteTunnel

IPv4 over IPv6 の回線。RFC 6333 の B4 側である。IPv4 パケットを IPv6 でカプセル化して
事業者の AFTR に渡し、アドレス変換は AFTR が行う。

バックエンド: kind `ip6tnl` / mode `ipip6` の `.netdev` と、その `.network`。

| フィールド | 必須 | 値 |
|---|---|---|
| `underlayRef` | はい | トンネルを載せる IPv6 を持つ `Interface` |
| `localAddressFrom.interfaceRef` | どちらか | このインターフェースの IPv6 アドレスをトンネルのローカルアドレスにする。後述 |
| `localAddress` | どちらか | IPv6 アドレスのリテラル。静的にアドレスを持つ構成向け |
| `aftrHost` | どちらか | 事業者の AFTR。名前で書く。適用時に解決する |
| `aftrAddress` | どちらか | 事業者の AFTR。IPv6 アドレスのリテラル |
| `mtu` | いいえ | 既定 `1454` |
| `ttl` | いいえ | 既定 `64` |
| `defaultRoute.install` | いいえ | 既定 `true` |
| `defaultRoute.metric` | いいえ | 既定 `0` |
| `routes` | いいえ | `Interface` と同じ |

トンネルのリンク名は `metadata.name` から付ける。つまりこの名前もカーネルの
インターフェース名であり、`ifname` と同じ 15 文字の上限が掛かる。

`localAddressFrom` と `localAddress` はちょうど一方が必須。プレフィックスが委譲で
来る構成では `localAddressFrom` を使う。**プレフィックスが変わったときに、誰かが
ファイルを直すまで沈黙するのではなく、トンネルが追随する。**

**regied が対象とするプラットフォームでは、`localAddressFrom` に書けるのは下位リンクだけ
である。** トンネルのローカルアドレスは networkd の `[Tunnel]` の `Local=` であり、
systemd 257 がここに取るのはトンネルを積んでいるリンクのアドレス —— `slaac` か `dhcp6`
—— である。委譲プレフィックスから取るための値 `dhcp_pd` は systemd 258 で入ったもので、
Debian 13 には無い（[ADR 0011](../adr/0011-target-platform.md)）。だからこのフィールドは
下位リンク自身のグローバルアドレスとして描画され、それ以外のインターフェースを名指した
場合は警告する。トンネルは上がるが、ファイルが求めたのとは別のアドレスから送る。
フィールドの意味は変わらない —— アドレスを書き下すのではなくインターフェースから取る、
である。名指したとおりに動くようになるのは、systemd 258 を積んだプラットフォームである。

`aftrHost` と `aftrAddress` も、上の組と同じくちょうど一方が必須である。
**手を伸ばすべきなのは `aftrHost` のほうである。** 事業者は AFTR の安定した well-known な
名前を公開しており、その裏のアドレスは自分たちの都合で変えてよいものとして扱っている。
つまり**名前が公式な識別子で、アドレスは実装詳細**である。実装詳細を写し取るのは、
`PortForward` が待ち受けアドレスを受け取らないことで避けている失敗と同じ形である。
相手が「変えない」と約束していないものを変えるまでは動き、変わった時点で、
何も言わずに止まる。

`aftrHost` を解決するのは適用時の 1 回だけで、返ってきたアドレスでトンネルを作る。
**regied は名前を監視しないし、再解決もしない。** `ip6tnl` のリンクは作成時に remote を
要求し、networkd は DHCP のイベントでトンネルを作り直さない。名前に追随させるには、
regied が**自分でレンダリングした後の状態を見て、そこから作り直す**ことになり、
それは [ADR 0009](../adr/0009-ownership-boundary.md) が意図して避けた構造である。
アドレスが変わったときの答えは、もう一度の適用である。**駆動されるのではなく選んで行い、**
事前に `--dry-run` で見え、ロールバックできる。

`--dry-run` は名前が解決した先のアドレスを報告する。これは秘密ではなく、
**いま何に向かってトンネルを張ろうとしているのか**は診断にまさに要る情報である。
[ADR 0003](../adr/0003-secrets-out-of-configuration.md) で DUID に与えたのと同じ扱いになる。

**`aftrHost` は IPv6 で解決できなければならない。** IPv4 を運んでいるのがそのトンネルなので、
IPv4 でしか届かないリゾルバにはトンネルが上がるまで何も訊けない。他にリゾルバが無いホストは、
**トンネルを作るための名前を引くのにそのトンネルを要する**ことになる。リゾルバに IPv6 で
届くかどうかは構成の性質であって設定が述べていることではないので、regied はこの循環を
静的に弾こうとはしない。解決するのは適用時であり、解決しない名前 —— あるいは IPv6 の
アドレスを返さない名前 —— は、その周回を失敗させるのではなく、トンネルをその周回から
省く。周回はその名前を待っていると言い、名前が答えた後の周回がトンネルを作る
（[ADR 0016](../adr/0016-converging-on-the-accepted-declaration.md)）。起動した直後の
ホストでは、まだ上がっていないのがリゾルバであることが多い。

**AFTR を DHCPv6 から学ぶフィールドは作らない。これは見落としではなく決定である。**
RFC 6334 のオプション 64 は AFTR の名前を運ぶ。つまり届くのは `aftrHost` が受け取るのと
同じ FQDN であってアドレスではなく、解決の手順も、それについて上に書いたことも、
そのまま残る。変化に追随させようとすれば `ip6tnl` の制約に再び当たる。remote は
リンクを作るときに固定されるので、regied が監視して作り直すことになる。
そして**この選択肢を使い切ってはいない。** オプション 64 を送ってくる事業者に当たった構成では、
`aftrHost` の供給元が 1 つ増えるだけであり、これらのフィールドの意味を変える話ではない。

**この回線に `SourceNAT` を置いてはならない。** AFTR が変換するので、内側の送信元
アドレスはそのままにする。ここで masquerade を掛けると二重変換になる。同じ理由から
この回線で内向きに公開できるものは無く、これを名指す `PortForward` は検証エラーになる。

## EgressRoutePolicy

ある種別のトラフィックがどの回線から出るか。トラフィックを特定する**判定**と、
そこから決まる**経路**の両方を、1 つのリソースが持つ。

バックエンド: マークを打つ nftables ルールと、専用テーブルの `[RoutingPolicyRule]` および
デフォルトルート（どちらも systemd-networkd）。

| フィールド | 必須 | 値 |
|---|---|---|
| `family` | いいえ | 既定 `ipv4` |
| `priority` | はい | 小さいほうを先に評価する。ファミリの中で一意 |
| `egressRef` | はい | このトラフィックが出ていく回線 |
| `sourceRanges` | いいえ | CIDR、または `192.0.2.130-192.0.2.255` のような閉区間 |
| `sourceAddressSetRefs` | いいえ | `IPAddressSet` の名前。レンジを直接書く代わりに使う |
| `excludeDestinations` | いいえ | この回線に送ってはならない宛先の CIDR |
| `table` | いいえ | ルーティングテーブル番号を regied に選ばせず固定する |
| `mark` | いいえ | ファイアウォールマークを固定する |

`sourceRanges` と `sourceAddressSetRefs` は少なくとも一方が必要。

`sourceRanges` が取るのは上の表にある 2 つの形だけで、3 つ目は無い。裸のアドレスは
検証エラーである。`192.0.2.1/32` が既にある形で同じことを言えており、
1 つの意味に 2 つの書き方があると、その分だけ食い違う余地が増える。

**`excludeDestinations` がローカルの通信をローカルに留める。** 「このホスト群は PPPoE から
出る」と書いた政策は LAN 自身を除外しなければならず、さもないと LAN 内どうしの通信まで
回線に送られる。これは hairpin を成立させるものでもある。ただし間接的に、である。
マークは宛先変換の後で打たれるので、LAN 側の端末が回線のグローバルアドレス経由で
公開サービスに繋ぎに行くとき、その時点で宛先は既に内側のホストになっている。
だからこの除外に当たってローカルに留まる。**グローバルアドレスを知る必要がどこにも無い。**

`table` と `mark` は、ルーティングテーブルを他の何かと共有するホストのためにある。
省略すると regied が割り当て、その結果を `regied render` が報告する。

`EgressRoutePolicy` を 1 つでも書くと、`spec.global.sourceValidation` は無効でなければ
ならない。ポリシールーティングは戻りの経路を非対称にし、リバースパスフィルタは
まさにそれを落とす。

## IPAddressSet

名前の付いたアドレス／プレフィックスの集合。ホストのまとまりを 1 度書いて、
複数のルールから参照するためのもの。

バックエンド: regied のテーブルの中の nftables set。

| フィールド | 必須 | 値 |
|---|---|---|
| `family` | はい | `ipv4` または `ipv6` |
| `addresses` | いいえ | 個々のアドレス |
| `networks` | いいえ | プレフィックス |

2 つのリストの少なくとも一方は空でないこと。プレフィックスを含む集合は interval set になる。

## FirewallZone

名前の付いたリンクの集合。ファイアウォールの政策は、ゾーンとゾーンの間に書く。

バックエンド: インターフェース名の nftables set。

| フィールド | 必須 | 値 |
|---|---|---|
| `linkRefs` | はい | リンクリソースの名前 —— `Interface` / `PPPoESession` / `DSLiteTunnel` |

**`wan` や `lan` はただのゾーン名であって、スキーマが知っている概念ではない**
（[ADR 0009](../adr/0009-ownership-boundary.md)）。ルーターでないホストは、
実際にあるものに沿ってゾーンに名前を付ける。

`self` は予約名で、ゾーン名に使えない。ホスト自身を指す。

## FirewallPolicy

あるゾーンから別のゾーンへ、またはあるゾーンからホスト自身へ向かうトラフィックに
適用するルール。

バックエンド: regied の nftables テーブルの中のチェーン。hook のチェーンから
インターフェース集合で振り分ける。

| フィールド | 必須 | 値 |
|---|---|---|
| `from` | はい | `FirewallZone` の名前 |
| `to` | はい | `FirewallZone` の名前、または `self` |
| `defaultAction` | はい | `accept` / `drop` / `reject` —— どのルールにも当たらなかったとき |
| `logDefault` | いいえ | `defaultAction` が `accept` でなければ既定 `true` |
| `stateful` | いいえ | 既定 `true`。後述 |
| `rules` | いいえ | 順に評価する。最初に当たったものが勝つ |

netfilter の hook は組から決まる。`to: self` は input、ゾーンからゾーンは forward。
**output に対する政策は無い。** ホスト自身が送り出すものをここで絞ることはしない。
したがって `self` は `to` にだけ現れ、`from` には現れない。`from` に書いた政策は、
黙って何にも当たらない政策になるのではなく検証エラーになる。

**政策が書かれていないゾーンの組は drop される。** 誰も書かなかったからといって
その組が暗黙に開くことは無い。

**`stateful: true` は、どのチェーンにも要る 2 つのルールを先頭に置く。**
established / related を accept し、invalid を drop する。政策ごとに手で書くのは、
1 つ書き忘れる書き方である。

同じ `from` と `to` を持つ政策は 1 つだけ。

### `rules[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `name` | はい | 診断のため。カウンタとログの接頭辞に出る |
| `action` | はい | `accept` / `drop` / `reject` |
| `family` | いいえ | `ipv4` / `ipv6`。省略すると両方 |
| `protocol` | いいえ | `tcp` / `udp` / `icmp` / `icmpv6` / `ipip` / `esp`、またはプロトコル番号 |
| `sourceCIDRs` | いいえ | |
| `sourceAddressSetRefs` | いいえ | `IPAddressSet` の名前 |
| `sourcePorts` | いいえ | 数値、または `60000-60010` のような範囲 |
| `destinationCIDRs` | いいえ | |
| `destinationAddressSetRefs` | いいえ | |
| `destinationPorts` | いいえ | |
| `log` | いいえ | 既定 `false` |

ルールとファミリの合わないアドレス集合を参照するのは検証エラー。

**落とすと静かに壊れる**ので知っておく価値のあるルールが 2 つある。

- **上流ゾーンから `self` への `protocol: ipip`** が無いと、DS-Lite のトンネルが
  そもそも上がらない。カプセル化されたパケットはこのホスト宛に届く
- **上流ゾーンから `self` への udp 宛先ポート 546** が無いと、DHCPv6 クライアントが
  応答を受け取れず、したがってプレフィックスの委譲も受けられない

## SourceNAT

出ていくトラフィックの送信元アドレスを書き換える。

バックエンド: regied の nftables postrouting チェーンのルール。

| フィールド | 必須 | 値 |
|---|---|---|
| `type` | いいえ | `masquerade` が唯一の値であり既定 |
| `egressRef` | はい | 適用する回線。アドレスはその回線に追随する |
| `sourceRanges` | いいえ | CIDR。省略するとすべての送信元 |
| `excludeDestinations` | いいえ | 変換せずに通す宛先の CIDR |

`masquerade` はパケットが出る時点で出口リンクからアドレスを取る。だから動的アドレスの
回線でも、書き留めるものは何も無く、アドレスが変わっても再適用は要らない。

`DSLiteTunnel` に対する `SourceNAT` は検証エラー。AFTR が既に変換している。

## PortForward

回線に着いたトラフィックの宛先を書き換え、内側のホストに外から到達できるようにする。

バックエンド: 宛先 NAT のルール、hairpin のための送信元 NAT のルール、
そして（切らない限り）変換後のトラフィックを通すファイアウォールの穴。

| フィールド | 必須 | 値 |
|---|---|---|
| `egressRef` | はい | トラフィックが着く回線。待ち受けアドレスはその回線に追随する |
| `protocol` | はい | `tcp` または `udp` |
| `port` | どちらか | ポート 1 つ |
| `portRange` | どちらか | 閉区間。例 `60000-60010`。**1 本のルールで表す** |
| `target.address` | はい | 内側のホスト |
| `target.port` / `target.portRange` | いいえ | 既定は受けと同じ |
| `hairpin` | いいえ | 既定 `true` |
| `openFirewall` | いいえ | 既定 `true` |

**待ち受けアドレスを書くフィールドは無い。** それは回線のものであり、動的アドレスの
回線でそれを書き留めると、アドレスが変わるまでは動き、変わった瞬間に「別の何かが
壊れたように見える形」で失敗する設定ができる。`egressRef` がすべてである。

**`hairpin`** は、内側のホストが回線のグローバルアドレス経由で同じサービスに繋ぐ場合を
扱う。内側の端末が外側と同じ公開名を解決すれば、これが起きる。無いと応答が転送先から
端末へ直接返り、変換を通らないので端末はそれを捨てる。

**`openFirewall`** は、変換後のトラフィックが通る経路に、この転送に対応する accept を
足す。既定で有効なのは、既定 drop のファイアウォールで穴の無いポートフォワードは
**どの場合でも間違い**だからである。切るのは、より狭いルールを手で書くときだけ。

**`protocol` が取るのはこの 2 つの名前だけで、それ以外は取らない。** ファイアウォールの
ルールはプロトコル番号を受けるが、このフィールドは受けない。これは書き落としではない。
転送するのはトランスポートのポートであり、ポートを持たないプロトコルには転送するものが
無いからである。`tcp` のつもりで `6` と書いたものは、同じ意味として黙って受けるのではなく
拒否する。

**変換先は、待ち受けるのと同じ数のポートを覆っていなければならない。** 11 ポートを
11 ポートに落とすのは転送であり、11 ポートを 2 ポートに落とすのは検証エラーである。
後者では、外側のどのポートが内側のどれに着くかがどこにも書かれておらず、カーネルが決める。
**設定ファイルがホストの動作を説明しなくなる。** それはこのスキーマ全体が避けようとしている
壊れ方である。`target.port` と `target.portRange` を書かなければ幅は構造上一致し、
それが普通の書き方である。

`egressRef` が `DSLiteTunnel` を指す `PortForward` は検証エラー。
そこから公開できるものは無い。

**変換先は、そのフォワードが乗る回線から出ていくホストでなければならない。**
回線に入ってきた接続の戻りは、答えるホストの送信元アドレスで経路が決まる。だから
ポリシールーティングをしているホストでは、変換先はその回線に送る `EgressRoutePolicy` の
レンジの内側になければならない。どのレンジにも入っていない変換先は、届きはするが
答えが返らない。regied はこれを警告する。

## DHCPServer

配下のリンクへのアドレス配布。

バックエンド: dnsmasq。すべての `DHCPServer` と `DNSForwarder` が 1 つの dnsmasq 設定と
1 つの監督下プロセスに落ちる。

| フィールド | 必須 | 値 |
|---|---|---|
| `interfaceRef` | はい | 対象のリンク |
| `subnet` | はい | プールと静的マッピングが収まる CIDR |
| `pool.start`、`pool.end` | はい | 両端を含む。サブネットの一部でよい |
| `leaseTime` | いいえ | 既定 `24h` |
| `gateway` | いいえ | 既定はインターフェース自身のアドレス |
| `dnsServers` | いいえ | 既定はインターフェース自身のアドレス |
| `domain` | いいえ | 端末に渡す検索ドメイン |
| `staticMappings` | いいえ | 後述 |
| `ipv6` | いいえ | ステートレス DHCPv6。後述 |

サブネットより狭いプールは普通の使い方である。残りは静的マッピングと、
手で振るアドレスのために空けておく。

### `staticMappings[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `name` | はい | 配り、登録するホスト名 |
| `macAddress` | はい | |
| `address` | はい | `subnet` の中、かつ `pool` の外 |

ポリシールーティングが送信元レンジで回線を選ぶ構成では、**静的マッピングが境界の
どちら側に落ちるかが、そのホストの使う回線を決める。** マッピングを境界の向こうに
動かすのは見た目の変更ではなく経路の変更である。

### `ipv6`

IPv6 設定のステートレスな半分のためにある。プレフィックスとルーター広告は
インターフェース側（[`Interface.ipv6.advertise`](#ipv6advertise)）から出る。
ここにあるのは、**広告に言われた端末が DHCPv6 に聞きに来たときに答えるもの**である。

| フィールド | 必須 | 値 |
|---|---|---|
| `mode` | はい | `stateless` —— 情報要求に答え、アドレスは配らない |
| `dnsServers` | いいえ | |
| `informationRefreshTime` | いいえ | 既定 `6h` |

インターフェースの広告に `otherInformation` が無いままこれを書くと検証の警告になる。
誰も聞きに来ないからである。

## DNSForwarder

配下のセグメントのための名前解決。条件付きフォワードと名前の上書きを含む。

バックエンド: dnsmasq。すべての `DHCPServer` と併合して 1 つの設定になる。

| フィールド | 必須 | 値 |
|---|---|---|
| `listenOn` | はい | リンクリソースの名前と、予約名 `loopback` |
| `cacheSize` | いいえ | 既定 `150` 件 |
| `upstreams` | はい | 上位リゾルバのアドレス。IPv4 / IPv6 |
| `conditional` | いいえ | 後述 |
| `staticHosts` | いいえ | 後述 |

`listenOn` はアドレスではなくリンクを名指す。だから委譲プレフィックスからアドレスを
導いているインターフェースでも、プレフィックスが変わった後も待ち受け続ける。

`loopback` はホスト自身を意味し、その意味は双方向である。dnsmasq は loopback の
アドレスで答え、regied はホスト自身のリゾルバをそこへ向ける。ブリッジのポートでない
`Interface` のために書くすべての `.network` に、そのリンクの DNS サーバーとして、
また他のどのリンクも引き受けない名前の送り先として `127.0.0.1` を書き、
systemd-resolved がそれを networkd から受け取る。回線で事業者のリゾルバを断った
（`useDNS: false`）ホストが、リゾルバ無しで取り残されることはなくなる。`listenOn` に
並ぶリンクではなく、アドレスを持つすべてのリンクに載せるのは、resolved がリンクの
上位を使うのは、そのリンクが up で carrier とアドレスを持つ間だけであり、誰も挿さって
いないブリッジには carrier が無いからである。`loopback` を列挙しながら、載せ先になる
`Interface` を 1 つも宣言しない設定には render が警告を出す。dnsmasq は loopback で
答えるが、ホストにそれを聞けとは伝わらない
（[ADR 0018](../adr/0018-loopback-forwarder-is-the-host-resolver.md)）。

**ホストに `DNSForwarder` は高々 1 つであり、2 つ目は検証エラーである。**
dnsmasq はプロセス 1 つ・キャッシュ 1 つ・上位リゾルバ 1 組しか持たない。だから
リソース 2 つはそこへ併合するほかなく、その併合が何を決めたのか —— どちらの
キャッシュサイズが勝ったのか、片方の端末が結局どの上位に聞いたのか —— は
どこにも書かれない。この kind が表せるものは 1 つのリソースに収まる。
`listenOn`・`upstreams`・`conditional`・`staticHosts` はいずれも配列であり、
複数のセグメントの名前解決をするホストも、ここにまとめて並べる。

### `conditional[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `domain` | はい | 振り分けるゾーン |
| `servers` | はい | 上位の代わりに聞きに行く先 |

内部のゾーン —— たとえばクラスタのサービスドメイン —— を、それを知っているリゾルバに
解かせ、それ以外は上位に流すための仕組みである。

### `staticHosts[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `name` | はい | FQDN 1 つ |
| `address` | はい | 返す答え |

名前 1 つの上書き。よくある用途は、公開名を内側の端末には内側のアドレスで返し、
回線を出て戻ってくるのではなく直接そのサービスに繋がせることである。

## DNSRecordSet

1 つの DNS ゾーンの中で regied が保つレコード。`PortForward` で公開した名前が、
回線がいま持っているアドレスに解決されるようにするためにある。動的に割り当てられる
回線ではこのアドレスが変わり、古いアドレスを持ったままのレコードは、誰かが手で直すまで
外からサービスに届かなくする。

バックエンド: 事業者の HTTP API。regied が話す相手のうち、このホストの上に無い唯一の
ものであり、ホストに CA 証明書が要る唯一の理由でもある
（[ADR 0011](../adr/0011-target-platform.md)）。

| フィールド | 必須 | 値 |
|---|---|---|
| `provider` | はい | `cloudflare` |
| `zone` | はい | これらのレコードが属するゾーン。例: `example.com` |
| `apiTokenFile` | はい | 書き込みに使う API トークンを持つファイルのパス |
| `records` | はい | このゾーンの中で regied が保つもの。1 件以上。下記参照 |

**これはゾーンの *中の* レコードの集まりであって、ゾーンではない。** regied はここに
並んだ名前を書き、ゾーンのそれ以外については何も知らない。この一覧から外れたレコードは
追従されなくなるだけで、消されない。レコードに regied のものという印も付けない
（[ADR 0009](../adr/0009-ownership-boundary.md)、
[ADR 0019](../adr/0019-uplink-address-in-dns-records.md)）。

**1 ゾーン 1 リソースが基本の形である。** ゾーンに結びつくのはトークンであり、
1 つのゾーンだけに効くトークンの方が小さい credential だからである。共有していた
トークンをゾーンごとに分けるのは、各リソースのパスを 1 つずつ書き換えることになる。
同じゾーンを名指すリソースが 2 つあっても受け付ける —— それぞれ自分のトークンを持つ、
2 組のレコードである —— が、同じ名前と型を求める項目が 2 つあるのは検証エラーである。
1 つのリソースの中でも、2 つのリソースにまたがっていても同じで、レコードが結局どちらを
持つことになるのかがどこにも書かれていないからである。

**`provider` は必須で、値は `cloudflare` だけである。** 実装は 1 つで、2 つ目を受け入れる
インターフェースは無い。それでも名前を書かせるのは、2 つ目ができた日に宣言を有効なまま
保つためである。ファイルが自分の話し相手を言っているので、2 つ目の事業者は値が 1 つ
増えることであって、既にあるすべてのファイルを書き換えることではない。

**`apiTokenFile` は credential を名指す。** その中身は `--dry-run` の出力にも、差分にも、
ログにも、ターンの報告にも現れない
（[ADR 0003](../adr/0003-secrets-out-of-configuration.md)）。レコードを書くターンで読み、
捨てる。dry run はそもそも読まない。dry run は何も書かないからである。ファイルが無い、
読めない、空である場合は検証エラーになる。

### `records[]`

| フィールド | 必須 | 値 |
|---|---|---|
| `names` | はい | FQDN。それぞれ `zone` の中にあること。1 つ以上 |
| `type` | いいえ | `A`。既定であり、いまのところ唯一の値 |
| `egressRef` | はい | これらの名前が追従する回線。アドレスはそこから取る |
| `proxied` | いいえ | 既定は `false`。Cloudflare のプロキシの指定 |
| `ttl` | いいえ | 既定は `automatic`、つまり事業者に決めさせる。ほかに持続時間を書ける |

1 項目は、複数の名前にかかる 1 組の属性である。ゾーンの頂点とワイルドカードはこう書く。
同じ回線に追従し、同じ指定を欲しがるからである。名前はそれぞれ事業者側で 1 本のレコードに
なる。

**どの名前もゾーンの中になければならない。** ゾーンと等しいか、ドットに続けてゾーンで
終わるかである。外にある名前は、事業者が毎ターン拒むリクエストではなく、検証エラーに
する。

**`type` は `A` であり、`AAAA` は理由を添えて拒む。** ここのレコードが追従するのは
このホストの回線が持つアドレスであり、そのアドレスが外の世界の到達先になるのは IPv4 の
側である。構成が実際に欲しがる IPv6 の形は、委譲プレフィックスの中の、このホストの後ろに
いるホストのアドレス —— **このホストが経路を持つアドレス** —— であり、それは別の決定で、
まだ決めていない（ADR 0019）。フィールドがあるのは、その決定をしたときにフィールドでは
なく値が 1 つ増えるようにするためである。

**`egressRef` は回線を名指し、`DSLiteTunnel` は検証エラーである。** トンネルの IPv4 は
AFTR が変換するので、そこからは何も公開できず、レコードが持つべきアドレスも無い。
トンネルを名指す `PortForward` が受ける拒否と同じものである。

**`proxied` は Cloudflare のものである。** 事業者ごとの入れ物に入れず、素のフィールドと
して置く。事業者が 1 つなら入れ物は要らず、2 つ目ができたときにこれを検査可能にするのが
`provider` だからである。プロキシを通した名前は事業者自身のアドレスに解決され、regied が
書くアドレスは事業者がその先に流す相手になる。

**`ttl` は `automatic` か持続時間である。** `automatic` は事業者に選ばせることで、
フィールドを書かない場合と同じである。書くのは、既定を知っている読み手でなくても分かる
ようにするためである。1 分未満または 24 時間を超える持続時間は検証エラーである。事業者が受け付ける範囲の外だからである。`proxied: true`
のレコードに持続時間を書くのも検証エラーである。プロキシを通したレコードの TTL は事業者の
ものであり、両方を書いた宣言は毎ターン拒まれるものを求めている。

### ターンがレコードに対して行うこと

| いつ | 何が起きるか |
|---|---|
| 回線がアドレスを持っていない | それに追従するレコードはすべてそのままにし、ターンは何を待っているかを言う |
| アドレスが、このプロセスが最後に書いた値と違う | レコードを書く |
| レコードが事業者に無い | 作る |
| レコードが事業者にある | アドレスと宣言された属性を更新し、それ以外のフィールド —— 誰かが書いたコメントなど —— はそのままにする |
| このプロセスで既に書いてあり、アドレスも動いていない | 事業者には何も尋ねない |
| 書き込みに失敗した | そのレコードが *失敗中* になり、自分だけのバックオフに入る。ターンの残りは最後まで進む |

**決めるのは、このプロセスが最後に書いた値であって、事業者が持っているものではない。**
事業者はターンのたびには読まない。レコードごとに 1 度だけ、作るのか更新するのかを決める
識別子のために尋ねる。この記憶はプロセスの中にあってディスクには無いので、起動の直後は
空である。そして空は **分からない** であって **同じ** ではないので、起動後の最初のターンが
すべてのレコードを 1 度書く。その費用は起動ごと・レコードごとに 1 回の書き込みであり、
もう一方の案の費用は、数年に数回しか変わらないアドレスのために、再同期ごと・レコード
ごとに 1 回の読み取りである。

引き換えに、事業者側で人が手で編集したレコードは、アドレスが変わるか regied が再起動する
まで元に戻らない。

**`--dry-run` は、書くことになるレコードと書くアドレスをすべて名指し、事業者には何も
尋ねない。** トークンも読まない。dry run が見せるべきものを決めるのは記憶とカーネルで
あり、どちらも手元にあるからである
（[ADR 0006](../adr/0006-dry-run-and-rendering.md)）。起動したばかりのプロセスでは、
すべてのレコードが「書くことになるもの」として出る。ターンが実際にすることがそれである。

**regied を止めると更新も止まる。** デーモンを止めたホストのレコードは最後に持った値の
ままになる。それが止めるレバーの意味である。

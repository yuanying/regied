# ADR 0019: DNS レコードを回線のアドレスに保つ

- 状態: 決定（2026-09-11）。決着・実装済み（2026-09-12）。

> **以下の方向を先に決め、あとから作った。** この記録が残した 6 つの問いの答えは
> [作るときに決めたこと](#作るときに決めたこと)にある。答えがとった形は
> [`docs/ja/spec/kinds.md`](../spec/kinds.md#dnsrecordset) の `DNSRecordSet` kind で、
> 実例は [`config/example.yaml`](../../../config/example.yaml) にある。spec は regied が
> 受け付けるものを書く場所であり、この記録はその理由を書く場所である。

## 背景

### 要件

`PortForward` でサービスを公開するホストは名前で到達され、その名前は回線が持つ
アドレスに解決されなければならない。動的に割り当てられる回線では、このアドレスが
変わる。再接続で、事業者の保守で、再起動で。古いアドレスを持ったままのレコードは、
誰かが手で直すまで外からサービスに届かなくする。これはスキーマがわざわざ避けている
壊れ方そのものである。アドレスが変わるまでは動き、変わった途端に、別の原因に見える
形で止まる。

想定する構成は、事業者がアドレスを割り当てる回線が 1 本か 2 本あり、DNS のゾーンを
Cloudflare に置いて、その API で編集するものである。

### このアドレスについてスキーマが既に言っていること

スキーマには回線のグローバルアドレスを書けるフィールドが無く、それは意図したもので
ある（[ADR 0002](0002-configuration-schema.md)）。`SourceNAT` と `PortForward` は回線を
参照してそこからアドレスを取り、hairpin のルールはアドレスそのものではなく、
アドレスに追従するセットにマッチする（[ADR 0015](0015-uplink-addresses-in-sets.md)）。
アドレスを持つ DNS レコードは、同じ値がもう 1 か所に現れたものであり、同じ理屈が
当てはまる。書き留めるのではなく、回線に追従させるべきである。

### regied が既に知っていること

常駐プロセスはターンのたびに、すべての回線のアドレスをカーネルから読む。カーネルの
アドレスイベントはターンを早めに起こす
（[ADR 0016](0016-converging-on-the-accepted-declaration.md)）。レコードが持つべき
アドレスは、変わったその瞬間に、それについて権威を持つ情報源から、既に手元にある。

### 障害になるもの

**範囲。** [`docs/ja/scope.md`](../scope.md) は「クラウド事業者 API との連携」を
やらないものに挙げており、その一覧にあるものは黙って足すのではなく新しい決定として
記録せよと書いている。この記録がそれである。

**委譲。** [ADR 0008](0008-delegate-to-existing-implementations.md) は、regied は誰も
持っていない層だけを持つと言う。動的 DNS のクライアントは既にあり、いくつかは
Cloudflare の API を話し、ディストリビューションのパッケージにもなっている。

**そのクライアントがアドレスを知る方法。** よくある既定は、外部のサービスに
「リクエストがどのアドレスから来たか」を尋ねるものである。答えは、ホスト *自身の*
通信が出ていく回線のアドレスになる。それを決めるのは `defaultRoute.metric` であって、
サービスをどこで公開しているかではない。記載例と同じ形のホスト —— ポートフォワードは
PPPoE セッションに、ホスト自身の通信は DS-Lite トンネルに —— では、答えは AFTR の
共有アドレスになり、そこからは何も公開できない。クライアントにインターフェースを
読ませることもできるが、そうするとクライアントが正しいのは、その設定を宣言と手で
揃え続けている間だけになる。

## 決定

### 範囲に入れる。線はホストについてのまま

**regied は、事業者の DNS レコードを、このホストの回線が持つアドレスに保つよう
書いてよい。** `docs/scope.md` への例外はこれがすべてである。

あの節が引いている線はホストについてのものである。regied は 1 台のノードを見て、
他のノードを管理せず、設定を配布せず、自分の設定を事業者の制御面に頼らない。
このどれも動かない。このホストのアドレスを事業者に伝えること —— 外向きに、この
ホストについて、人が提出した宣言から —— は、[ADR 0007](0007-resident-process.md) が
他のシステムから読むことを線の手前に置いたのと同じ意味で、線の手前にある。線は
どのホストを管理しているかについてであって、ネットワークの API と話すかどうか
についてではない。

範囲の外に残るもの。事業者から設定を受け取ること、他のホストの回線を表すレコードを
管理すること、レコードにアドレスを持たせる以上の事業者の機能。

### 動的 DNS のクライアントに任せず、regied 自身がやる

ADR 0008 の試金石は、その層を既に誰かが持っているかどうかである。ここでの層は 2 つ
あり、他所が持っているのは片方だけである。

- **事業者の API と話すこと** は他所が持っており、小さい。トークンで認証し、
  レコードを読み、その内容を書く。
- **レコードがどのアドレスを持つべきか、それがいつ変わったかを知ること** は、既に
  regied のものである。回線のセットがどれも計算している関数であり、カーネルから、
  カーネル自身のイベントで起こされて計算している。

任せると、小さい方の半分を regied の外に置き、肝心な方の半分を二重にすることになる。
アドレスについて独自の考えを持ち、独自のポーリング間隔を持ち、トークンを載せた独自の
設定ファイルを持つ 2 つ目のプログラムであり、宣言を唯一の源に保つには regied がそれを
描画し、監視しなければならない。障害のときに読むものは減らずに増える。
[ADR 0001](0001-why-build-our-own.md) が気にしているのはそこである。

**事業者は 1 つで、事業者の抽象化は作らない。** この記録は Cloudflare のためにある。
2 つ目の事業者を受け入れるインターフェースは、2 つ目が必要になったときに設計する。
ADR 0002 が、必要になる前に kind を足さない理由として挙げたのと同じ理由である。

### 既にある決定から導かれること

以下は未決ではない。どれも既に立っている決定から導かれる。

- **アドレスは書かない。** レコードは追従する回線を参照し、持つアドレスのための
  フィールドは無い（ADR 0002）。
- **`DSLiteTunnel` に追従する IPv4 のレコードは作らない。** トンネルの IPv4 は AFTR が
  変換するので、そこからは何も公開できない。そういうレコードを求める宣言は、
  トンネルを名指す `PortForward` と同じく検証エラーである
  （[`kinds.md`](../spec/kinds.md#dslitetunnel)）。
- **API トークンは、それを持つファイルのパスで名指す。** 必要なターンで読み、使い、
  捨てる。`--dry-run` の出力にも、差分にも、ログにも、ターンの報告にも現れない
  （[ADR 0003](0003-secrets-out-of-configuration.md)）。ゾーンとレコードの名前は秘密
  ではなく、宣言に書いてよい。
- **レコードを更新するのは常駐プロセスである。** アドレスイベントがターンを起こし、
  そのターンが、回線の持つものを持っていないレコードを書く。別のポーリングも
  タイマーも無く、設定ファイルは何も読まない（ADR 0016）。**regied を止めると更新も
  止まる。** それが止めるレバーの意味である —— すべてをそのままにしておけ。
- **pppd のフックは DNS を更新しない。** フックはデーモン無しで動く経路であり、する
  ことは 1 つ、セットにアドレスを入れることだけである
  （[ADR 0015](0015-uplink-addresses-in-sets.md)）。リモートの API への書き込みには
  ネットワークとトークンとバックオフが要り、それはフックではなくターンの仕事である。
- **アドレスはリクエストに載せ、リクエストから推測させない。** 更新のリクエストは
  ホスト自身の通信が出ていく経路で出ていき、それはレコードが追従する回線とは限らない。
  事業者にリクエストの送信元アドレスを使わせると、間違ったアドレスがレコードに入る。
  アドレスを明示して送れば、リクエストがどの経路を通るかは関係なくなる。
- **持たせるアドレスが無いレコードは、そのままにする。** 回線がグローバルアドレスを
  持っていない間 —— セッションが再接続中、回線が落ちている —— ターンはレコードを
  消さず、空にも書き換えない。待っている状態であり、何を待っているかを言う。
  「未完了を半端に書いたもので表さない」という ADR 0016 の規則である。
- **無人のターンもレコードを更新してよい。** カーネルが言うことをレコードに書くのは、
  上がっているものを何も落とさない。ファイルを書くのと同じ段の書き込みである。
  対象ごとのバックオフの下に置くので、届かない、あるいは拒む事業者はそのレコードを
  *失敗中* にするだけで、他のものは何も止めない。
- **regied が触れるのは、書けと言われたレコードだけである**
  （[ADR 0009](0009-ownership-boundary.md)）。ゾーンのそれ以外は他の誰かのものである。

### 残した未決事項

方向を決めてから作るまでの間、以下が未決のまま立っていた。答えはその下に並べる。
問いは訊いたときのまま残す。並べてはじめて答えが読めるからである。

1. **IPv6 のレコードが何を持つか。** 回線自身のグローバルアドレスか、ルーターの後ろに
   いるホストの、委譲プレフィックス内のアドレスか。後者は、IPv6 には NAT が無いので、
   公開サービスの AAAA レコードがサーバー自身を名指す場合である。必要になりそうなのは
   後者で、「このホストの回線が持つアドレス」を「このホストが経路を与えるアドレス」に
   広げることになる。この記録はそこを決めていない。
2. **独自の kind にするか、回線のフィールドにするか。** ADR 0002 の最初の試金石では、
   レコードは名前で参照されないので、フィールドを指す。1 つ目の問いの答えが回線自身の
   アドレスでないなら、そこから離れる。
3. **所有がどこまで及ぶか。** 存在しないレコードを作るか、存在するものを更新するだけか。
   宣言から外れたレコードを消すか、残すか。消すなら、何が regied のものだと示すか。
   Cloudflare のレコードにはコメント欄があり、ADR 0009 の印を持たせられる。
4. **ずれをどう見るか。** ターンのたびに事業者からレコードを読めば、ループは
   レベルトリガーのまま保てるが、再同期ごとにレコード 1 件あたり 1 リクエストを、
   事業者のレート制限に対して払う。最後に書いた値を覚えておけば費用はかからないが、
   事業者側で行われた編集を見逃す。読み取りの失敗は *問い合わせられなかった* で
   あって、*無い* ではない（[ADR 0004](0004-apply-model.md) の三値のプローブ）。
5. **`--dry-run` が何を見せるか。** それを見せるために事業者に問い合わせるか。
6. **レコードのどの属性を宣言するか。** TTL や Cloudflare のプロキシの指定を宣言に
   書くか、レコードが既に持っているものに任せるか。

### 作るときに決めたこと

上の 6 つの問いは 2026-09-12 に答えを出し、さらに 2 つが付いてきた。答えがとった形が
`DNSRecordSet` kind である。

#### IPv4 のレコードだけ。IPv6 のレコードは作らない

**レコードは回線の IPv4 アドレスに追従する。IPv6 のアドレスに追従するものはここには
無い。**

1 つ目の問いは AAAA レコードの読み方を 2 つ挙げていたが、この 2 つは 1 つの機能の
変種ではない。回線自身のグローバルアドレスを持つ AAAA は、構成が欲しがるものでは
ほとんどない。IPv6 には NAT が無いので、公開サービスの名前はサーバーを名指さなければ
ならず、その手前にいるルーターを名指しても仕方がない。役に立つ AAAA は、委譲
プレフィックスの中の、このホストの後ろにいるホストのアドレスを持つ。それは
**このホストの回線が持つアドレス** ではなく **このホストが経路を持つアドレス** である。
所有についての別の主張であり、他のホストのアドレスの名前を誰が公開してよいのかに
先に答えなければ作れない。

そこでこの記録の範囲は IPv4 の側になる。要件が出てきたのもその側である。`PortForward`
が公開するものに届くのは回線の IPv4 アドレス経由だけであり、変わるのはそのアドレス
である。レコードの型は決め打ちにせず宣言させる。あとで範囲を広げる決定のために
フィールドを空けておくためで、`AAAA` と書いた宣言は理由を添えて拒む。黙って何もしない
ものとして受け付けはしない。

#### 独自の kind にする。1 つのゾーンのレコードをまとめて持つ

**`DNSRecordSet` がリソースである。レコード 1 本はリソースではない。**

ADR 0002 の最初の試金石は kind から離れる方を指す。レコードを名前で参照するものは無く、
それは所有者に畳む印である。ただしこの試金石は「回線に置け」とは言っていない。誠実に
適用すれば、言っているのは「何が所有者かを見つけろ」である。回線が所有者でないことは、
3 つのことが言っている。

レコードは単独で失敗する対象である。この記録は既に、届かない事業者は **そのレコード** を
対象ごとのバックオフの下で失敗中にするだけで他は何も止めない、と言っている。それは
ライフサイクルであり、ADR 0002 が畳むのはライフサイクルを持たないものである。

レコード自身の属性は回線と何の関係も無い。ゾーン、名前、型、プロキシの指定、TTL、
API トークンのファイルのパス。どれも事業者にある物を説明する。回線のリソースが説明する
のはこのホストの上のリンクであり、2 つを混ぜるとフィールド一覧の半分が別の場所の話に
なる。

多重度も畳むのとは逆を向いている。1 本の回線を通して、複数のゾーンにまたがる複数の
名前を公開する構成がある。畳めばそれは回線の spec の中のレコードの一覧、つまり
リソースの下のリソース一覧になる。`spec.resources` はその形を避けるためにある。

**レコードを所有するのはそのゾーンである。** credential がそうだからである。トークンは
ゾーンに対して発行され、ゾーンごとに 1 つ持つ理由は、その方が小さい credential だから
である。だからリソースは 1 つのゾーン分のレコードになる。ゾーン、事業者、そこへ書く
トークン、そして regied がそこに保つレコード。これは
[`IPAddressSet`](../spec/kinds.md#ipaddressset) と同じ形 —— 本体がリストである kind ——
であり、ADR 0002 の畳み込みをもう 1 段下で適用したものでもある。レコード 1 本は、何かに
名前で参照されることも、set のもの以上のライフサイクルを持つことも無い。だからリストの
項目であって、リソースではない。

このリソースはゾーンの **中の** レコードの集まりであって、ゾーンそのものではない。regied は
リストに名指されたレコードを書き、ゾーンのそれ以外については何も知らない。次の答えが
扱う所有の境界がそれである。

**`egressRef` は set ではなくレコードに置く。** どの回線に追従するかはその名前の性質で
ある。1 つのゾーンが、セッション経由で公開する名前と、そもそも公開しない名前の両方を
持つことは普通にある。ゾーンは credential のある場所であって、経路の決定がある場所では
ない。

#### 宣言は事業者を名指す。それでも事業者の抽象化は作らない

**どの set も `provider: cloudflare` と書く。実装は 1 つで、2 つ目を受け入れる
インターフェースは無い。**

この 2 つは対立しない。別々のことについての決定だからである。上の決定 —— 事業者は 1 つ、
抽象化は作らない —— はコードについてのもので、これは動かない。2 つ目の事業者が現れる前に
その継ぎ目を作るのは、ADR 0002 が拒む先回りである。

宣言に事業者を書かせるのはファイルについてのもので、いま払う費用は無い。どの事業者を
相手にしているか書いていない宣言の意味は「regied がたまたま実装している方」であり、それは
構成についての事実ではなくバイナリについての事実である。2 つ目の事業者を作る価値が出た
日には、既に書かれたどの宣言も、自分が何と話していたかを言っている。だから 2 つ目を足す
のは値を足すことであって、ファイルを書き換えることではない。抽象化を早く作ることの逆で
ある。コードは閉じたまま、**宣言の側** を開けておく。

事業者固有のフィールドを検査できるようにもなる。`proxied` は Cloudflare のもので、他には
無い。これは事業者ごとの入れ物に入れず、レコードの素のフィールドとして置く。事業者が 1 つ
なら入れ物は要らず、いま作るのはまた先回りになるからである。それを安全にしているのが
`provider` のフィールドである。そういう指定を持たない事業者を名指した宣言は、黙って何も
しないフィールドを載せたままにせず、名指しで拒める。

#### 更新し、無ければ作り、決して消さない

**宣言にあって事業者に無いレコードは作る。宣言から外れたレコードはそのままにする。**

作るのは、宣言を主張の全体にするためである。regied が保つ前に人が手でレコードを作って
おかなければならないホストは、設定が 2 か所にあるホストである。

消さないのは、regied が所有する他のすべてと違うところで、意図してそうしている。
ADR 0009 の境界は「自分が入れたものだけ取り除く」であり、このホストの上では regied が
書いたファイルの所有マーカーがそれを担保する。DNS ゾーンはこのホストではない。ホスト
より長生きし、人と他のツールが編集し、regied が作ったレコードは 1 年経てば人が手で
作ったものと見分けがつかない。レコードを regied のものと印を付けて ADR 0009 を満たす
こと —— Cloudflare のレコードにはその印を持たせられるコメント欄がある —— は、
レコードについての人の覚え書きであるフィールドに印を書き込み、そのうえで、宣言が
編集されたときやゾーンを使ったままホストを退役させたときに他人のレコードを消すことを
意味する。

**だから何も消さないし、印も要らない。** 所有の境界は、より強い主張で満たす。regied は
書けと言われたレコードだけを書き、何も取り除かない。宣言から外れたレコードは追従され
なくなる。宣言を編集した人が求めたのはそれである。名前を DNS から消すのは別の行為で、
ゾーンのある場所で行う。

**既にあるレコードの他のフィールドはそのままにする。** 更新に載せるのはアドレスと宣言
された属性だけで、それ以外は載せない。だからレコードに人や以前のツールが書いたコメントは
残る。今あるレコードの上にレコード全体を書けば、regied が持つ筋合いの無い覚え書きを
消してしまう。

#### 事業者を毎ターン読まず、書いた値を憶えておく

**レコードを書くのは、回線のアドレスがこのプロセスが最後にそこへ書いた値と違うときで
あり、それ以外のときには書かない。**

もう一方の案は、ターンのたびに事業者から各レコードを読むものだった。regied の他の部分と
同じくループをレベルトリガーに保てる。ホストを宣言と突き合わせ、見つけたものが決める。
費用は再同期ごとにレコード 1 件あたり 1 リクエストである。常駐プロセスの再同期は既定で
1 分ごとなので、レコード 8 本なら、数年に数回しか変わらないアドレスを観測するために
1 日およそ 1 万 1 千リクエストになる。

記憶はプロセスの中にあり、ディスクには無い。プロセスが起動したときは空で、空の記憶は
**分からない** であって **同じ** ではない —— ADR 0004 の三値のプローブである —— ので、
起動後の最初のターンがすべてのレコードを 1 度書く。肝心なところでレベルトリガーの性質を
取り戻すのはそれである。再起動はまさに、事業者が何を持っているか regied が請け合えなく
なる出来事であり、費用はレコード 1 件あたり 1 回の書き込みで済む。レコード 1 件あたり
毎分 1 回の読み取りではない。永続化はしない。永続化してできることは、この保証を
成り立たせている書き込みを省くことだけだからである。

事業者側でレコードを引き当てること —— 作るのか更新するのかを決め、更新先を特定する
識別子 —— は、プロセスごと・レコードごとに 1 度読み、他と一緒に憶える。これは引き当てで
あって、ポーリングではない。

**引き換えに失うものは、隠さず書いておく。** 事業者側で人が手で編集したレコードは、
アドレスが変わるか regied が再起動するまで直らない。ループが収束する先は宣言であり、
その 2 つの出来事の間、ループはそこを見ていない。それより速い訂正が要る構成は、ここを
考え直す理由を持っている。考え直すことになっても、それは費用の変更であって設計の変更では
ない。

書き込みが失敗したら記憶は元のままなので、次のターンがもう一度試す。この記録が既に
決めている対象ごとのバックオフである。そのレコードが **失敗中** になり、ターンの他の
部分は影響を受けない。

#### `--dry-run` はレコードを見せ、事業者には何も尋ねない

**dry run は、書くことになるレコードと書くアドレスをすべて名指し、リクエストは 1 本も
出さない。**

出さずに済むのは、書くかどうかを決めるのが記憶とカーネルであり、どちらも手元にあるから
である。出してはならないのは ADR 0006 が挙げる理由による。dry run は、確信が持てない
ときに操作する人が打つものである。答えを出すためにリモートの API に認証する dry run は、
誰かのレート制限と監査ログに副作用を持つ dry run である。トークンも読まない。それが、
印字しないという約束と、印字するものがそもそも無いこととの違いである（ADR 0003）。

帰結として、起動したばかりのプロセスでの dry run は、すべてのレコードを「書くことになる
もの」として見せる。そのプロセスはまだ 1 本も書いていないからである。ターンが実際に
することがそれなので、dry run が言うこともそれである。

#### 型とプロキシの指定と TTL は宣言する

**レコードの型、プロキシの指定、TTL は宣言に書き、レコードはそれらとともに書かれる。**

属性をレコードが既に持っているものに任せられるのは、regied がレコードを作らない間だけ
である。regied は作る。作られるレコードには任せる先の既存の値が無いので、作成に要る属性は
どこかになければならず、人がそれを置ける場所は宣言しかない。

プロキシの指定にはそれ以上の理由がある。公開する名前を事業者のプロキシに通す構成と通さない
構成は別の構成であり、どちらが効いているのかは事業者を見に行って分かるのではなく、
ファイルを読んで分かるべきである。TTL は `automatic` と書ける。事業者に決めさせるという
ことで、これは宣言された値であり、フィールドが無いこととは別である。

#### トークンは set に名指す。ゾーンごとのトークンを持てるように

**各 set が、そのレコードを書くための API トークンを持つファイルを名指す。**

1 つのゾーンだけに効くトークンはより小さい credential であり、構成がそちらへ移るときに
スキーマが邪魔をしてはならない。set は 1 つのゾーンのレコードなので、トークンはゾーンの
隣に置かれ、ゾーンと 1 対 1 で並ぶ。共有していたトークンをゾーンごとのトークンに分ける
のは、各 set のパスを 1 つずつ書き換えることであり、それ以外には何も要らない。まだ
トークンを分けていない構成は、すべての set から同じファイルを名指す。スキーマはそれを
妨げないし、別のものだと言い張りもしない。パスは宣言にあり、中身は決して宣言に無い
（ADR 0003）。ファイルは書き込むターンで読み、捨てる。

## 帰結

- `docs/scope.md` を改める。このホスト自身のアドレスのための動的 DNS が「クラウド
  事業者との連携はしない」への唯一の例外であり、ここを指す。
- スキーマは 12 個目の kind `DNSRecordSet` を得て、記載例はそれを 2 つ得る。ゾーンごとの
  トークンとプロキシの指定の両方が見えるようにするためである。
- regied は初めて、リモートのサービスへの外向きの接続を HTTPS で持つ。それを検証する
  ために、ホストには CA 証明書が要る。これは
  [ADR 0011](0011-target-platform.md) の前提条件に加わった。CA 証明書の無いホストは
  起動にも経路にも失敗しない。レコードが *失敗中* になり、理由を言う。
- 適用の順序は、プロセスの後ろにもう 1 つ相を得る。レコードはカーネルが持つアドレスから
  書かれ、その書き込みにホスト上の何も依存しないからである
  （[ADR 0004](0004-apply-model.md)）。失敗してもターンを止めない唯一の相でもある。
  届かない事業者はそのレコードを失敗中にするだけで、ターンの残りは最後まで進む。
- ターンが何をするかは、もはや宣言とホストだけの関数ではない。このプロセスが既に何を
  書いたかにも依る。再起動が各レコードを 1 度書くのも、どのレコードを書いたかを報告が
  言うのも、そのためである。
- 委譲ではなく regied が書くコードである。1 つの API のための HTTP クライアント。
  事業者を 1 つに絞ることが、それを釣り合った大きさに保つ。
- レコードがアドレスに追従するのは、常駐プロセスが動いている間だけである。デーモンを
  止めたホストでは、レコードは最後に持った値のままになる。それは止めるレバーが働いて
  いるのであって、壊れているのではない。
- 公開名を内側から引いたときの扱いは変わらない。回線のアドレスを受け取った内側の
  クライアントは hairpin され（ADR 0015）、内部アドレスで答えたいなら今までどおり
  `DNSForwarder.staticHosts` を使う。

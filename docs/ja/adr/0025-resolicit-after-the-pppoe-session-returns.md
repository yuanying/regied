# ADR 0025: PPPoE セッションが別のルーターから戻ったら委譲を要求し直す

- 状態: 決定（2026-10-23）
- pppd のフックが何をするかについて、[ADR 0015](0015-uplink-addresses-in-sets.md) と
  [ADR 0019](0019-uplink-address-in-dns-records.md) を補正する

## 背景

PPPoE セッションと DHCPv6 のプレフィックス委譲クライアントが同じ上流インターフェースの
上で走る回線では、事業者が回線を自分の別のルーターへ移すことがある。PPPoE セッションは
すぐに気づく。切れて、pppd が発呼し直し、新しいルーターに辿り着く。DHCPv6 の
クライアントはまったく気づかない。上流インターフェースは一度もキャリアを失っていない
ので、networkd は持っているリースを持ち続ける。新しいルーターが経路を持たない
プレフィックスのリースを、リース自身のタイマーが更新させるか期限切れにするまで ——
典型的な回線では数時間である。それまで委譲から導出したアドレスはすべて届かず、
[ADR 0021](0021-values-derived-from-the-delegated-prefix.md) が入っていれば、委譲から
導出した値はすべて忠実に間違う。

上流が変わったかもしれないとホストが受け取る合図は、セッションが切れることだけである。
それは証拠ではない。セッションは上流をそのままにする理由でも切れる。同じルーターでの
事業者の保守、LCP エコーのタイムアウト、手での発呼し直しである。

### networkd 257 が持っているもの

257 のソースで確かめた。

| コマンド | DHCPv6 のクライアントに何をするか |
|---|---|
| `networkctl renew` | **何もしない。** その裏にある D-Bus のメソッドは DHCPv4 のリースだけを更新する |
| `networkctl reconfigure` | DHCPv6 のクライアントを止め、それが持ち込んだ動的な設定 —— 委譲プレフィックスと、下流のリンク上でそこから導出したアドレス —— を捨て、`.network` を適用し直す。これでクライアントが起動し、新たに Solicit を送る。リンクは落とさないので、同じインターフェース上の PPPoE セッションはキャリアを保つ |
| `networkctl down` / `up` | リンクを落とし、PPPoE セッションも一緒に落とす |

Debian 13 を走らせる実験機で測った。計画した操作のうち RELEASE を送るのは、再起動と
上流インターフェースの reconfigure であり、`[DHCPv6] SendRelease=no` を設定すれば
どちらも送らない。同じ測定で、**reconfigure は `SendRelease=no` でも、下流のリンクの
委譲アドレスを一瞬取り下げる** ことも分かった。委譲を保つのは事業者側の束縛であって、
クライアントが再起動する間のこのホスト上のアドレスではない。

### reconfigure の費用と、それを払うもの

取り下げられるアドレスは IPv6 のものだけではない。LAN の IPv4 を DS-Lite トンネルで
運ぶルーターは、そのトンネルをそれらのアドレスの 1 つから送り
（[ADR 0022](0022-dslite-local-address-follows-the-delegation.md)）、トンネルは PPPoE
セッションにまったく依らない。PPPoE セッションがひとりでに切れるのは PPPoE の回線だけの
停止である。発呼し直すたびに reconfigure すれば、それが LAN の IPv6 と、トンネルが運ぶ
IPv4 の停止にまで広がる。**費用は発呼し直すこと自体の停止の内側には収まらず、発呼し直す
たびに払ってはならない。**

### フックに見えるもの

pppd の PPPoE プラグイン（ppp 2.5）は、ディスカバリで知ったことを、pppd 自身の変数と
並べて、自分が走らせるスクリプトの環境に入れる。

| 変数 | 持っているもの |
|---|---|
| `MACREMOTE` | セッションを開いた相手のアクセスコンセントレータ（AC）の MAC アドレス |
| `ACNAME` | AC が名前を送ってきたときは、その名前 |
| `REMOTENUMBER` | 同じ MAC アドレスを、pppd の汎用の「リモート番号」として |
| `IPREMOTE`、`IPLOCAL` | 両端の IPCP のアドレス |

事業者が回線を別のルーターへ移すと、ディスカバリに答える AC はその別のルーターであり、
MAC アドレスが違う。移動が起きたとき、それをただの発呼し直しと見分けたのはこの観察で
あった。

## 決定

**PPPoE セッションが上がったとき、regied が描画する ip-up のフックは、AC の MAC アドレスを
そのセッションが前回上がったときのものと比べ、違うときに限って networkd に上流
インターフェースの reconfigure を頼む。** そのときには新しい上流が応答している ——
セッションがそこを通ってちょうど上がったところである —— ので、Solicit は答えられる
ルーターに届く。

| 場合 | フックがすること |
|---|---|
| MAC が記録したものと違う | 新しい MAC を記録し、セッションが走っているインターフェースで `networkctl reconfigure` を走らせる |
| MAC が記録したものと同じ | 既にしていること以外は何もしない |
| 何も記録されていない —— 起動してから最初の ip-up | MAC を記録し、他には何もしない。起動の後は DHCPv6 のクライアントが Solicit を送ったばかりなので、捨てる古いリースが無い |
| `MACREMOTE` が無いか空 | 何もしない。reconfigure は LAN に停止を強いる。移動を見逃したときの費用はこの記録の前と同じであり、古いプレフィックスを見張る監視はそれを引き続き見る |

- **名前ではなく MAC で。** `ACNAME` は事業者が設定したものにすぎず、事業者は自分の複数の
  ルーターに同じ名前を付けることも、何も送らないこともある。MAC はセッションが終端する
  機器を識別する。事業者がその場で機器を入れ替えれば MAC が変わり、不要な reconfigure が
  1 回起きるが、それは間違えても安く済む向きである。`IPREMOTE` も使わない。それが識別
  するのは IPCP のリンクの向こう端であってルーターではなく、同じルーターでもセッション
  ごとに変わりうる。
- **記録は `/run` の下に置く。** regied 自身のディレクトリに、セッションごとに 1 つ、
  セッションの名前を付けたファイルを丸ごと書く。`/run` は起動時に空になり、それはちょうど
  比較をやり直さなければならないときである。DHCPv6 のクライアントはホストと一緒に新しく
  始まる。pppd だけが再起動された場合や常駐プロセスが止められた場合には残り、それらは
  networkd のリースがセッションより長生きする場合である。これは設定ではなく、受理した宣言
  （[ADR 0016](0016-converging-on-the-accepted-declaration.md)）の一部でもない。フックの
  記憶である。
- **セッションとクライアントがインターフェースを共有する場合に限る。**
  `PPPoESession.interfaceRef` と、そのインターフェースの `dhcpv6.prefixDelegation` を
  合わせれば、両者が上流を共有していることが分かり、フィールドは足さない。共有して
  いなければ、フックは何も記録せず、余分なことを何もしない。
- **ループではなくフックに置く。** セッションが別のルーターから戻ることは出来事であり、
  それにどう応じるかは宣言と何かを比べることに依らない。レベルトリガーのターンには
  比べるものが無い。フックはデーモンを止めていても動く経路でもあり、それはプレフィックス
  の変化が最も必要とする性質である。起きたときに誰も見ていないからである。
- **ip-down ではなく ip-up で。** ip-down の時点では回線はもう無く、次のルーターも
  分からない。
- **その失敗をセッションは無視する。** 走らせられない reconfigure がセッションの立ち上がり
  を止めてはならない。次のターンは、networkd が持っているプレフィックスを、それが何であれ
  見る。
- **`SendRelease=no` を併せて設定しておくことを前提とする。** RELEASE を送る reconfigure は、
  ちょうど応答し始めたルーターでの束縛を手放す。送らなければ、束縛を保っていたルーターは
  同じプレフィックスを返す。

[ADR 0015](0015-uplink-addresses-in-sets.md) と [ADR 0019](0019-uplink-address-in-dns-records.md)
は、フックがすることは 1 つ、セットにアドレスを入れることだけであり、ネットワークや
トークンやバックオフが要るものはターンの仕事である、と言った。この記録は後半を保ち、
前半を広げる。**フックは、ネットワークも credential もバックオフも要らないローカルの
コマンドを走らせてよく、`/run` の下に自分の小さな記録を持ってよい。** バス越しの
networkd への要求はこれに当たり、DNS への書き込みは引き続き当たらない。

### 作る前に確かめること

テストベッドがプレフィックスを委譲できるようになったら
（[ADR 0021](0021-values-derived-from-the-delegated-prefix.md) の単位 7）、そこで確かめる。
プラットフォームが載せている pppd で、プラグインが ip-up の環境に `MACREMOTE` を入れる
こと。同じインターフェース上の PPPoE セッションが reconfigure を生き延びること。同じ AC
への発呼し直しが、導出したアドレスに手を触れないこと。そして、束縛を保っていない DHCPv6
サーバーを持つ別の AC への発呼し直しが新しいプレフィックスをもたらし、次のターンがそれに
追従すること。

## 採らなかった選択肢

**ip-up のたびに reconfigure する。** この記録の最初の草稿である。却下。PPPoE の発呼し直し
のたびに、セッションに依らない LAN の IPv6 と DS-Lite トンネルの停止を引き起こし、しかも
ほとんどの発呼し直しは上流を変えない。

**AC ではなく委譲プレフィックスを比べる。** 新しいルーターが委譲するはずのプレフィックスを、
フックは Solicit を送らずに知ることができない。そして Solicit を送るかどうかこそが、
決めようとしていることである。

**regied の外でやる。** 構成が `/etc/ppp/ip-up.d/` に置くスクリプトとして。これは動くが、
どのインターフェースが委譲のクライアントを走らせているかを知っていなければならない ——
それは宣言が既に言っている。regied が描画すれば、その事実は 1 か所に保たれる。置き場所は、
regied が既に自分の名前でフックを書いているディレクトリである。

**常駐プロセスでやる。** PPPoE のリンクのアドレスイベントで。却下。意図してレベル
トリガーにしているループの中のエッジトリガーの仕事であり、上がっているアドレスを無人の
ターンから取り下げ、デーモンを止めていると起きない。

**`networkctl renew`。** 257 では DHCPv6 に何もしない。

**リースを待つ。** 現状である。リースの有効期間のうちには正しくなるが、それこそが
この記録が扱う停止である。

## 帰結

- **事業者が回線を別のルーターへ移しても、セッションが戻ってから数秒で追従する。**
  リースの有効期間のうちに、ではない。
- **同じルーターへの発呼し直しは、発呼し直すこと以上の費用を払わない。** LAN の IPv6 と
  DS-Lite トンネルには手を触れない。
- **移動の代価は、導出したアドレスが数秒失われることである。** トンネルのローカル
  アドレスもその中に入る。
- **pppd のフックが走らせるコマンドの種類が 1 つ増え、小さなファイルを 1 つ持つ。** フック
  が何をしてよいかの規則は、暗黙にせず書き下される。

## 実装の単位

[ADR 0021](0021-values-derived-from-the-delegated-prefix.md) の単位 8。単位 7 がテスト
ベッドに委譲する DHCPv6 のサーバーを与え、上の確認が通ったあとに作る。単位 2 から 6 とは
独立している。これはプレフィックスを早く届かせるもので、あちらはホストをそれに追従
させるものである。

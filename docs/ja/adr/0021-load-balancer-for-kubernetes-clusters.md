# ADR 0021: このホストの背後にある Kubernetes クラスターのロードバランサーになる

- 状態: 提案（2026-10-18）
- [`docs/scope.md`](../scope.md) を広げる。[ADR 0013](0013-nftables-ruleset-shape.md) と
  [ADR 0020](0020-port-forward-reply-on-arrival-uplink.md) を補正する

> **ここに書いたものは何も実装していない。kind 名とフィールド名は仮である。** この記録は
> 方向を決め、それが生む問いへの答えを提案する。フィールド単位の形は、方向が受け入れられて
> から [`docs/spec/`](../spec/) に入れる。その前には入れない。

## 背景

### 要件

ルーターの LAN 側に、Kubernetes クラスターが 1 つ以上ある。各クラスターは、
`type: LoadBalancer` の `Service` に、クライアントが届くアドレスを持たせたい。LAN から、
IPv6 のインターネットから、そしてルーターの IPv4 の回線を通して届くアドレスである。
また各クラスターは、自分の API サーバーに安定したアドレス（*control-plane のエンドポイント*）
を持たせたい。すべてのノードとクライアントがそれを使う。

想定する構成は次の性質を持つ。

- **ルーターが持つ公開 IPv4 アドレスは 1 つで、動的である。** PPPoE のセッションなどの回線が
  持ち、再接続で変わり、それを通してクラスターへ経路を渡すことはできない。IPv4 がクラスターに
  届くのは、ルーターでの宛先変換によってだけであり、ポート単位になる。
- **IPv6 は委譲されたプレフィックスから来る。** ルーターは DHCPv6 のプレフィックス委譲で
  プレフィックスを受け取り、その中からサブネットを切り出せる。IPv6 の NAT はしない
  （[`docs/scope.md`](../scope.md)）ので、公開する IPv6 アドレスは、そのプレフィックスの中の
  経路で届くアドレスでなければならない。
- **クラスターは 1 つではない。** 例えば本番用と開発用が、1 台のルーターの背後に並ぶ。
  どちらも相手のアドレスやポートを取ってはならず、一方のクラスターのマニフェストの誤りが、
  他方の名で何かを公開できてはならない。
- **control-plane のエンドポイントは、クラスターに依存してはならない。** これを持たせる
  普通のやり方は、クラスター内のロードバランサー —— ARP・NDP・BGP でアドレスを広告する
  controller —— である。冷えた状態から起こすとき、これは循環する。controller は何を広告するかを
  知るために API サーバーを要し、API サーバーには controller が広告するアドレスで届く。
  丸ごと止めたクラスターが、人の手を借りずには戻れないことがある。

### クラスター内のロードバランサーに残る仕事

クラスター内の実装は、`Service` に LAN のアドレスを与えて広告することはできる。この種の
構成では、そのアドレスを外から届くようにはできない。

- 公開 IPv4 アドレスはルーターのものである。公開するポートごとにルーターの `PortForward` が
  要り、それは手で書き、手でクラスターと揃え、ポートの範囲を持つクラスターごとにまた書く。
- 公開する IPv6 アドレスには、ルーターのファイアウォールの穴が要り、同じく手で書く。
- control-plane のエンドポイントには、上の循環が残る。

回線も、委譲されたプレフィックスも、ファイアウォールも既に持っているのはルーターである。
ルーターに欠けているのは、クラスターが何を求めているかという知識である。

### 既存の記録が既に言っていること

**このホストが何をすべきかを知るために他のシステムを読むことは、範囲の内側にある。**
[ADR 0007](0007-resident-process.md) は、ADR 0009 の線はホストについての線であって、出所に
ついての線ではないと述べる。「他のシステムの API を読んで、このホストが何をすべきかを
知ることは線の手前にあり、他のホストに何をすべきかを告げることが線の向こうにある。」
同じ記録は、*在る*・*無い*・*訊けなかった* を区別し、3 つめを 2 つめとして通すことを拒む。

**まさにこの場合が、開けたまま残されてきた。** ADR 0007 の結果の節は、「Kubernetes
クラスターが求めた、ロードバランスされたアドレスの背後にある健全なバックエンド」を、回線の
セットと同じ場所に置かれ、常駐プロセスが書き、レンダリングされたテキストに触れない実行時の
状態として名指している。[ADR 0016](0016-converging-on-the-accepted-declaration.md) は最後の
結果でそれを繰り返す。[ADR 0017](0017-submission-through-the-resident-process.md) が常駐
プロセスを唯一の書き手にしたのは、この状態がテーブルの置き換えをくぐれるようにするためでも
ある。書き手が 1 つなら、テーブルを置き換える周回は、デーモンが知るすべての要素を播く周回で
ある。

**実行時の状態は、テキストではなくセットと map に入る。**
[ADR 0015](0015-uplink-addresses-in-sets.md) は回線のアドレスをルールセットから外し、
レンダリングされたテキストを宣言だけの関数に保った。ADR 0007・0016・0017 が繰り返したその
警告は、ここに一字一句そのまま当てはまる。回線のセットが安全なのはカーネルが答えを持って
いるからであり、出所がカーネルでない要素にはその回復が無い。それに答えるべきなのがこの記録で
ある。

**他のシステムの API に書き込むことには前例がある。**
[ADR 0019](0019-uplink-address-in-dns-records.md) は、regied が事業者の DNS レコードを書くことを
認めた。事業者に伝えるのは *この* ホストのことであり、事業者から設定を受け取らない、という
理由である。

**変換した接続の戻りは、既に来た道を戻る。**
[ADR 0020](0020-port-forward-reply-on-arrival-uplink.md) は、到着した回線を接続に保存し、戻りで
復元する。回線から内側のアドレスへの宛先変換は、政策が何と言おうと、その回線から答える。

### 障害になるもの

[`docs/scope.md`](../scope.md) は、regied は 1 台のノードを見るもので「フェイルオーバーは
持たない」と言い、動的ルーティングは FRR・BIRD・GoBGP のものだと言う。バックエンドの死活を
見て、落ちたものから通信を外すのはフェイルオーバーに読め、実行時に変わる経路を入れるのは
動的ルーティングに読める。[ADR 0008](0008-delegate-to-existing-implementations.md) は、既存の
実装がその層を既に持っていないかを問う。どちらにも以下で答える。

## 決定

### regied は、知らされたクラスターのロードバランサーになる

**regied の常駐プロセスは、宣言された各クラスターの API を読み取り専用で watch し、
そのクラスターが求める `LoadBalancer` のサービスを、宣言がそのクラスターに定める枠の中で
届くようにする。** アドレスを払い出し、そのアドレスを健全なノードへ経路で向け、回線のポートを
そこへ変換し、ファイアウォールを開け、クラスターの control-plane のエンドポイントを持つ。

**どこまで任せるかは宣言が言い、その中で何をするかはクラスターが言う。** 人はクラスターごとに
一度、枠を書く。どのアドレス、どの回線のポート、どのノード、どの control-plane の
エンドポイントか。枠の中のすべては、クラスターの API が言うことから実行時に決まり、ADR 0015 の
意味での実行時の状態である。レンダリングされたテキストは枠に依存し、どの `Service` にも依存
しない。

**push ではなく pull。** クラスターが regied に届きに来ることはない。regied にエンドポイントは
足さず、書き込み API は存在せず（[`docs/scope.md`](../scope.md)）、クラスターの中の何も
ルーターとの話し方を知る必要が無い。regied に届くのは、運用者が与えた資格情報で regied が
読むものである。

### なぜ範囲の内側なのか、線はどこに残るのか

- **ノードは今も 1 台である。** regied が管理するのは、このホストの経路・変換・ファイア
  ウォールである。このホストが何をすべきかを知るためにクラスターの API を読むことは、ADR 0007
  が既に線の手前に置いた。どのホストにも何をすべきかを告げず、どこへも設定を配らず、
  クラスターに参加しない。
- **バックエンドの死活を見ることは、regied のフェイルオーバーではない。** ルーターは今も単一
  障害点である。ここでは何も regied を冗長にせず、リーダーを選ばず、状態を移さない。動くのは
  パケットがどのバックエンドへ行くかであり、それはどのロードバランサーもすることで、宛先変換が
  既にしていることである。
- **実行時の経路はルーティングプロトコルではない。** regied はどのピアともプロトコルを話さず、
  ピアから経路を学ばない。経路は 2 つの出所 —— クラスターの API と自分の死活監視 —— から計算し、
  自分が入れる他のすべての経路と同じように所有する（[ADR 0009](0009-ownership-boundary.md)）。
  BGP・OSPF・RIP は FRR・BIRD・GoBGP に残る。
- **クラスターへの書き込みは 1 つ、1 つだけである** —— regied が受け持つ各サービスのアドレス。
  線に最も近い部分なので、下で決める。

### なぜ既存の実装ではないのか

ADR 0008 の問いは、その層を既に誰かが持っているかである。ここでの層は 3 つに分かれる。

| 部分 | 他が持っているか |
|---|---|
| ルーター上の宛先変換・経路・ファイアウォール | いいえ。ADR 0008 は NAT とファイアウォールを regied の持ち分に挙げており、経路はこのホストのものである |
| バックエンドの死活を見て、その中から選ぶこと | はい。keepalived と IPVS。ただし keepalived はクラスターを watch せず、その設定を実行時の状態から生成することになる |
| クラスターの API を watch して、サービスとノードを知ること | クラスターの中でだけ。MetalLB・kube-vip・Cilium。これらは LAN で広告するもので、ルーターの回線にもファイアウォールにも届かない |

**keepalived と IPVS** が本気の対抗案だった。クラスターが求めるサービスから keepalived の設定を
レンダリングすると、レンダリングした生成物が実行時の状態の関数になる。それは ADR 0015 が防ぐ
ためにあるものである。あるいは周回の横でそれを生成する 2 つめの書き手が要り、それは ADR 0017
が防ぐためにあるものである。IPVS は nftables の隣のもう 1 つのパケットの通り道にもなり、障害時に
読むべき状態がもう 1 つ増える。IPVS の direct routing は、バックエンドの集合が変わっても接続を
そのバックエンドに留める。素の経路はそうしない（結果の節を参照）。見直す価値のある性質は
それ 1 つであり、始めるのに要るものではない。

**クラスター内の実装** は別の問いに答えている。アドレスが LAN のどこにいるかを決めるのである。
ルーターには、公開するものすべてについて、クラスターごとに、手で書いた `PortForward` と
ファイアウォールの穴がなお要り、control-plane のエンドポイントには循環が残る。

### リソース: クラスターごとに 1 つの kind

**新しい kind を 1 つ、仮に `KubernetesLoadBalancer` とし、クラスターごとに 1 リソースとする。**
クラスターへの接続、その枠、その control-plane のエンドポイントを持つ。

ADR 0002 の基準はこちらを指す。このリソースは独自のライフサイクルを持つ —— 接続し、切れ、
繋ぎ直す watch と、走り続ける死活監視である。そしてクラスターごとに 1 つずつ、単独で意味の
ある項目として繰り返される。各部分をそれぞれ kind にすることも考え、畳んだ。名前で参照する
ものが無いからである。クラスターへの接続を使う枠はちょうど 1 つで、control-plane の
エンドポイントが属するクラスターはちょうど 1 つである。

| フィールド（仮） | 持つもの |
|---|---|
| `kubeconfigFile` | クラスターの API のアドレスと資格情報を持つ kubeconfig のパス（[ADR 0003](0003-secrets-out-of-configuration.md)） |
| `addresses.ipv4` | IPv4 のサービスアドレスを払い出すプレフィックス |
| `addresses.ipv6` | IPv6 のサービスアドレスを払い出すプレフィックス。リテラルか、`interfaceRef` と `subnetID` を持つ `fromDelegatedPrefix`。形は `Interface.addresses[]` が既に使うもの |
| `nodes.within[]` | next hop に使ってよいノードのアドレスが入るべきプレフィックス。両方のファミリーを受け持つなら両方 |
| `publish[]` | 回線ごとに、`egressRef` と、このクラスターが公開に使ってよい回線のポート |
| `controlPlane.address` | control-plane のエンドポイント。`addresses.ipv4` の中 |
| `controlPlane.port` | 既定 6443 |
| `controlPlane.endpoints[]` | control-plane ノードのアドレス。手で書く |
| `controlPlane.healthCheck.path` | 既定 `/readyz` |

2 つめのクラスターは 2 つめのリソースである。kind の中の何も、他のリソースを参照しない。

### アドレス

**IPv4 のサービスアドレスは、どの LAN セグメントの外にもあるプライベートな範囲から取る。**
セグメントの上に置くと、アドレスはそこのすべてのクライアントにとって on-link になる。
クライアントは ARP でそれを引き、ルーターは持っていないアドレスに答えなければならない ——
リンクにアドレスを足すか proxy ARP で、どちらにしてもリンクの持ち主が宣言していない
アドレスをリンクに載せることになる。さらに、同じセグメントのクライアントに答えるノードは
クライアントへ直接答えるので、LAN のすべてのクライアントに送信元の変換が要り、サービスは
クライアントのアドレスを失う。すべてのセグメントの外なら、クライアントは既定のゲートウェイ
—— ルーター —— へ送り、あとは経路が運ぶ。

**IPv6 のサービスアドレスは、委譲されたプレフィックスの、どのリンクも載せていない
サブネットから取る。** ノードへ経路で向け、セグメントには広告しない。`fromDelegatedPrefix`
で書けば、委譲が変わっても編集なしで追従する。払い出した各アドレスのホスト部は保ち、
プレフィックスを置き換える。

**払い出しは regied が行い、それはクラスターに記録される。** 特定のアドレスを求めない
`Service` は、範囲の中で空いている最も小さいアドレスを得る。アドレスはサービスの status
（後述）に書かれ、regied は再起動後にそこから読み戻すので、払い出しはサービスが存在する限り
安定する。control-plane のエンドポイントは予約し、払い出さない。

**どのサービスを受け持つか** は `spec.loadBalancerClass` で決まる。regied は、自分が watch
するクラスターの中で、class が自分のものであるサービスを受け持つ。class の無いサービスや
別の class のサービスは、そのクラスターにある他の何かに任せる。これにより、クラスター内の
実装が、サービスが 1 つずつ移るあいだ自分のサービスを持ち続けられる。

### 通信がサービスに届く道

**サービスのアドレスは健全なノードへ経路で向け、その先はノードの kube-proxy が受け持つ。**
kube-proxy は、サービスの `status.loadBalancer.ingress` にあるすべてのアドレスについて規則を
入れるので、そのアドレス宛てにノードへ届いたパケットは、どのロードバランサーから来た場合とも
同じように扱われる。

| `externalTrafficPolicy` | next hop | 死活監視 |
|---|---|---|
| `Cluster` | 健全なすべてのノード | ノードの kube-proxy の health エンドポイント（`:10256/healthz`） |
| `Local` | このサービスの ready なエンドポイントを持つノードだけ | ノードの、そのサービスの `healthCheckNodePort` の `/healthz`（ローカルにエンドポイントがあれば 200、無ければ 503） |

経路はサービスのアドレスごとに、その next hop へのマルチパスの経路として入れる。**範囲全体には
unreachable の経路を置く。** これは宣言から導き、設定としてレンダリングする。こうすると、
誰も持たないアドレスにはルーターが unreachable と答える。これが無いと、払い出していない
アドレス宛てのパケットは既定経路に従い、規則を持たないノードに届き、ノードの既定経路で
送り返され、ホップ数が尽きるまで行き来する。

ノードはクラスターの `Node` オブジェクトから取る。ノードが候補になるのは、`Ready` で、その
ファミリーの `InternalIP` が `nodes.within` の中にあり、外部ロードバランサーから外すための
既知のラベルを持たないときである。`nodes.within` は安全弁である。乗っ取られたり設定を誤ったり
したクラスターが、その外のアドレスへルーターに通信を送らせることはできない。IPv6 のアドレスには
IPv6 の `InternalIP` を持つノードが要る。経路は IPv4 の next hop を通れない。

`Local` のサービスの背後にあるエンドポイントは、クラスターの `EndpointSlice` からではなく
死活監視から知る。regied がそこから計算するはずの問いには kube-proxy が既に答えており、
ノードから答えを得れば、regied が読むリソースの種類は 2 つで済む。

**マルチパスの経路はトランスポートのポートでハッシュする。** 1 つのクライアントの接続が
ノードに散らばるようにするためである。`KubernetesLoadBalancer` が宣言されているとき、regied は
両方のファミリーについてカーネルのマルチパスのハッシュ方式を設定する。`spec.global` の
スイッチを既に書いているのと同じである。

### 回線を通した公開

**サービスは、そのサービスに付けた annotation で公開する。** 仮に `net.unstable.cloud/publish`
とし、回線 —— そのクラスターの `publish[]` にある `egressRef` —— を名指す。これが無ければ何も
公開しない。アドレスを持ち annotation を持たないサービスは、内側からだけ届く。

**サービスの `port` が回線のポートである。** 公開した TCP の 443 は回線の 443 であり、
サービスのアドレスの 443 へ変換する。サービス自身のポートの隣に、回線のポートの対応表は
持たない。2 つめの数字は揃えるべきものが 1 つ増えるだけで、別の公開ポートが欲しいサービスは、
別のポートを持つことでそう言える。

| ファミリー | 公開がすること |
|---|---|
| IPv4 | 回線のアドレスとポートから、サービスのアドレスの同じポートへの宛先変換。そこから先は上の経路。戻りは ADR 0020 の接続マークで回線に戻り、回線のアドレスへ届く LAN のクライアントは、`PortForward` と同じく ADR 0013 の送信元変換で hairpin する |
| IPv6 | サービスのアドレスとポートについての、ファイアウォールの穴。範囲が委譲されてくるインターフェースに届いた通信について開ける |

**ファイアウォールは公開したものだけを開ける。** 枠はクラスターがどこまで行けるかを言い、
穴そのものは実行時に、公開したサービスのアドレスとポートについてだけ書く要素である。内側の
ゾーンからサービスのアドレスへの通信は、宣言が既に持つ政策が決める。

### control-plane のエンドポイント

**control-plane のエンドポイントは同じ IPv4 の範囲から取り、それについてはクラスターから何も
学ばない。** そのバックエンドをクラスターの API から学ぶことは、この記録が取り除くためにある
循環そのものである。エンドポイントは宣言し、それぞれを、宣言したポートの health のパスへの
HTTPS のリクエストで確かめる。

**経路ではなく変換で届ける。** エンドポイントへの接続は健全な control-plane ノードへ宛先を
変換し、送信元をルーターに変換する。クライアントとノードが同じセグメントにいても、戻りが
ルーターを通るようにするためである。kube-proxy は通さない。冷えたクラスターでは、kube-proxy は
API サーバー無しに規則を作れないからである。

- **死活監視は証明書を検証しない。** 決めるのはそのノードへ接続を送るかどうかだけで、接続
  そのものはクライアントと API サーバーの間の TLS である。検証するには、クラスターが存在する
  前にクラスターの CA が要る。
- **どのエンドポイントも通らないときは、すべてを使う。** まだ ready でない API サーバーも
  答えはし、そのクライアントはどれも再試行する。クラスターが起きる途中ですべての接続を拒むと、
  クラスターを ready にする部品そのものを止めてしまう。
- **変換は、ホスト自身が送る通信にもかける。** control-plane のエンドポイントを名指す
  kubeconfig —— regied 自身のものも含め、普通はそうである —— は、ルーターからそこへ届かなければ
  ならない。

クラスターから何も要らないので、入れる順序は「ルーターに枠を宣言し、そのエンドポイントに
向けてクラスターを install する」になる。regied が読む kubeconfig はその後に置けばよい。置く
までのあいだ、control-plane のエンドポイントは動き、何も公開されない。

### 重なりは静的に拒み、衝突は実行時に拒む

**枠は重なってはならず、何かを適用する前に検証がそう言う。** 検査は、重なる `PortForward` を
拒むために提案中の検証（未マージ、regied#43）を延長する。

- 2 つのリソースの IPv4 と IPv6 の範囲どうし。またそのどちらかと、いずれかの `Interface` の
  アドレスや静的経路。
- `nodes.within` と範囲。自分が受け持つ範囲の中の next hop はループになる。
- control-plane のアドレスが自分の IPv4 の範囲の外にあること。
- 同じ回線についての 2 つのリソースの回線のポートどうし。またそのどちらかと、その回線と
  プロトコルの `PortForward`。重なりの定義はその検証と同じ。

**枠の中では、先にあったサービスが勝つ。** 同じ回線のポートを求める 2 つのサービスや、
クラスターの枠の外のアドレスやポートを求めるサービスは、実行時に拒む。先に作られたサービスが
持っているものを保ち、後のものはそのポートやアドレスについて受け持たれず、理由を報告する ——
周回の報告に（[ADR 0016](0016-converging-on-the-accepted-declaration.md)）、そしてサービス自身に、
`status.loadBalancer.ingress[].ports[]` がそのために持つポートごとのエラーとして。

### ルールセットとループの中での置き場

**ルールセットは宣言の関数のままである。** 新しいルールは、要素を実行時に書くセットと map を
名指す。サービスのアドレスも、ポートも、ノードのアドレスもテキストには現れない。ADR 0013 の
テーブルは次を得る。

- `prerouting_nat` に、公開の変換。回線のアドレスのセット（[ADR 0015](0015-uplink-addresses-in-sets.md)）
  に一致させ、プロトコルとポートを map で引いてサービスのアドレスにする。そして control-plane
  の変換。
- output フックの、優先度 `dstnat` の基底チェーン。ホストが送る通信のための control-plane の
  変換を持つ。
- `postrouting_nat` に、control-plane ノードへ変換した接続のための送信元変換。
- `forward` の、ポートフォワードの穴の後に、公開の穴。ファミリーごとに、アドレス・
  プロトコル・ポートのセットに一致させる。

**control-plane の変換は、固定数のスロットから選ぶ。** ルールは接続を、宣言したエンドポイントの
数だけのスロットへハッシュし、各スロットがどのエンドポイントへ送るかを map が持つ。健全な
エンドポイントは自分のスロットに入り、健全でないエンドポイントのスロットには健全なものが
入る。数は宣言にあるのでテキストに書けて、どのエンドポイントが各スロットを埋めるかは実行時の
状態である。死活で割る数が変わるルールは、実行時の状態をテキストに戻してしまう。

**ADR 0020 のマークは、`KubernetesLoadBalancer` が公開に使うすべての回線について導出する。**
`PortForward` が公開に使う回線と同じである。公開したサービスは、その回線からの宛先変換だから
である。

**周回がそのすべてを書く。** watch のイベントと死活監視の結果の変化は、カーネルのアドレスの
イベントと同じく周回を起こす。周回は、違っている map とセットの要素・経路・サービスの status
を、回線のセットを播くのと同じ場所で書く。そしてテーブルを置き換える周回が、持っている要素を
すべて入れ直す。これが、この状態について ADR 0007・0016・0017 の警告への答えになる。セットを
空にする周回が、そこに何を戻すかを知っている周回なのである。無人の周回もこれをすべて行って
よい。健全なものへ通信を移すことは、上がっていたものを何も落とさない。回線のセットを播くのと
同じく、宣言の意味を新しい事実に当てはめることである。

**クラスターに訊けなかったものは、最後の答えを保つ。** 切れた watch は *訊けなかった* であって
*無い* ではない。要素は残り、周回はクラスターの API を待っていると報告し、死活監視は走り
続けるので、落ちたノードはなお外れる。API が消えたと言うサービスは *無い* であり、その要素・
経路・穴は消える。

**宣言からリソースを外すと、それが受け持っていたものを外す。** それを行う周回は、届く限り、
そのクラスターのサービスに自分が書いた status を消す。regied を止めると、すべてはそのまま残る。
それが停止レバーの意味である。

### 経路の持ち主

**実行時の経路は、regied 自身のルーティングのプロトコル番号を負う。** これが経路についての
ADR 0009 の所有の印である。regied はそれを負う経路だけを消し、負わない経路は決して消さない。

**systemd-networkd は、そう言われない限り、リンクを設定するときに外来の経路を消す。**
`ManageForeignRoutes=` の既定は yes であり、無条件に残すプロトコルは `kernel` だけである。
regied が実行時に入れた経路は、適用が起こす次の reload で消され、周回が戻すことになる ——
networkd が変わるたびに隙間ができる。そこで regied は、`KubernetesLoadBalancer` を宣言した
ホストで、`ManageForeignRoutes=` を切る `networkd.conf` の drop-in をレンダリングする。共有
ディレクトリに置く他のファイルと同じく、自分の名前の接頭辞と所有の印を付ける。

### 承認を求める点

複数の答えが成り立った点で、この記録が選んだものである。どれも提案であり、記録が受け入れ
られる前に変えられる。

#### 1. サービスの status は regied が書く

**提案: regied は、受け持つサービスの `status.loadBalancer` を書き、クラスターの他の何も
書かない。**

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **regied が書く** | 払い出し、衝突を判定する者が、それを報告する。status にあるアドレスは regied が受け持つアドレスであり、拒んだポートはサービスの上でそう言う。status は払い出しの記録にもなり、regied がファイルを持たなくても再起動をまたいで安定する | 他のシステムの API への書き込みであり、ADR 0019 が認めた種類の例外が要る |
| クラスターの中の小さな controller が書く | regied は読み取り専用のまま | 枠を 2 か所 —— 宣言と controller の設定 —— に書き、両者が払い出しと衝突について一致しなければならない。食い違えば、status はルーターが受け持たないアドレスを名指す |
| クラスター内のロードバランサーに、広告せずに払い出しだけをさせる | 新しい部品が無い | 2 か所になるのは同じ。また、そのような実装が広告せずに払い出すかどうかは、頼れるように文書化された挙動ではない |

例外は ADR 0019 のものと同じ仕方で狭い。regied が書くのは、*このホスト* がサービスのために
受け持つアドレスである —— クラスターはこのホストについて知らされている —— そして、読むよう
言われたもの以外の設定をクラスターから受け取らない。資格情報に要るのは、サービスとノードの
読み取りと、サービスの status サブリソースへの書き込みで、それ以上は要らない。

#### 2. class の名前は 1 つで、全クラスターに共通、フィールドにしない

**提案: regied が受け持つ `loadBalancerClass` は 1 つで、どのクラスターでも同じとし、変える
フィールドは持たない。** 名前は apiGroup と同じ理由で、プロジェクト名の下ではなく
`net.unstable.cloud/` の下に置く（[ADR 0002](0002-configuration-schema.md)）。正確な値は spec が
決める。

サービスがどのクラスターに属するかは、regied がどの API からそれを読んだかで既に決まる。
リソースごとの class は情報を持たず、あるクラスターから別のクラスターへ移したマニフェストに
編集を要することになる。フィールドは、2 台のルーターが 1 つのクラスターを受け持ち、自分の
サービスを見分ける必要が出たときに足せる。それが必要になる場合である。

#### 3. 再起動の後は、クラスターが答えるまで何も公開しない

**提案: regied は、最後に受け持っていたもののファイルを持たない。プロセスの開始以来クラスターが
答えていないリソースは何も公開せず、クラスターの API を待っていると報告する。**
control-plane のエンドポイントは影響を受けない。クラスターから何も要らないからである。

対案は、最後の答えをファイルから戻し、クラスターが答えるまでそれを公開することである。
これが覆うのは 1 つの場合 —— クラスターは上がって動いているのに、ルーターからその API に
届かない場合 —— である。control-plane のエンドポイントがルーター自身のものになれば、API には
ルーターを通して届くので、その場合はまれである。反対に、ファイルは、中身がカーネルのもので
も宣言のものでもない生成物をもう 1 つ増やす。また regied が止まっているあいだに消された
サービスは、ファイアウォールの穴も含め、クラスターが答えるまで公開されたままになる。
払い出しはどちらでも失われない。クラスターの中にあるからである。

#### 4. 経路は regied のプロトコル番号を負い、networkd は外来の経路に触れない

**提案: 上の「経路の持ち主」のとおり。** networkd の既定を保ち、networkd の reload のたびに
経路を入れ直す対案は、`.network` ファイルに触れる適用のたびに隙間を残す。`ManageForeignRoutes=`
を切ると、他の誰かが残した経路も networkd は消さなくなる。このホストでは、それは損失ではなく、
ADR 0009 の規則を networkd に当てはめたものである。nexthop オブジェクトを使わないあいだは、
`ManageForeignNextHops=` はそのままにする。

#### 5. ルールセットは、セット・map・固定数のスロットを持つ

**提案: 上の「ルールセットとループの中での置き場」のとおり。** サービスの通信は経路で届くので
バックエンドごとのルールは要らない。バックエンドへ変換するのは control-plane のエンドポイント
だけで、そのスロットの数は宣言から来る。

#### 6. クラスターの API には、client-go ではなく最小のクライアントで話す

**提案: regied は、自分の小さなクライアントでクラスターの API と話す。** 2 種類のリソースを
list して watch し、watch はリソースバージョンから再開し、バージョンが古すぎれば list し直し、
1 つのサブリソースに patch する。kubeconfig からは、サーバー、CA、クライアント証明書か bearer
token を読む。exec プラグインを要する kubeconfig は検証のエラーとする。

regied の第三者の依存は今 1 つで、Cloudflare にも同じ理由で自分の小さなクライアントで届いて
いる（[ADR 0019](0019-uplink-address-in-dns-records.md)）。client-go はその片隅を使うために
大きなモジュールの木を持ち込み、その informer が解く問題 —— 多くの controller が多くの種類の
キャッシュを共有すること —— はここには無い。ループは既にレベルトリガーで、自分で resync する。
informer のうちここで効くのはその部分である。

#### 7. netns テストベッドに、偽物の API と複数のノードを足す

**提案:** [ADR 0010](0010-netns-testbed.md) のテストベッドに、偽物のクラスター API ——
サービスとノードの list と watch をフィクスチャから返し、status の patch を受ける小さな HTTP
サーバー —— と、複数のノードの namespace を足す。各ノードは与えられたサービスのアドレス宛ての
通信を受け、求めに応じて死活監視に答える。ルーターの外から確かめるのは次のことである。
公開したサービスに回線から届き、その回線から答えること。hairpin すること。IPv6 のアドレスに
届くこと。死活監視に落ちたノードが新しい接続を受けなくなること。接続がノードに散らばること。
偽物の API が落ちていても control-plane のエンドポイントが動くこと。範囲の中の払い出していない
アドレスに unreachable と答えること。クライアント・払い出し・衝突の規則は、`make test` の中で
偽物の API に対するユニットテストにする。本物のクラスターはテストベッドに含めない。

#### 8. kind も記録も 1 つ

**提案: 上のとおり kind を 1 つ、記録はこの 1 本。** 接続・枠・control-plane のエンドポイントは、
他の何からも名指されず、1 つのライフサイクルを共有するので、1 つのリソースである。決定は
1 つの機能のもので、記録を分けると、範囲の変更をそれを正当化する仕組みから切り離すことになる。

### spec が決めること

kind・フィールド・class・annotation の名前。サービスが特定のアドレスを求めてよいか、どう
求めるか。`publish[].ports` が TCP と UDP を同じく覆うか、プロトコルを取るか。死活監視の間隔と
閾値。プロトコル番号。ポートごとのエラーの正確な文言。

## 結果

- **公開はクラスターの操作になる。** 枠を宣言した後は、class と annotation を付けたサービスを
  作れば、アドレス・回線のポート・IPv6 のアドレス・ファイアウォールの穴が付き、消せば外れる。
  ルーターの宣言はサービスごとには変わらない。
- **クラスターどうしは踏み合えない。** 枠は、何かを適用する前に、互いと宣言の残りに対して
  確かめられ、クラスターが何を言っても自分の枠の外には届かない。
- **control-plane のエンドポイントはクラスターに依存しなくなり**、冷えた状態からの起動に循環は
  残らない。代わりに、ルーターに依存する。
- **ルーターを通る通信が増える。** LAN のクライアントからサービスのアドレスへの通信と、
  ノードから control-plane のエンドポイントへの通信が、ルーターを通るようになる。ルーターの
  再起動や、ルーターを壊す適用は、公開したサービスだけでなく、クラスターの control-plane にも
  届く。
- **LAN のクライアントからの通信は非対称になる。** ノードと同じセグメントにいるクライアントは
  ルーターを通してサービスのアドレスに届き、ノードはクライアントへ直接答える。その 2 つの
  ゾーンの間で接続の状態に頼るファイアウォールの政策は、これを落とす。その道の政策は
  ステートレスでなければならない。ルーターは ICMP redirect を送らない（[`docs/scope.md`](../scope.md)）
  ので、クライアントはルーターを通して送り続ける。
- **next hop の集合が変わると、確立した接続が切れうる。** マルチパスの経路はパケットごとに
  ハッシュする。ノードが増えたり減ったりすると、一部のフローは別のノードにハッシュされ、
  そのノードはそのフローの接続の状態を持たないのでリセットする。公開した IPv4 の道も同じ影響を
  受ける。変換先はサービスのアドレスで、経路はパケットごとに引かれるからである。これを減らすのは
  resilient な nexthop グループや IPVS の direct routing で、どちらも始めるのには要らない。
- **`Cluster` のサービスはクライアントのアドレスを失う。** kube-proxy が別のノードの Pod へ送る
  途中で送信元を変換するからである。`Local` のサービスは保つ。これは kube-proxy の挙動で、
  この記録では変わらない。
- **ノードは、ルーターからの死活監視を受けなければならない。** kube-proxy の health のポートと、
  各サービスの `healthCheckNodePort` で。ノードへの通信を絞るクラスターは、これを許す必要がある。
- **ルーターは、クラスターごとの資格情報を持つ。** 他の秘密と同じくファイルで。クラスターの
  運用者は、サービスとノードの読み取りと、サービスの status への書き込みを許す。
- **regied は 2 つめの外部 API のクライアントを得る。** クラスターごとの長く続く接続、
  死活監視、実行時の経路、`networkd.conf` の drop-in、自分で設定する 2 つのカーネルのスイッチ。
  常駐プロセス以来、単独では最も大きな追加であり、テストベッドもそれとともに大きくなる。
- **ADR 0013 のチェーンの表と、ADR 0020 の回線のマークの導出を補正する。** この記録が受け入れ
  られたとき、それぞれに注記を付ける。
- [`docs/scope.md`](../scope.md) の、動的ルーティングの節と、マルチノード・HA・クラウド連携の節を、
  この記録とともに書き直す。

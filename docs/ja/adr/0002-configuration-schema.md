# ADR 0002: 設定スキーマの形

- 状態: 決定（2026-08-30）
- ADR 0008 より前に引いた暫定の kind 一覧を**上書きする**

## 背景

最初の kind 一覧は「すべての層を regied が自分で実装する」前提で引いたものだった。
ADR 0008 でその前提が変わった。インターフェース、アドレス、ルート、ルーティングポリシー
ルール、ip6tnl トンネル、プレフィックス委譲、ルーター広告は、いずれも systemd-networkd が
既に宣言的に持っており、regied は自分で実装せずに渡す。

そうすると、古い一覧では答えられない問いが残る。**その層を networkd が持つなら、
利用者は何を書くのか。**

間違え方が 2 通り、逆向きにある。

- **厚すぎる。** networkd の概念ごとに kind を立てる。設定は「句読点の違う networkd の
  語彙」になり、利用者は両方を知らなければならなくなる
- **薄すぎる。** その層をスキーマから落とし、`.network` を別に書けと言う。
  すると 1 つの宣言が無くなり、そもそもの目的が消える

スキーマは **regied 自身の語彙**でなければならず、かつ利用者に継ぎ目を見せずに
networkd / nftables / dnsmasq / pppd へ落ちなければならない。

## 決定

### 文書

ホスト 1 台につき YAML 1 文書。`apiVersion: net.unstable.cloud/v1alpha1`、`kind: NetworkConfig`、
ホスト全体のスイッチを `spec.global`、リソースを `spec.resources[]` に並べる。
各リソースは `kind` / `metadata.name` / `spec` を持つ。**apiGroup にプロジェクト名を
入れないのは意図的である。** バイナリを改名しても設定ファイルが無効にならないようにする。

**`NetworkConfig` は文書が何を収めるかを名乗るのであって、ホストが何であるかを名乗らない。**
`Router` は暫定の名前で、2 つの向きに間違っていた。1 つは ADR 0009 との衝突である。
あの決定は `wan` / `lan` のような役割名を型に入れないことを求めており、いちばん外側の型は
その規則を破ってよい最後の場所である。もう 1 つは事実との食い違いで、ファイアウォールしか
持たないホストを言い表せない。**このスキーマは既にそれを受け付ける。** 必須のリソース kind は
1 つも無いので、ゾーンと政策だけを収めた文書は正当である。

`NodeConfig` も検討して落とした。regied の持ち分より多くを主張するからである。ホスト名、
タイムゾーン、アカウント、パッケージはいずれもノードの設定であり、いずれも意図的に範囲外に
置いてある（[`docs/ja/scope.md`](../scope.md)）。この文書が収めるのはネットワークの設定だけで、
`spec.global` の 7 つのカーネルスイッチまで含めてそうである。

リソース間の参照は `<kind の lower camel case>Ref` というフィールドで、値は相手の
`metadata.name`。kind はフィールド側で決まるので値には書かない。

### 何を kind として立てるか

次のいずれかに当たるとき、リソース kind として立てる。

1. **他から名前で参照される。** アドレス集合はファイアウォールのルールから、
   ゾーンは政策から、回線は NAT とポリシールーティングから名指される
2. **自分のライフサイクルを持つ。** 監督するプロセス、現れたり消えたりするリンク、
   リース情報のような状態
3. **繰り返し現れ、その 1 つ 1 つが単独で意味を持つ。**
   ちょうど 1 つの親の属性ではない

それ以外は、それを持つリソースのフィールドに畳む。
多くの場合は 1 番で決着する。**誰も名指さないものに名前は要らない。**

### kind 一覧

| # | kind | 何を表すか | バックエンド |
|---|---|---|---|
| 1 | `Interface` | 両端を regied が持つリンク（物理 NIC / ブリッジ）と、そのアドレス・MTU・静的ルート・PD クライアント・ルーター広告 | systemd-networkd |
| 2 | `PPPoESession` | PPPoE の回線 | pppd |
| 3 | `DSLiteTunnel` | IPv4 over IPv6 の回線（RFC 6333 の B4 側） | systemd-networkd |
| 4 | `EgressRoutePolicy` | ある種別のトラフィックがどの回線から出るか | nftables + systemd-networkd |
| 5 | `IPAddressSet` | 名前の付いたアドレス／プレフィックスの集合 | nftables |
| 6 | `FirewallZone` | 名前の付いたインターフェースの集合 | nftables |
| 7 | `FirewallPolicy` | 2 つのゾーンの間に適用するルール | nftables |
| 8 | `SourceNAT` | 出ていく側の送信元アドレス変換 | nftables |
| 9 | `PortForward` | 入ってくる側の宛先変換と hairpin | nftables |
| 10 | `DHCPServer` | 配下のリンクへのアドレス配布 | dnsmasq |
| 11 | `DNSForwarder` | 名前解決、条件付きフォワード、名前の上書き | dnsmasq |

以前の 14 個から 11 個になった。フィールド単位の詳細は [`docs/ja/spec/`](../spec/) にある。

### 畳んだもの、とその理由

**`StaticRoute` → `Interface.spec.routes[]`。** networkd に「ルートだけのファイル」は無く、
ルートは、そこから出ていくリンクの `.network` に置かれる。どのリンクから出るかを
利用者に書かせるのは正直な形であり、ルートが名前で参照されることは無い。

**`DHCPv6PrefixDelegation` → `Interface`。** クライアントは上流リンクの属性であり、
そこから導かれるアドレスは、それを載せる下流リンクの属性である。別立てにすると、
両側から指されるためだけに存在するリソースができる。

**`IPv6RouterAdvertisement` → `Interface.spec.ipv6.advertise`。** リンクは広告するか
しないかのどちらかで、何を広告するかはそのリンクが既に持つアドレスから導かれる。
インターフェースに置くことで、**同じリンクに 2 人目の広告者を立てることが構造的に
不可能**になる。スキーマの他のどこにも頼む場所が無いからである。

**`SystemSettings` — 落とした。** ホスト名・タイムゾーン・NTP は OS のものであり、
[`docs/ja/scope.md`](../scope.md) に既にそう書いてある。別の道具が持っているものを
言い直すだけの kind は、無いより悪い。

**`spec.global.allPing` — 落とした。** echo request を通すかどうかは
ファイアウォールのルールであり、ファイアウォールは regied 自身のモデルである。
裏でルールを書く大域スイッチは、ファイアウォールに入口を 2 つ作ってしまう。

### 足したもの、改名したもの

**`FirewallZone` を `FirewallPolicy` から分けた。** ADR 0009 は `wan` / `lan` を
型に固有名詞として埋めないことを求めている。ゾーンが政策の中の map であるかぎり、
政策の既定動作は `wanToLan` / `lanToSelf` のように綴るしかなく、**名前がスキーマに
入ってしまう**。ゾーンを kind にすると、政策は `from` と `to` を名指すだけになり、
名前はデータになる。予約語は `self` の 1 つだけで、ホスト自身を指す。
netfilter の hook は組から決まる。`to: self` は input、ゾーンからゾーンは forward。
**output に対する政策は書けない。** 対象とする構成に、ホスト自身の送出を絞るものが
無いからである。

**`NAT44Rule` → `SourceNAT`。** アドレスファミリは名前ではなくフィールドに置く。

### 利用者が書かないもの

古い一覧なら露出していたものを 2 つ、導出に変えた。

**ルーティングテーブル番号とファイアウォールマーク。** `EgressRoutePolicy` は
トラフィックの種別と回線を名指すだけである。regied がテーブルとマークを割り当て、
そのテーブルにデフォルトルートを入れ、マークからテーブルへの `[RoutingPolicyRule]` を
出し、マークを打つ nftables ルールを出す。番号は `regied render` で見えるし固定もできるが、
**regied の外から依存してはならない。**

**マークを打つ場所。** ポリシールーティングのマークを打つチェーンは **nat prerouting より
後ろ**で走る。したがって DNAT で書き換えられた後の宛先で照合する。hairpin —— LAN 側の
端末が、回線のグローバルアドレス経由で公開サービスに繋ぎに行く場合 —— は、マークを
考える時点で既に内側のアドレスに書き換わっており、その政策自身のローカル宛除外に落ちて
ローカルに配送される。**このため、回線のグローバルアドレスをどこにも書けないように
スキーマを作ってある。** `PortForward` と `SourceNAT` が取るのは回線リソースへの参照で
あって、アドレスのリテラルではない。アドレスを書けるスキーマは、アドレスが変わった
瞬間に壊れる設定を招き入れる。

## 帰結

- networkd に面する部分は 7 kind ではなく 3 kind になり、どれも networkd の書式を
  知らなくても書ける
- networkd の機能を後から使うのは、たいてい新しい kind ではなく `Interface` の
  フィールドが 1 つ増えることになる
- 2 つの kind（`DHCPServer`、`DNSForwarder`）が 1 つの dnsmasq プロセスに落ちる。
  適用のモデルはこれを併合する必要があり、どちらかの検証エラーは両方を落とす
- テーブル番号とマークが導出なので、ポリシールーティングの変更はリソース 1 つの編集で
  済む。3 か所を揃えて直す作業にならない
- ルーター広告は networkd、DHCPv6 のオプション配布は dnsmasq。**同じ宣言から動くが
  バックエンドは 2 つである。** この分かれ目は仕様書に見える形で残しておかないと、
  壊れたときにどちらを見ればよいか分からなくなる

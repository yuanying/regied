# ADR 0024: AAAA レコードを委譲プレフィックス内のアドレスに保つ

- 状態: 決定（2026-10-23）
- [ADR 0021](0021-values-derived-from-the-delegated-prefix.md) を前提とする
- [ADR 0019](0019-uplink-address-in-dns-records.md) を拡張し、作るときに
  [`docs/ja/scope.md`](../scope.md) を改める

## 背景

[ADR 0019](0019-uplink-address-in-dns-records.md) は DNS レコードを、1 つの目的に限って
範囲に入れた。名前を、このホストの回線が持つアドレスに追従させることである。AAAA は
次の理由で断った。役に立つ IPv6 のレコードはルーターのアドレスではなく、その後ろにいる
ホストの、委譲プレフィックス内のアドレスを持つ。それは *このホストが経路を持つアドレス*
であり、それを決めるには、他のホストのアドレスの名前を誰が公開してよいのかに答えなければ
ならなかった。

この一連の記録の他のものと同じ出来事が、いまその問いへの答えを迫っている。IPv6 で
サービスを公開する構成は、その AAAA レコードを事業者のところで手で保っている。委譲が
変わったとき、そのどれもが誰も持っていないプレフィックスを指すことになり、1 本ずつ
探して書き直さなければならなかった。ルーターは新しいプレフィックスを届いた瞬間に
知っており、ホスト部は人が選んだ固定の数である。レコードを書くのに、それ以外には
何も要らない。

公開する各ホストで動的 DNS のクライアントを動かせば、それぞれが自分のレコードを
保てる。だがコンテナ、ロードバランサーのアドレス、その他クライアントを走らせる
ホストでないものについては、レコードを保てない。しかも各ホストにトークンの写しが
もう 1 つずつ増える。

## 決定

### 範囲に入るもの

**regied は、このホストに委譲されたプレフィックス、またはこのホストが受け取る広告から
自分のために導いたプレフィックス（[ADR 0023](0023-downstream-hosts-derive-their-subnet.md)）
の中のアドレスと、その広告からこのホストが取るアドレスを持つ DNS レコードを保ってよい。**
広げるのはこれがすべてであり、「このホストが経路を持つアドレス」より狭い。リテラルの
サブネットへの静的経路はこれに当たらない。

[`docs/ja/scope.md`](../scope.md) が引く線は、どのホストを管理しているかについての
ものであり、その位置は動かない。

- **プレフィックスは、このホストが知っていてよいものである。** ルーターは事業者から委譲を
  渡された。下流のホストはそこから自分のサブネットを導き、どのサブネットとどのホスト部を
  使うかはその宣言が決める。そうしたアドレスの 1 つに名前を公開することは、このホスト
  自身のアドレス割り当てについての表明である。A レコードがこのホストの回線についての
  表明であるのと同じである。
- **他のホストは管理しない。** regied はそのアドレスの後ろにいるホストやコンテナを
  設定せず、そこで何かが応答するかを尋ねず、そこから何も受け取らない。そのアドレスが
  使われているかは健全性であって差ではなく
  （[ADR 0016](0016-converging-on-the-accepted-declaration.md)）、レコードが言うのは
  名前がどこを指すべきかだけである。
- **事業者から設定を受け取ることはない。** これまでどおりである。

`docs/scope.md` の例外の段落への補正は、「レコードは追従する回線を名指して IPv4
アドレスを持ち」を次で置き換えるものである。レコードは回線に追従してその IPv4 アドレスを
持つか、このホストに委譲された、またはこのホストが自分のために導いたプレフィックス内の
IPv6 アドレス —— 広告から取る自分自身のアドレスを含む —— を持つかのどちらかであり、
regied はそのアドレスで何かが応答するかを確かめず、各名前は 1 台のホストが保つ。
「他のホストは管理せず」は書かれたとおりに残す。

### どのホストが名前を保つか

**名前は、そのアドレスを決める宣言を持つホストが保つ。**

| 名前が指すもの | 保つホスト |
|---|---|
| ルーター自身、またはルーター自身のセグメント上にあって regied を走らせていないもの —— クラスターのロードバランサーのアドレス、他の何かが設定しているホスト | ルーター |
| regied を走らせている下流のホスト、またはそのブリッジの後ろにいるコンテナ | **その下流のホスト** |

下流のホストのアドレスのサブネット ID とホスト部は、下流のホストの宣言に書かれる
（[ADR 0023](0023-downstream-hosts-derive-their-subnet.md)）。そこで保つレコードは、
ブリッジとアドレスのセットが使うのと同じ `interfaceRef` を通してそれらを名指す。だから、
名前がどのホストのものか、それがどのアドレスを持つかを 1 つのファイルで読める。
ルーターも同じレコードを保つことはできる —— 自分の委譲を通した `fromDelegatedPrefix`
に、サブネット ID とトークンを添えて。だがそうすると、ADR 0023 が既に受け入れている 2 か所
に加えて、トークンが 3 か所目に、サブネット ID が 2 か所目に現れる。ルーターの上の何にも
それは見分けられないので拒みはしないが、手を伸ばすべき形ではない。

費用は、レコードを保つすべてのホストに置く credential である。どのホストにも、自分の
ゾーンに書けるトークンが要る。ADR 0019 が既に好む、1 つのゾーンだけに効くトークンなら、
それをできるだけ小さく保てる。

**1 つの名前を書くホストは、多くても 1 台である。** 2 つの regied が同じ名前を書けば、
変化のたびに互いが書いたものを書き戻し、どちらも相手を見られない。検証は、1 つの宣言の
中で同じ名前と型を持つ 2 つの項目を、今と同じく set をまたいでも拒む。ホストをまたいでは
それができず、名前を分けておくのは、両方の宣言がある設定リポジトリの責任である ——
ADR 0023 がサブネットの割り振りの確認を委ねているのと同じ場所である。

### 形

**レコードの項目は、回線に追従する A レコードか、導出したアドレスを持つ AAAA レコードの
どちらかである。** `type` は `AAAA` を取り、AAAA の項目は `egressRef` の代わりに
`address` を持つ。`address` は 2 つの形のうちちょうど 1 つを持つ。

| フィールド | A | AAAA |
|---|---|---|
| `type` | `A`。既定 | `AAAA` |
| `egressRef` | 必須 | 拒む |
| `address.fromDelegatedPrefix` | 拒む | どちらか 1 つ。`interfaceRef`、`subnetID`、`token` |
| `address.fromRouterAdvertisement` | 拒む | どちらか 1 つ。`interfaceRef` |
| `names`、`proxied`、`ttl` | 今と同じ | 今と同じ |

**`fromDelegatedPrefix`** は ADR 0021 の形であり、レコードはアドレスを持つものなので
`token` は必須である。その `interfaceRef` が名指せるのは、ルーターではプレフィックス委譲の
クライアントを走らせているインターフェース、下流のホストでは
`ipv6.advertisedDelegation` を宣言しているインターフェースである。

**`fromRouterAdvertisement`** は、名指したインターフェースが受け取る広告から取るアドレス
であり、トークンはそのインターフェース自身の `fromRouterAdvertisement` のアドレスが宣言する
ものを使う。下流のホストが自分の LAN アドレスを公開するのはこの形である。トークンは
もう一度書かない。インターフェースが既に持っており、レコードはそのインターフェースを
参照する。同じアドレスを `fromDelegatedPrefix` で書くには LAN のサブネット ID が要るが、
それはルーターが選ぶもので、下流のホストの宣言のどこにも現れない。そこに書けば、
ルーターの計画の写しがもう 1 つ増える。名指したインターフェースは
`fromRouterAdvertisement` のアドレスを持っていなければならず、持っていなければ検証エラー
である。

どちらかの形を項目に直接置かず、入れ物として `address` を置くのは、*レコードが何を持つか*
を言うフィールドが、どちらの形を持っていても同じように読めるようにするためである。
リテラルのアドレスを持つ AAAA は拒む。リテラルのレコードは regied が最新に保つものを
何も持たず、置き場所は事業者自身のコンソールである。回線自身の IPv6 アドレスに追従する
AAAA は、ADR 0019 の理由で引き続き拒む。

A と AAAA の両方の項目を持つ名前は 2 本のレコードであり、問題ない。

### ADR 0019 からそのまま引き継ぐもの

所有、書いたものの記憶、dry run、トークン、バックオフは ADR 0019 のものを一言一句
そのまま使う。

| 問い | 答え |
|---|---|
| 事業者に無いレコード | 作る |
| 宣言から外れたレコード | 事業者に残す。決して消さず、印も付けない |
| レコードを書くとき | 解決したアドレスが、このプロセスが最後に書いた値と違うとき |
| `--dry-run` | 各レコードとアドレスを名指し、事業者には何も尋ねない |
| トークン | ファイルで名指し、書き込むターンで読み、決して見せない |
| 書き込みの失敗 | そのレコードが *失敗中* になり、それ自身のバックオフの下に置かれる。ターンは最後まで進む |

### 新しいもの

**委譲が無い間、レコードはそのままにする。** 下流のホストでは、広告されたプレフィックスを
まだ読んでいない間である。それはこのホストの上に無い成果物である
（[ADR 0021](0021-values-derived-from-the-delegated-prefix.md)）。ターンは待ち、その
インターフェースを名指す。1 分の間前のプレフィックスを指しているレコードは、レコードが
無いよりよい。

**プレフィックスが変わると、すべての AAAA レコードを一度に書き直す。** それが求められた
ことであり、帰結が 3 つある。

- **TTL が一斉に切れる。** 古い答えをキャッシュしたリゾルバは、TTL の間それを持ち続ける。
  既定は引き続き `automatic` で、事業者のところでは短い。AAAA レコードに長い TTL を
  付けるのは、変化のあとその間だけ届かなくなることを選ぶことであり、spec はそう書く。
- **書き込みはまとめて来る。** レコード 1 本につき 1 回の書き込みを、1 つのターンで行う。
  家庭や小規模オフィスの構成が持つ数十本のレコードなら、事業者のレート制限の内側に
  十分収まる。拒まれたときはレコードごとのバックオフが既に扱う。残りは書かれ、拒まれた
  ものは再試行する。
- **ホスト自身の出口が上がっているとは限らない。** 変化が、ホスト自身の通信が通る経路の
  停止 —— これから作り直されるトンネル
  （[ADR 0022](0022-dslite-local-address-follows-the-delegation.md)）—— と一緒に来た
  なら、最初の試行は失敗してバックオフする。ADR 0019 は既にアドレスをリクエストに
  載せているので、リクエストがどの経路を通るかは、何が書かれるかを変えず、いつ成功
  するかを変えるだけである。

## 採らなかった選択肢

**公開する各ホストでの動的 DNS のクライアント。** それを走らせられるホストしか扱えず、
各ホストにトークンを置き、どのホストも丸ごとは持っていないアドレス —— ロードバランサーの
仮想アドレス —— のレコードを保てない。却下。

**AAAA を、アドレスを持つ `IPAddressSet` や `Interface` に畳む。** レコードのゾーン、
トークン、プロキシの指定、TTL は事業者についてのものであり、だから ADR 0019 は
レコードに独自の kind を与えた。ファミリが変わっても、そこは何も変わらない。

**宣言から外れた AAAA レコードを消す。** ADR 0019 が決して消さない理由として挙げたものは、
ここではもっと強く当てはまる。ゾーンの AAAA レコードは、regied が保つものの隣に手で
書かれていることが多く、regied にはそれらを見分ける方法が無い。

**すべての AAAA をルーターに保つ。** 下流のホストとそのコンテナの名前も含めて。この記録の
最初の草稿はこれだった。ルーターは委譲を持ち、credential も最も少なくて済む。却下した
のは、そうするとルーターが下流のホストのサブネット ID とトークンをもう一度持つことになり、
コンテナの番号を振り直すのに、それを走らせていないホストを編集することになるからである。
下流のホストに要る credential のほうが、小さな費用である。

**公開する前に、そのアドレスが応答するか確かめる。** それは方針を伴う健全性のプローブで
あり、ADR 0016 がループの外に置いているものである。しかもレコードを、regied が管理
しないホストに依存させることになる。

## 帰結

- **構成が手で保っている AAAA レコードは、そのアドレスを持つホストの宣言に移る。**
  ルーターは自分自身と regied を走らせていないものの分を、各下流のホストは自分自身と
  自分のコンテナの分を保ち、移したレコードは編集無しでプレフィックスの変化に追従する。
- **レコードを保つホストは、ゾーンのトークンを持つ。** 下流のホストも含めて。
- **1 つの名前を 1 台のホストで保つことは、設定リポジトリが確かめる。**
- **`docs/scope.md` の例外が 1 節伸びる。** ホストについての行は変わらない。
- **`DNSRecordSet.records[].type` が 2 つ目の値を得る。** ADR 0019 がそのために残しておいた
  フィールドを通して。
- レコードのアドレスは `--dry-run` で、導出元のプレフィックスと並べて見せる。

## 実装の単位

[ADR 0021](0021-values-derived-from-the-delegated-prefix.md) の一覧のうち 2 つの単位。

- **単位 4、ルーターのレコード**: プレフィックス委譲のクライアントを走らせている
  インターフェースを通した `type: AAAA` と `address.fromDelegatedPrefix` を spec と検証に、
  解決したアドレスを受け取る DNS の書き手、範囲の補正を、1 つのプルリクエストで。
  プレフィックスを解決する単位 1 の後に続き、単位 2 と 3 からは何も要らない。
- **単位 6、下流のホストのレコード**: `ipv6.advertisedDelegation` を宣言している
  インターフェースを通した `fromDelegatedPrefix` と、`address.fromRouterAdvertisement`。
  下流のホストにプレフィックスを与える単位 5 の後に続く。

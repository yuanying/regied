# ADR 0017: 提出は常駐プロセスを通る。常駐プロセスがホストの唯一の書き手である

- 状態: 決定（2026-09-05）。**実装済み。**

> **ここで決めた提出経路、制御ソケットの 4 メッセージ、プロセス寿命の書き手ロック、root
> 専用ソケット、最初の無人周回、単一のサービスは実装済みである。**
>
> ADR 0007 の HTTP API は保留のままであり、この記録はそれを復活させない。

## 背景

### 提出の経路が 2 本あり、書き手は最大 3 プロセスある

ADR 0016 は設計としては正しかったが、実装は噛み合わない 2 つの半身になった。普通の
`regied apply` はファイルを読み、宣言を検証してステージし、記録を書き、周回のロックを取り、
周回を回す —— すべて `apply` のプロセスの中で。`regied apply --confirm` は前半を `apply` の
プロセスでやったうえで、宣言を制御ソケット越しに常駐プロセスへ渡し、常駐プロセスが試行として
周回を回して時計を持つ。`regied reconcile` は 3 つめの入口で、さらに別のプロセスで周回を回し、
起動時ユニットがそれを走らせる。

つまりホストは最大 3 つのプロセス —— apply、reconcile、デーモン —— から書かれ、ファイルロックで
直列化されている。同じエンジンを走らせるので、どれが動いても結果は同じである。コードは
重複していない。重複しているのは**「書き手である」という立場**であり、これには具体的な代償がある。

### その代償

**デーモンしか知らない実行時の状態は、デーモンが回さなかった周回を生き延びられない。**
[ADR 0013](0013-nftables-ruleset-shape.md) は regied のテーブルを 1 トランザクションで
置き換える。置き換えれば、その中のセットもマップも空になる。回線セットは何も失わない。
カーネルが答えを持っていて、どの周回も播き直すからである（ADR 0015）。ADR 0007 も ADR 0016 も
同じ警告で締めくくっていた —— 出所がカーネルでない要素にはそういう回復が無く、テーブルを
置き換えるたびに、答えを知っている何かが書き直すまで暗いままの窓が開く。両方の記録が挙げた
例は、クラスタの API から学ぶ、負荷分散アドレスの背後のバックエンドである。デーモンには
持てて、`apply` のプロセスには持てないもの。`apply` のプロセスがテーブルを置き換えられる限り、
提出のたびにその窓が開き、デーモンにできるのは後から気づいて縮めることだけである。

書き手が 1 つなら、窓は存在しない。テーブルを置き換える周回はデーモンの周回であり、同じ周回が
デーモンの知る要素をすべて播く。いまフェーズ 1 が回線セットを播いているのと同じ場所で。
regied をクラスタの負荷分散アドレスの provider にするという方向はタスクが閉じないでいる道であり、
この記録を起こしたのもそれである。ここでその機能を足しはしない。この記録がやるのは、
apply のたびにその扉を閉めるのをやめることである。

**経路が 2 本あれば、等しく保つべきものが 2 つある。** いま、試行はデーモンに届き、普通の提出は
届かない。記録は一方のプロセスが書き、他方が読む。「試行中の普通の apply は試行を終わらせる」は、
デーモンが次の比較で気づく、という形で実装されている。どれも小さい。しかし合わせれば、
両方が書く 2 つのプロセスのあいだのプロトコルであり、そういうものが壊れる普通の形は、片方が
覚えた規則を他方が覚えていない、である。

**提出は運用者のセッションに縛られている。** 周回は `apply` のプロセスで走り、それを起動した
ssh セッションと一緒に死ぬ。運用者の経路を奪う変更 —— ADR 0016 が期限を作った理由そのもの ——
は、周回を途中で殺すこともでき、そうなるとループは許された半分しか終わらせない。

### Kubernetes の形を、最後まで描く

ADR 0016 は対応表を描き、1 行手前で止まっていた。Kubernetes の `kubectl apply` は etcd を
書かず、コントローラも回さない。マニフェストを API サーバーに送り、サーバーが検証し、保存し、
答える。コントローラはサーバー側のものである。クライアントが薄いのは、自分のプロセスでできる
ことが何であれ、サーバーがどのみちやらなければならないことの二重実装になるからである。

| Kubernetes | この記録の後の regied |
|---|---|
| `kubectl apply` がマニフェストを API サーバーに送る | `regied apply` が宣言のバイト列を常駐プロセスに送る |
| API サーバーが検証し、保存し、答える | 常駐プロセスが検証し、ステージし、記録を書き、周回を回し、答える |
| コントローラはコントロールプレーンにだけ居る | ループとすべての周回は常駐プロセスにだけ居る |
| admission を通らないマニフェストは保存されない | 検証かステージングを通らない宣言は記録されない |

### この記録より前に決まっていたこと

次の 3 つは 2026-09-05 にユーザーが決めたことであり、この記録はそれを蒸し返さない。

- 提出の経路は 1 本にする。常駐プロセスを通す。
- `regied reconcile` と起動時ユニット `regied-reconcile.service` は廃止する。常駐プロセスが
  ホストの唯一の書き手であり、その最初の周回が起動時の収束を兼ねる。
- HTTP API は保留のまま。ソケットは提出の経路であって、読み取り API ではない。

クライアントの半分を独立したバイナリにするかどうか、その名前を何にするかは、意図して
ここでは決めない。

## 決定

### `regied apply` はクライアントであり、常駐プロセスが唯一の書き手である

**`regied apply` は設定ファイルを読み、そのバイト列を制御ソケット越しに常駐プロセスへ送る。
ホストには何も書かず、周回も回さない。** 常駐プロセスが宣言を検証し、ステージし、記録を書き、
そこへ向けて提出の権限を持つ周回を回し、周回が何をしてホストをどこに残したかを答える。
クライアントはその答えを印字し、状態に応じた終了ステータスで終わる。

ADR 0016 が提出について言ったことはすべてそのまま成り立ち、しかも 1 か所で成り立つようになる。

- **記録は提出時に書かれる。宣言が検証とステージングを通った時点、最初のコマンドが走る前に。**
  それを書くプロセスが、それを読むプロセスと同じになる。
- **設定ファイルを読むのは `regied apply` だけである。** デーモンが読むのは記録と、クライアントが
  送ってきたバイト列だけである。設定ファイルのフラグは持たないし、これからも持たない。
- **記録が持つのは求められたものである。** コマンドが失敗した提出は、新しい宣言を記録に残し、
  ホストは到達した安全な接頭辞に居る。残りは ADR 0016 の規則のもとでループが働く。
- **試行は記録を書かない。** デーモンが期限のあいだメモリに持つ。

デーモンが行う検証は、いま `apply` が行っているものと同じである。文書、スキーマ、そして宣言が
名指すファイル。読めない認証情報ファイルは、いまと同じく、何かが走る前に提出を失敗させる。
クライアントは検証しない。早く失敗するためにファイルを parse してもよいが、答えはデーモンの答えで
あり、デーモンが拒んだ宣言は拒まれたのである。

**verb は 5 つ。** `render` と `apply --dry-run` はデーモンを読まず、これからも読まない。
これらは読み手であり、[ADR 0006](0006-dry-run-and-rendering.md) が引いた「ホストを読むもの」と
「何も読まないもの」の線は動かない。`apply` はデーモンを必要とする。`serve` がデーモンである。
`confirm` と `cancel` は ADR 0016 がソケットに与えた 2 つのメッセージである。

| verb | 読むもの | デーモンが要るか |
|---|---|---|
| `render` | ファイル | 要らない |
| `apply --dry-run` | ファイルと、このホスト（読むだけ） | 要らない |
| `apply` | ファイル。このホストを読むのはデーモン | **要る** |
| `serve` | 記録とこのホスト | それがデーモンである |
| `confirm`、`cancel` | ソケット | 要る |

**`reconcile` は無くなる。** それは「ファイルを読まない周回」を頼む唯一の手段だった。いまや
すべての周回がファイルを読まず、デーモンが毎分 1 周回す。人が `reconcile` を打っていた目的 ——
何も提出せずに、ホストをあるべき場所へ戻す —— は、ADR 0016 が無人の周回に引いた線までなら、
ループが頼まれずにやる。線の向こうの残り半分は提出であり、その頼み方は変わらない。ファイルを
`regied apply` する。同じ apply をもう一度走らせることは冪等で、残った手順だけをやり、
他には何もしない（[ADR 0004](0004-apply-model.md)、ADR 0016）。

**ファイルと記録が食い違っていて、人の権限で回し直したいのが記録のほうであるとき**も、答えは
やはり `apply` である。記録された宣言はファイルであり、そのバイト列は普通の宣言なのだから、
それを `apply` に指すことは同じリビジョンの普通の提出である。そのためのソケットのメッセージは
足さない。運用してみて、これが verb に値するほど頻繁に求められると分かれば、後から足せる ——
バイト列を運ばない提出が記録を意味する、という形で —— そのときここにある他の何も変わらない。
ソケットは verb ごとに版が切れるからである。いま足さない理由は
[ADR 0002](0002-configuration-schema.md) のものである。誰も必要としないうちに足した
インターフェースが、いちばん引っ込めにくい。

### ソケットが運ぶメッセージは 4 つ。ソケットは提出の経路である

ADR 0016 がソケットに与えた 3 つのメッセージ —— 試行、確認、取消 —— に、この記録は **提出
（submit）** を足す。4 つ。他には無い。

| メッセージ | 運ぶもの | デーモンがすること | 記録 |
|---|---|---|---|
| 提出（submit） | 宣言のバイト列と、それをどこから読んだか | 検証し、ステージし、記録を書き、提出の権限を持つ周回を回し、答える | 最初のコマンドの前に書かれる |
| 試行（trial） | 同じものと、期限 | 検証し、ステージし、宣言を試行として保持し、時計を始め、提出の権限を持つ周回を回し、答える | 触らない |
| 確認（confirm） | 何も | 試行を記録に書き、時計を止め、答える | 書かれる |
| 取消（cancel） | 何も | 試行を捨て、記録へ向けて提出の権限を持つ周回を回し、答える | 触らない |

**提出と試行は、線の上では 2 つのメッセージであり、デーモンの中では 1 本の経路である。**
この記録が受け取った枠組み —— 試行は同じ経路に期限が付いただけ —— は、デーモンの扱いそのもの
である。1 つの手順。検証してステージし、記録を書くか試行を保持するかのどちらかをして、同じ
周回を回す。もう 1 つの案、期限を任意のフィールドにした 1 つのメッセージ、は検討したうえで
1 つの根拠で退けた。2 つの違いは、ホストに戻り道が残るかどうかであり、**それをフィールドの
不在で決めてはならない。** メッセージが 1 つなら、期限が抜け落ちて届いた試行の要求は、運用者が
安全網を頼りにしているまさにその瞬間に、網の無い恒久的な提出になる。2 つのメッセージなら、
期限の無い試行は不正な要求であり、拒まれる。

**ADR 0007 と ADR 0016 が引いた線を、ここで次の言葉に引き直す。ソケットは、宣言がホストへ
向かうときに通る経路である。ホストに問いを投げる手段ではない。** 先の 2 つの記録は、ソケットは
status も apply も dry-run も運ばない、と言っていた。提出を足せば「apply を運ばない」は文として
間違いになるので、線は列挙ではなく「ソケットが何のためにあるか」で述べなければならず、
列挙はそこから導かれる。

ソケットが運ばないもの。この記録はこれを開いたままにしない。

- **たったいま変更を頼まれたわけでもないホストについての、いかなる問いも。** status も報告も
  readiness も health も無い。最後の周回の報告はファイルであり、journal は journal である
  （ADR 0016）。提出への応答は、その提出が起こした周回について述べる。誰か他の者が起こした周回に
  ついて述べるものは無い。
- **プレビューも無い。** dry-run も render も無い。どちらもデーモンを読まないし、ADR 0006 は
  dry-run の出力を機械向けのインターフェースにせず、コンソールに居る人のためのものとして
  意図的に残した。
- **reload も、リソース操作も、CRUD も無い。** 提出の単位は宣言であり、それより小さい単位は無い。
- **リースも、conntrack も、リンクの状態も、ログも無い。** それらは読み取り API のものであり、
  それは保留である。

**応答は、いまコンソールが受け取っているのと同じ報告を運ぶ。** README の障害時の手順を
真のままにするのはこれである。手順は「どの段で失敗したかはコンソールが言う」と書いており、
これからもそう言う。応答が名指すのは、リビジョン、状態（収束済み・待機・失敗）、結果、周回が
フェーズごとに何を変えたか、何を待っているか、何がどこで失敗したか —— フェーズ、段、原因 ——、
レンダラの警告、そして注記である。これは最後の周回の報告の中身であり、報告はすでに構造化された
ファイルである。ADR 0006 が非構造のままにした dry-run の計画ではないので、2 つの決定は衝突しない。

### ソケットに届ける相手は、ホストを設定し直してよい相手である

ADR 0007 は読み取り専用の API のためにソケットを設計し、root と 1 つのグループに与えた。
ADR 0016 はそのモードを confirm と cancel のために保った。ソケットに届いても、ホストで `regied` を
打てる者に何の能力も足さない、というのが根拠だった。提出が乗ればその根拠は消える。ソケットへの
接続は、いまやホストのネットワークを変える能力そのものであり、その能力を既に持つ者にだけ
与えなければならない。**ソケットは root のものである。パッケージはグループを設定しない。**
グループに開く運用者は、そのグループにホストのネットワークに対する root を与えたのであり、
それを分かったうえでそうするべきである。regied はそれを止めないし、代わりにやりもしない。

### 結果は同期で返る

**提出は自分の周回を待ち、その結果を返す。** デーモンが宣言を受け入れた時点で戻って、
運用者に報告を読ませる形にはしない。

- **人がそこに居る。** ADR 0016 が自動ロールバックを退けた論拠の全体は、提出が誰かの打った
  コマンドであり、失敗が同じ秒にその人のコンソールに落ちる、ということだった。提出して
  ポーリングする設計は、それを捨てる。
- **周回は有限である。** ADR 0004 は発呼やリゾルバを待つことを拒んでおり、周回は走らせる
  コマンドの集まりでしかない。それを待つことは、終わるものを待つことである。
- **README の手順はコンソールを読む。** どの段で失敗したか、ホストがいま何を動かしているかは、
  運用者が打ったコマンドが印字する。この記録はそれを、習慣ではなく要件として保つ。

**周回は接続に属さない。** クライアントが周回の途中で居なくなっても —— 運用者が中断した、ssh の
セッションが落ちた、変更そのものが運用者の経路を切った —— デーモンは周回を終わらせ、報告を書き、
結果をログに残す。クライアントは、まだできるなら、接続が失われたことと、結果は報告と journal に
あることを言う。接続が切れたときクライアントに分からないのは、記録が書かれたかどうかである。
それに答えるのが報告である。

これはいまの設計に無い性質であり、期限の仕組みが直接その恩恵を受ける。運用者の経路を奪う変更が、
周回の半分まで一緒に奪うことは、もう無い。

### 書き手は 1 つ、ロックは 1 つ、周回のあいだの線は同じ

**周回をプロセスをまたいで直列化する必要は無くなる。回すプロセスが 1 つだからである。**
デーモンは周回を 1 度に 1 つ回す。いまと同じである。再同期の周回の最中に届いた提出はそれを待ち、
提出の最中に来た tick は遅らされ、試行の期限切れは自分の番を待つ。

**状態ディレクトリの下のロックは残り、意味が変わる。** これまでは走っている周回が持っていた。
これからは**デーモンのものになり、プロセスの生きているあいだ持ち続ける。** 2 つめの
`regied serve` はそれが取られているのを見て、そう言って、起動を拒む。最初のデーモンから
ソケットを奪うのではなく。他にロックを取るものは無い。dry-run はいまと同じくロック無しで
ホストを読み、締め出すべき他の書き手も無い。「書き手は 1 つである」と主張するロックを残す価値が
あるのは、設計がまさにそれが真であることに依存するようになったからである。

**ADR 0016 が引いた段 —— 提出の権限を持つ周回は再起動と停止ができ、無人の周回は上がっているものを
落とさない —— は変わらず、線も変わらない。線は「誰がその周回を頼んだか」である。** 両方の種類が
1 つのプロセスで走るようになったいま、区別はそれを走らせるプロセスの性質ではなく周回の性質であり、
エンジンはすでにそう表している。

| 周回を起こしたもの | 種類 |
|---|---|
| 提出のメッセージ | 提出の権限を持つ |
| 試行のメッセージ | 提出の権限を持つ |
| 取消のメッセージ、または試行の期限切れ | 提出の権限を持つ —— 期限を置いたとき運用者がそれを頼んだ |
| 確認のメッセージ | 無し。確認は記録を書くだけで、周回を回さない |
| 定期の再同期 | 無人 |
| カーネルのアドレスイベント | 無人 |
| **デーモンの起動** | **無人** |

最後の行が、この記録が間違えてはならない行である。廃止された起動時ユニットの権限が、
さもなければそこへ行っていたからである。

### 起動時は、デーモンの最初の無人の周回が収束である

`regied-reconcile.service` は廃止する。`regied.service` が唯一のユニットであり、デーモンが
上がる途中で回す最初の周回が、再起動の後にルールセットも他のすべても入れるものになる。

**起動時に最初の周回で足りる理由。** 再起動の直後、regied が宣言するものは何も上がっていない。
テーブルはカーネルに無く、スイッチは既定値で、セッションは発呼しておらず、dnsmasq は動いていない。
ADR 0016 が無人の周回に引いた線 —— 上がっているものを決して落とさない —— は、そういうホストでは
何も縛らない。上がっているものが無いからである。起動時にやるべきことはすべて線の許される側にある。
テーブルを入れる、スイッチを書く、ファイルを書く、ユニットを起動する。起動時ユニットは提出の
権限を持つ周回を回していた。起動したばかりのホストでは、提出の権限を持つ周回と無人の周回は
同じことをする。

**再起動直後の最初の周回も無人であり、無人のままでなければならない理由。** `systemctl restart
regied` は運用者がやることである。アップグレードの後、ユニットを直した後、癖で。もしデーモンが
起動と再起動を区別して、最初の周回に提出の権限を与えたら、前の途中で終わった提出がオプション
ファイルを書き換えていた稼働中の PPPoE セッションを、再起動のたびに張り直す資格を持つことになる ——
誰も apply だと思っていない `systemctl restart` で回線が落ちる。デーモンには起動と再起動を確実に
見分ける術が無く、見分けようともしない。どの起動も同じであり、最初の周回は無人である。
動いているホストが残り半分を必要とするなら、人が `apply` で頼む。ADR 0016 がすでにそう言っている。

**起動時にやらなくなること 1 つ。** 途中で失敗した提出が再起動に出会ったとき —— たとえば、
止めたセッションの走っていたユニットを回収する前に —— これまでは起動時の周回がそれを終わらせていた。
提出の権限を持っていたからである。これからは、ループに許されていない提出の残り半分がすべてそうで
あるように、人を待ち、報告がそう言う。これは ADR 0016 が再起動抜きの同じ場合に与えている扱いと
同じであり、再起動に回線を落とす力を与えるよりはこちらを採る。

**失うものと、その代わり。** 失敗した oneshot ユニットは `systemctl status regied-reconcile` で
赤く見え、それは本物の合図だった。代わりになるのは、既にある 2 つと、新しい 1 つである。

- `regied.service` の journal は、状態がいつ何に変わったか、何が失敗したかを言い、他の周回と
  同じく最初の周回でもそれを言う（ADR 0016）。
- 最後の周回の報告がディスクにあり、同じことを言う。
- **デーモンは自分の状態を、systemd がそのために表示する status 行に置く。** `systemctl status
  regied` が、収束済み・待機・失敗のどれかと、何を待っているか・何に失敗しているかを、誰も
  journal を開かずに言うように。最初の周回の後に readiness も systemd に報告するかどうか ——
  それは起動に「ホストが設定された確定した時点」を与え、ADR 0016 が別ユニットに価値を見た
  もう 1 つの理由に答える —— は、これを作る単位に委ねる。regied が配るユニットのどれも
  それに依存しない、という注記つきで。

**止めるのであって、無効にするのではない。** ADR 0016 は別の起動時ユニットに 2 つめの根拠を
与えていた。デーモンの stop のレバーは disable のレバーでもあり、障害の最中にデーモンを無効にして
から再起動した運用者にも、再起動後のファイアウォールは要る、と。ユニットが 1 つなら、それを
無効にすることは起動時の収束も無しにすると選ぶことである —— そしてそういうホストでも、regied が
書いたセッションのユニットは起動時に発呼する。それを起動するのは systemd だからで（ADR 0004）、
前にテーブルは無い。これはいまも両方のユニットを無効にすれば得られるホストであり、この記録が
それを起こりやすくするわけではない。しかし障害時の手順は**止めよ、決して無効にするな**と
言わなければならず、その 1 文は README のものである。

`regied.service` の順序は、ADR 0007 が両ユニットに決め、ADR 0016 が保ったものである。
`systemd-networkd.service` の後、ディストリビューションの `nftables.service` が有効なら
その後、そして `network-online.target` より前には決して置かない。ADR 0007 の理由により、
パッケージが配り、regied は描画しない。

### デーモンが居なければ `apply` は拒まれる

**常駐プロセスが動いていないホストでの `regied apply` は、ホストから何かを読む前に拒まれ、
何をすべきかを言う。`regied.service` を起動せよ、と。** 自分で周回を回す形に切り替えはしない。

その切り替えは魅力的に見える。そしてそれこそが、裏口から戻ってくる 2 つめの書き手である ——
いちばん監督の薄いホストでこそ使われ、この記録が取り除く仕掛けをまるごと抱えて。動いていない
デーモンは緊急事態ではない。ホストは載っているものを動かし続け（ADR 0016 の stop のレバー）、
デーモンを起動する 1 つのコマンドは、拒否の文が名指すコマンドそのものである。

**新しいホストでは、まずデーモンを起動し、それから最初の `apply` がホストを設定する。**
記録の無いデーモンは何もせず、そう言い（ADR 0016）、そして待ち受ける。何も提出されていない
うちに起動しても安全である。インストールの手順は「入れる、`regied.service` を有効にして起動する、
`regied apply` する」になる。いまは「apply して、両方のユニットを有効にする」である。この変更は
README に申し送る。

クライアントから見た「動いていない」は、制御パスにソケットが無いか、誰も待ち受けていない
ソケットがあるか、である。どちらも同じ文で拒まれる。誰かが待ち受けては*いる*が答えないソケットは
別の失敗であり、次の節にある。

### それぞれの失敗が、記録とホストをどこに残すか

ADR 0016 の不変条件は、プロセスを失うあらゆる経路が前の宣言へ解決すること、そして試行は決して
デーモンを生き延びないことである。どちらも成り立ち、表がその論証である。

| 失敗 | 記録 | ホスト | 運用者に見えるもの |
|---|---|---|---|
| ソケットが無い、または誰も待ち受けていない | 触られない | 触られない | `apply` が拒み、`regied.service` を起動せよと言う |
| デーモンが接続を受けたまま答えない | クライアントからは不明。報告が言う | 周回がしたこと | クライアントは待つ。中断されればどこを見るべきかを言う |
| デーモンが検証かステージングの最中、記録の前に死ぬ | 前の宣言 | ステージングが書いたファイルがあればそれ。次の周回が前の宣言のものを書き戻す。ファイルの書き込みは線の許される側にある | 接続が切れる。クライアントは結果が報告にあると言う |
| デーモンが記録の後、コマンドの最中に死ぬ | 新しい宣言 | 周回が到達した安全な接頭辞。デーモンが戻ってきて無人で収束し、人が要ることを報告する | 同上 |
| デーモンが試行の最中に死ぬ | 前の宣言 | 戻ってくる途中でそこへ収束する（ADR 0016） | 同上 |
| クライアントが周回の途中で死ぬ | 周回が残したとおり | 周回は終わる | 報告を読むまで何も |

2 つの行には理由を書いておく価値がある。

**ステージングと記録のあいだでデーモンが死ぬ**のは、受け入れられていない宣言のファイルが
ホストにある唯一の場合である。これが正しく解決するのは、ADR 0016 が既に与えた理由による。
ファイルの書き直しは無人の線の許される側にあるので、再起動後のデーモンの最初の周回が前の宣言の
ファイルを書き戻し、そのあいだにそれを読むものは何も再起動されていない。勝つのは前の宣言であり、
それは不変条件が求める向きである。

**クライアントが周回の途中で死ぬ**行は、良くなる行である。いまは `apply` のプロセスが周回であり、
それを失えば —— ssh のセッションが落ちる、変更が運用者の経路を切る —— 周回はその場で止まる。
この記録の後、周回はデーモンのものであり、終わる。運用者にもう見えなくなった提出は、完了し、
記録され、報告される。

デーモンはユニットが既に言っているとおり、失敗時に systemd が再起動する。そしてどの起動の後でも
最初の周回は、上で決めたとおり無人である。

### netns の受け入れは形を保つ

VM のルーターを対象にした受け入れ（[ADR 0010](0010-netns-testbed.md)）は、ホストに `apply` を
当ててから `serve` を起こし、ループが引き継ぐことを確かめている。この記録の後、順序は逆になり、
受け入れについて変わるのはそれだけである。**`serve` を先に、制御パスを付けて起こし、デーモンが
待ち受けたら同じ制御パスで `apply` を走らせる。** `apply` は変わらず周回が終わるまで待ち、変わらず
同じ状態を同じ終了ステータスで印字するので、その直後に受け入れが行う検査 —— 管理経路がまだ
答えること、答えなければテーブルを消すこと —— はこの記録が動かすものに何も依存しない。続く
7 つの検査はルーターの外から行われ、ルーターがどう設定されたかを知らない。受け入れが許容しなければ
ならなくなるのは、起動から最初の `apply` までのあいだに、デーモンが「受け入れられた宣言は無い」と
ログに書くことである。それはまだ設定されていないホストのデーモンの正しい答えである（ADR 0016）。
順序の入れ替えは、コードと一緒に実装単位へ申し送る。受け入れとバイナリが同じ pull request で
変わるように。

ユニットテストも形を保つ。デーモンが提出のメッセージを扱うのは同じインターフェースの背後の
同じエンジンであり、クライアントはソケットとファイルの関数で、どちらもすでに偽物が立っている。

### この記録が決めないこと

- **クライアントを別のバイナリにするか、その名前を何にするか。** クライアントが要るのは
  ソケットとファイルだけで、エンジンは要らない。分けることはパッケージングの問題であり、
  そのためにここの何かを変える必要は無い。
- **線上の符号化。** 4 つのメッセージと、応答が運ぶものより先は決めない。
- **この記録が窓を閉じる、負荷分散の要素。** kind もフィールドも要素も約束しない。約束するのは、
  それが存在するようになったとき、テーブルを置き換えるのと同じ周回で、それができる唯一の
  プロセスによって書かれる、ということである。

## 採らなかった選択肢

**経路を 2 本のままにし、`apply` が後からデーモンに知らせる。** デーモンは知らされたら自分の知る
ものを播き直し、窓は通知の遅延の長さになる。退けた。窓はまだそこにあり、2 つの書き手のあいだの
プロトコルもまだそこにあり、メッセージが 1 つ増えている。

**デーモンの無いホストの逃げ道として `reconcile` を残す。** ユーザーが廃止を決める前に合意されて
いた形であり、それを退ける論拠はユーザーのものである。逃げ道は同じバイナリなので、デーモンが
動かせないホストは `reconcile` も当てにできないホストである。そして 2 つめの書き手である逃げ道は、
この記録が取り除くために存在するものそのものである。`reconcile` が起動時に担っていたことは
デーモンの最初の周回がやり、人が手で打っていたことはループが頼まれずにやり、`apply` が頼まれてやる。

**デーモンの最初の周回に提出の権限を与え、途中で終わった提出を起動時に終わらせる。** 退けた。
デーモンには起動と再起動を見分ける術が無く、その権限を持った再起動は回線を張り直す。

**提出と試行の代わりに、期限が任意の 1 つのメッセージ。** 上で退けた。ホストに戻り道が残るか
どうかは、フィールドの有無に依存してはならない。

**提出して戻り、運用者に報告を読ませる。** 上で退けた。人がコンソールに居て、周回は有限で、
README の手順はコンソールを読む。

**デーモンが居ないとき `apply` のプロセスで周回を回す。** 上で退けた。裏口からの 2 つめの
書き手であり、いちばん監督の薄いホストで使われる。

**デーモンがシグナルで設定ファイルを読む**、つまり `apply` を `kill -HUP` にする。ADR 0016 の
根拠 —— 自分で走るものはファイルを読んではならない —— で退けた。そのうえシグナルはどのファイルかを
運べず、答えられず、人と同じくらい容易くスクリプトが送る。

**書き手が 1 つになったのだからロックを捨てる。** 退けた。設計が依って立つ不変条件を主張する
ロックはただで、二重に起動したデーモンを競合ではなく拒否に変える。

## 帰結

- **ホストの書き手は 1 つになる。** テーブルの置き換えはすべてデーモンが回す周回の中で起き、
  デーモンの知るものはすべてその同じ周回で書き戻せる。ADR 0007 と ADR 0016 が警告した窓は、
  まだ存在しない要素について閉じる。閉じるのがいちばん安いのはそのときである。
- **`regied apply` には `regied.service` が動いていることが要り**、動いていなければそう言う。
  新しいホストではデーモンが先に起動する。これが書き手を 1 つにする代償であり、インストール時に
  1 度払う。
- **提出は運用者のセッションを生き延びる。** クライアントがまだ繋がっているかどうかにかかわらず、
  周回は終わる。運用者を締め出す変更が、切断がたまたま止めた段にホストを置き去りにすることも
  もう無い。
- **6 つのコマンドは 5 つの verb になり、2 つのユニットは 1 つになる。** `reconcile` と
  `regied-reconcile.service` は消える。それらがやっていたことは、デーモンの最初の周回と `apply` が
  やる。
- **デーモンの再起動は構造として安全である。** 最初の周回が無人だからである。上げることはでき、
  回線を落とすことはできない。別の起動時ユニットを持たないことを受け入れられるのはこれによる。
- **状態は `systemctl status regied` に見える。** 赤い起動時ユニットの代わりはこれである。
- **ソケットのモードはホストを設定し直す権限であり**、パッケージはそれを root だけに与える。
- **エンジンの形は変わらない。** ステージング、記録、周回、段、報告、バックオフ、期限は
  ADR 0016 のものであり、1 つのプロセスに移るだけである。新しいのはクライアントで、小さい。
- **ADR 0007 の HTTP API は保留のままであり、このソケットからは前より遠くなる。** ソケットは
  いまや、ADR 0007 がエンドポイントの裏に置くことを拒んだ唯一の書き込みを運ぶ —— ただし root と
  同等のファイルシステムの権限のもとで、同じホストのプロセスへ運ぶ。ADR 0007 が「その拒否は
  当たらない」と言った条件がそれである。読み取り API は、誰かが欲しがったとき、露出と認証を一緒に
  決める別の決定であり、ADR 0007 がそう言ったとおり、このソケットには乗らない。

## この記録が置き換えるもの

- **ADR 0016 の提出の経路を supersede する。それ以外は置き換えない。** 提出が回す周回は `apply` の
  プロセスのものではなくデーモンのものになる。記録はデーモンが書く。`regied reconcile` と起動時
  ユニットは廃止され、デーモンの最初の周回が起動時の収束になる。周回はプロセスをまたいでではなく
  1 つのプロセスの中で直列化され、ロックはデーモンのものになる。記録、段、3 つの状態、ロール
  バックの拒否、期限、stop のレバー、周回が省いてよいものの規則は変わらず、ここはその上に載っている。
- **ADR 0007 の「ソケットが運ぶもの」を補正する。** 「status も apply も dry-run も無い」は
  「ソケットは提出の経路であって読み取り API ではない —— 4 つのメッセージであり、ホストへの問いは
  無い」になる。`/run` の下のソケットという決定とその理由は立ったままであり、モードは root に絞られる。
- **ADR 0006 は変わらない。** `render` と `apply --dry-run` はデーモンを読まない。
- **ADR 0004 は変わらない。** 2 つの段階、順序、監督の決定はどの周回もやることであり、変わるのは
  提出の権限を持つ周回をどのプロセスが回すかだけである。

# ADR 0001: 自作する

- 状態: 決定（2026-08-23）

## 背景

更新の止まったベンダー OS のルーターを、arm64 の SBC に載せ替えたい。
そのとき、EdgeOS 独自の設定言語（`config.boot`、700 行あまり）を宣言的なモデルに
置き換える必要がある。既存の実装を採る道が 2 つあった。

想定する構成は次のとおりである。**外向きの回線が 1 本しかなく、それが止まると
生活と作業の両方が止まる。** 冗長構成は無く、機材も 1 台である。

## 検討した選択肢

### imksoo/routerd を採る

擬似 WAN のテストベッド（→ ADR 0010）に実際に掛けて実測した（`v20260822.2333`）。
移植対象の 7 領域は概ね表現でき、**検証項目 7 つとも通った**。機能は足りている。

採らなかった理由は、その版で実測して分かった次の性質による。
いずれも upstream に報告すれば直る種類のものであり、実装の優劣の話ではない。

- **PPPoE セッションが切れても張り直さない。** Linux 側の pppd 設定に `persist` も
  `maxfail` も `holdoff` も書かれず、再接続ループも connect を送るコードも無い。
  リンクを落として 7 分観測しても復帰しなかった。回線が 1 本しかなく、それが PPPoE である
  以上、これが最も重い
- **検証を通るのに黙って壊れる設定が 2 つある。** `PPPoESession.spec.ifname` を書くと
  実デバイス名と食い違って PPPoE 経路が全滅する。`NAT44Rule.egressPolicyRef` を使うと
  masquerade が 1 本も生成されず NAT が消える。どちらも `validate` は通る
- **公開スキーマが実装の写像になっていない。** 何が書けるかを知るにはソースを読む必要がある

回避策はすべて外側に置ける形で実証済みである。つまり技術的には採れる。
だが採るということは、28 万行の QA を自分で引き受けるということでもある。

### VyOS を採る

EdgeOS の直系（Vyatta の後継）であり、必要な機能はすべて入っている。
設定モデルの管理方法が好みに合わないため採らなかった。

## 決定

自作する。ただし **「機能が足りないから」ではない。**
1 本しかない回線を預ける先を、自分で読み切れる規模に保つためである。

## 帰結

- 規模を保つことが目的なので、**既にある実装を置き換えない**（→ ADR 0008）
- 他人が作った状態を壊さない（→ ADR 0009）
- imksoo/routerd の kind 名とスキーマの作法は引き続き設計の参考にする
- 評価の過程で作った擬似 WAN のテストベッドは、どちらに転んでも使うものとして残る

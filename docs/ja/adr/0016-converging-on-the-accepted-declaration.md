# ADR 0016: ホストが受け入れた宣言へ収束し続ける

- 状態: 決定（2026-09-04）。**実装済み。**

> **ここで決めた記録、1 周の収束、常駐ループ、起動時ユニット、確認、取消、試行とその期限は
> 実装済みである。** ADR 0007 の HTTP API は保留のままである。
>
> **[ADR 0005](0005-apply-rollback.md) が決めたロールバックは削除済みである。**
> この記録は決定としては 0005 を置き換える —— 自動で戻すものはもう無い。ループは提出された
> ものへ向けて働き続け、戻るのは人が前のファイルを適用することである。コードはループを作る
> 単位が削除した。
> [ADR 0015](0015-uplink-addresses-in-sets.md) が「決定」と「実装」の 2 段で運ばれたのと
> 同じ形である。
>
> ADR 0007 の HTTP API は保留のままであり、この記録はそれを復活させない。
> ここで求める常駐プロセスは、HTTP で何にも答えず、エンドポイントを 1 つも提供しない。
>
> **提出の経路は [ADR 0017](0017-submission-through-the-resident-process.md) が supersede する**（2026-09-05 実装済み）。提出は制御ソケット越しに常駐プロセスへ届き、常駐プロセスが記録を書いて周回を回す。`regied reconcile` と起動時ユニットは廃止された。それ以外はここに書かれたとおりである。

## 背景

### エンジンは既に調整ループである。1 周分ずつではあるが

ADR 0004 が決めたのは「設定を適用する」ことではない。「ホストを設定に一致させる」ことである。
適用は宣言を読み、ホストが持っているものを読み —— 所有するファイルのバイト列とモード、
書き込むカーネルスイッチの現在値、自分のテーブルがカーネルに在るか、その中のセットが何を
持っているか、各回線のリンクが何を持っているか —— 比べて、違うところだけを動かす。
**何も変わっていない適用は 1 コマンドも実行しない。**これは level-triggered な調整であり、
この系の安全性は既にそこに載っている。dry-run の「変更なし」（ADR 0006）も、回線セットを
記録したテキストではなくカーネルに照らして播くこと（ADR 0015）も、カーネルが持っていない
テーブルを起動時に入れることも、すべてそこから来ている。

だから、この記録の発端になった要求 —— **一度当てて終わりではなく、宣言された状態をずっと
保ってほしい** —— は作り直しの要求ではない。**適用は既にループの 1 周分である。**
足りないものは 2 つしかない。それを回し続ける何かと、回す対象の宣言を置く場所である。

### 何が求められたか

3 つの要求が同時に出た。**これらは 1 つの設計の 3 つの面である。**

1. 誰かがコマンドを打った瞬間だけでなく、Kubernetes のコントローラのように、
   宣言された状態を継続して保つこと。
2. **daemon を止めることで、調整ループを止められること。**障害のさなか、運用者は nftables を
   手で直し、その手直しがそのまま効いていてほしい。
3. 戻すことに専用の機構は要らない。前の宣言はバージョン管理にあり、人がそれを適用すればよい。

そして、これらを引き出したのは、どれとも直接は関係しない 1 つの指摘だった。設定は
**妥当で、描画も通り、エラーもなく適用され、そのうえで間違っている**ことがありうる ——
インターフェースの宣言を誤り、そのせいでネットワーク越しにホストへ届かなくなる、という形で。

### 4 つの安全策がどれも捕まえない失敗

このプロジェクトの元になったタスクは、安全性として 4 つを挙げている。運用者を締め出す
宣言に対して、そのどれもが「通ってしまう」。

| 既存の策 | なぜ効かないか |
|---|---|
| 冪等な適用 | 成功している。**壊れた状態が正しく保たれ**、当て直せばまた正しく保たれる |
| ロールバック | 何も失敗していないので発動しない |
| dry-run | 設定は妥当で描画も通る。**間違っているのは意味の側である** |
| 調整ループ | 宣言と実際は一致している。収束としては健全なホストである |

**エラーが起きないことが、この問題の本質である。**regied が持つ機構はどれも「宣言」と
「ホスト」を比べる。その宣言が運用者の望んだものかどうかは、比較のどちら側からも答えが
出ない問いである。答えられるのは、**まだホストに届く人**だけであり、しかも意味を持つ答えは
「届いた」という事実そのものである。

### Kubernetes と同じところ、違うところ

対応は上に載せられるほど近く、正確に取っておく価値がある。

| Kubernetes | regied |
|---|---|
| `kubectl apply`（API サーバへの提出） | `regied apply` —— **設定ファイルを読むのはここだけ** |
| admission。検証を通らないマニフェストは保存される前に拒まれる | 最初のコマンドの前の検証と描画（ADR 0004 のステージング段） |
| etcd に入った spec。提出時に書かれる | 受け入れられた宣言の記録。提出時に書かれる |
| コントローラの調整ループ | 常駐プロセス —— **設定ファイルを読まない** |
| 収束できないコントローラは再試行して報告する。決して戻さない | 同じ |
| 戻るのは前のマニフェストを `kubectl apply` すること | 同じ。前のファイルを `regied apply` する |

**ディスク上のファイルは spec ではない。**Kubernetes でもそうである。エディタの中の
マニフェストは、提出されるまでクラスタの中に無い。同じ規律を敷けば、継続的に調整する
ルーターの明白な危険が**構造的に消える** —— `/etc/regied/config.yaml` を読むループは、
書きかけの編集からホストを再構成する。定期的に、誰も見ていないところで。
記録を入力とするループは、**人が提出したものへ近づけることしかできない。**

違うところは 2 つあり、どちらも同じ事実から来る。**このホストは回線が 1 本で冗長性が無く、
regied は自分が再構成している線の上から触られる。**

- Kubernetes のコントローラがすべての行為を等しく扱えるのは、Pod が 1 つ再起動しても
  Deployment の残りが応答し続けるからである。ここでは、セッションの再起動は事業者が要する
  時間だけ線が落ちることである。nftables のテーブルを入れ直すことと PPPoE を張り直すことを
  同じ種類の行為として扱うループは、いずれ自分の判断で線を落とす。だからループには、
  自分の判断では越えてはならない線を与える。
- 悪い Deployment でクラスタから締め出される人は居ない。API サーバはワークロードの
  向こう側に無いからである。ここでは運用者が設定の向こう側に居るので、変更した本人がもう
  何も言えなくなったときに、**変更が自分で自分を取り消す道**が要る。この設計が「前の宣言」を
  持つのはその 1 か所だけであり、持つのは窓の長さのあいだだけである。

## 決定

### 記録が宣言を持ち、記録が spec である

ADR 0007 は、適用に regied の状態ディレクトリ下の 2 つめの成果物を持たせ、その中身を挙げた。
リビジョン、出所、時刻、結果、失敗、走ったフェーズ、注記、警告、回線、実行時の値である。
あの記録は**読まれるため**に設計された。この記録はそれを、**収束の対象**にする。
それによって 1 つが変わり、残りは位置づけが変わる。

**記録は宣言そのもの —— 検証されたときのドキュメントのバイト列 —— を持つ。ダイジェストだけ
ではない。**ダイジェストは 2 つの宣言が同じものかどうかを言えるが、描画はできない。
記録を spec とするループは、そこからすべてのバックエンドを描画しなければならないので、
記録は**レンダラに渡せるもの**を持っていなければならない。リビジョンはその隣に残る。
依然としてそのバイト列のダイジェストであり、依然としてホストの外から比較でき（ADR 0007）、
そして今や隣にあるものから自明に導ける。

宣言を保存して安全なのは、ADR 0003 がそう仕組んだからである。宣言は秘密を含めず、秘密を
持つファイルのパスしか持てない。PPPoE の認証情報は、宣言が名指したファイルから、必要になった
瞬間に読まれ、捨てられる（ADR 0004）。**認証情報は記録の中に無く、入りえない。**ループも、
それを必要とする周回で、適用と同じやり方で読む。

**`regied apply` が提出であり、設定ファイルを読むのはそれだけである。**ループも、起動時の
ユニットも、regied が配るどのタイマーも読まない。これは ADR 0007 の「`serve` は設定ファイルを
取らない」をそのまま残したうえで格上げしたものである。あそこではアドレス監視を正直に保つ
手段として論じられたが、**書きかけの編集からルーターが自分を再構成しないための保証の全体**が、
実はこれだったのである。

### 記録は提出時に書かれ、「求められたもの」である

**提出は、検証とステージングを通った時点で受け入れられ、記録はそのとき —— 最初のコマンドが
走る前に —— 書かれる。**その瞬間から、続くコマンドが成功しようとしまいと、その宣言が spec で
ある。`kubectl apply` がやっているのはこれである。spec は admission の時点で保存され、
コントローラがそれをどうしたかは別の話で、status が報告する。

したがって記録は「最後にうまくいった」宣言を決して持たず、2 つ持つことも決して無い。
持つのは**求められたもの**であり、ホストはそこに居るか、そこへ向かう途中か、そこへ到達できずに
いるかのいずれかで、それは周回の状態が言う（後述）。記録の中に「この宣言はかつて通用した」
という保証は無く、要りもしない。前の宣言はバージョン管理にある。ADR 0005 が「1 回の適用より
先に戻ることは、普通のファイルの普通の適用である」と決めたとき、既にそこに置いていた。

spec の隣には、最後の周回が何をしたかの記録 —— ADR 0007 の報告に、周回の状態を足したもの ——
が置かれる。提出だけでなくループも書く。**診断であって 2 つめの spec ではない。**
何もそこへは収束しない。

| 成果物 | いつ書かれるか | 何のためか |
|---|---|---|
| 受け入れられた宣言 | 提出時。検証とステージングを通った時点 | **spec。**ループが収束していく先 |
| 最後の周回の報告 | 言うことが変わったとき | **診断。**リビジョン・出所・結果・失敗・フェーズ・注記・警告、周回が終わった状態、何を待っているか・何に失敗しているか |

報告は中身が変わるときに書かれる。regied が書くすべてのファイルに ADR 0004 が与えた規則と
同じである。そして報告が記録するのは**その状態に入った時刻**であって、最後の周回がそれを
確認した時刻ではない。最後の周回の時刻を持つ報告は、ホストが生きているあいだ毎分書き直されて
何も新しいことを言わない。最後の周回がいつ走ったかは `systemctl status` が答えることである。

ADR 0007 が記録に入れた回線の行は、独立した項目ではなくなる。あれは監視側が YAML を読まずに
「どのリンクが回線か」を知るためにあった。宣言が記録に入るなら、他のすべてと同じく、
そこから導かれる。

**もう 1 つ書いておく価値がある帰結。ADR 0004 が記録するルールセットのテキストは、
ホストが覚えていなければならないものではなくなる。**ADR 0015 が描画されたルールセットを
設定だけの関数にしたので、最後に入れたテキストは、受け入れられた宣言を描画したものと
**厳密に等しい。**導出できるのである。エンジンがそれをキャッシュとして持ち続けるかどうかは
実装の問題であり、この記録が決める必要は無い。ここで決めるのは、
**再起動をまたいで生き残らなければならないのは、受け入れられた宣言 1 つである**ということである。

### 1 周と、それを起こすもの

**1 周（turn）**とは、適用が既にやっていることから「ファイルを読む」を除いたものである。
実行時の値を集め、spec からすべてのバックエンドを描画し、ホストと比べ、違うところを動かし、
違いが要求するコマンドを ADR 0004 の順で走らせる。**収束の実装は 2 つ無い。**ループが通る
経路で、適用が通らないものは 1 つも無い。

1 周を起こすものは 3 つある。

- **提出。**`regied apply` はファイルの中の宣言を検証してステージし、記録に書き、
  自分のプロセスの中でそこへ向けて 1 周を回す。
- **定期の再同期（resync）。**これが床である。ループを「イベント処理系」ではなく
  「修復の機構」にしているのはこれであり、成り立つのは**何も違っていない周回が 1 コマンドも
  走らせない**からである。間隔は常駐プロセスのフラグで、パッケージが配るユニットが与え、
  既定は 1 分 —— 誰かがずれの上に何かを積む前に取り戻せる程度に短く、何もしていないホストが
  数秒おきに 4 つのバックエンドを描画しない程度に長い。これは regied をどう走らせるかの話で
  あってパッケージングであり、宣言が言うことではない（ADR 0002、および ADR 0007 の
  「ユニットはパッケージのもの」の論拠）。
- **カーネルのアドレスイベント。**ADR 0007 が監視側に与えた netlink の購読である。
  セットを直接書く代わりに、1 周を起こす。

最後のものは、機構を増やすのではなく**溶かす。ADR 0015 が挙げた回線セットの 3 つめの書き手は、
もはや独立した書き手ではない。早く起こされたループそのものである。**1 周は既にすべてのセットを
カーネルから播くので、アドレスイベントがやることは「再同期を待たずに周回を起こす」以外に無い。
そういう周回をファイアウォールのフェーズだけに絞るのは、ループの内側の最適化であって、
ここで決めたことを何も変えない。

**ADR 0015 が描画する pppd のフックは残す。意図して畳まない。**あの記録が挙げた 3 つの書き手の
うち 2 つ —— 適用とデーモン —— は、同じものを二度見ていたと分かり、「1 周」に潰れる。
フックは潰れない。**pppd がアドレスを知ったその瞬間にセットへ入れる速い経路**であり、
ループが止まっていても、落ちていても、一度も起動されていなくても効く。
ADR 0015 が「デーモン無しでもホストは正しい」と言ったときに買ったのはその性質であり、
この記録はそれを使い潰さない。**3 つの書き手は 2 つになる。1 周と、その隣のフックである。**

**他には何も監視しない。**regied が所有するファイルへの inotify も、systemd のユニット状態の
購読も、`/proc/sys` の監視も無い。イベント源は、安くてすでに必要なところにだけ足す。
すべてを覆うのは再同期の側である。Kubernetes の informer が resync period を持つのも同じ理由で、
**イベントストリームは遅延の改善であって、決して真実の出所ではない。**

**周回は重ならない。1 つのプロセスの中でも、プロセスをまたいでも。**提出は `apply` の
プロセスで自分の周回を回し、そのとき常駐プロセスも自分の周回を始めようとしているかもしれない。
だから周回は、走っているあいだ状態ディレクトリの下のロックを持ち、もう一方は待つ。
走っている最中に来た tick は、並べて走らせるのではなく遅らせる。

### 誰も見ていない周回に許すこと、許さないこと

**段は行為で分かれているのではない。誰がその周回を求めたかで分かれている。**

**提出された周回（submitted turn）**とは、運用者が求めたものである。`regied apply` と、
期限切れによる巻き戻し —— これは運用者が期限を設定した時点で**あらかじめ求めた**ものである。
ここでは ADR 0004 に書かれたすべてが許され、PPPoE セッションの再起動も含まれる。

**誰も見ていない周回（unattended turn）**とは、再同期やイベントが起こしたものである。
見ている人はおらず、ホストの回線は 1 本しかない。

| 何が違っているか | 誰も見ていない周回 |
|---|---|
| nftables のテーブル、またはその中のセット | 入れ替える。1 トランザクション、ADR 0013 の形、他には何も乱さない |
| カーネルスイッチ | 読んでから書く |
| regied が所有するファイル —— networkd、pppd のオプション、dnsmasq の設定、フック、regied が書くユニット | 書く |
| 宣言されているのに active でないユニット | **バックオフの下で起動する** |
| オプションファイルをいま書き直した、走っているセッション | **報告する。再起動しない** |
| 走ってはいるが、ユニットが上がり続けられずにいるセッション | **報告する。再起動しない** |
| 宣言が既に宣言していないのに走っているもの | **報告する。止めないし、それが走っているユニットを回収もしない** |

**線はここである。誰も見ていない周回は、上がっているものを決して落とさない。**作る・書く・
起動するはする。再起動と停止はしない。**走っていないセッションを起動しても、既に落ちている線を
失うことはありえない。**それは午前 3 時に運用者が処理されていてほしい側である。
上がっているものを再起動することは、1 本しかない線を数秒失う行為であり、その判断は人か、
人が設定した期限のものである。

この線から出てくる 2 つの帰結は、ループが**分かったうえで途中で止まる**場所なので、
書いておく価値がある。

- **走っているプロセスの下でファイルを書き直すのは、周回が半分しか解決しない差である。**
  誰かが pppd のオプションファイルを編集していたなら、周回は regied の内容を戻すが、
  走っているセッションは起動時に読んだもので走り続ける。周回はそう報告する。セッションが
  そのファイルを読むのは、次に起動されたとき —— 運用者の手か、クラッシュ後の systemd —— である。
- **走っているものがあるあいだ、ユニットは回収されない。**ADR 0004 は、ユニットの削除を、
  それを経由する停止の**後ろ**に置いている。誰も見ていない周回は停止をしないので、削除もしない。
  報告し、次の提出された周回が両方を正しい順序で行う。

networkd の reload は線の安全な側にあり、そこに留まる。ADR 0004 が既に「reload であって
restart ではない」と決めており、pppd が上げたセッションの上で reload を安全にしているのは
`KeepConfiguration=yes` である。networkd の restart は、どの周回もしない。

誰も見ていない周回に許された行為のうち、素のファイル書き込みでないものはすべてバックオフの
下にある。それは後の節で述べる。

### 1 周は描画できるものだけを描画し、残りは後の周で届く

ADR 0004 はステージング段に「適用時にしか存在しない値」の集まりを与えた。AFTR 名が解決する
アドレス、DUID ファイルの中身、各回線のリンクが持っているアドレス、PPPoE の 2 つの認証情報である。
そしてそれぞれについて、無いことが致命的かどうかを 1 つずつ決めなければならなかった。
**試行が 1 回きりなら難しい問いである。ループがあるなら、ほとんどの場合そもそも問いではない。
いま無い値はいま無いだけであり、1 分後にまた 1 周が来る。**

| 実行時の値 | 1 回きりの適用では | ループでは |
|---|---|---|
| 回線のアドレス | ADR 0015 がルールセットから外してセットに置いた | **セットをカーネルから播くこと自体が 1 周の仕事**である。既に level-triggered で、既に反復されている |
| AFTR 名が解決するアドレス | 適用時に名前解決する。DNS が上がっていない起動直後は適用の失敗になる | トンネルを出さず、名前が解決した周で出す |
| DUID | 適用時に読む。読めなければ描画を止める。さもないと networkd が自分の識別子を送り、委譲される prefix が黙って変わる | prefix 委譲を出さず、**既にホストに在るものはそのままにする。**ファイルが読めた周で拾う |
| PPPoE の認証情報 | 読み、使い、捨てる | 変わらない。必要とする毎周回で同じ規則が働く |

これは ADR 0006 が `regied render` に定めた規則 —— **与えられなかった値に依存するものは、
適用が省くのと同じように省く** —— を、エンジンの普段のやり方に変えたものである。
半分は既にエンジンに在り、**残り半分を安全にしているのがループである。**
省いたものが落ち着くのは、誰かがそれを取りに戻ってくる場合だけだからである。

**省くのは、その値に依存する成果物まるごとである。そして既にホストに在るものには手を付けない。**
ここが間違えやすいところであり、ADR 0004 の DUID の論拠がそれを示す事例である。
**DUID 無しで書いた prefix 委譲は、その小さい版ではない。別の設定である** —— networkd が自分の
識別子を送り、prefix が黙って変わる設定である。だから、ある成果物を計算できなかった周回は、
劣化版を書かない。**そして、前の周回が書いたものを回収もしない。**足りないものをループが待つあいだ、
ホストは最後に与えられた完全なものを持ち続ける。
**「不完全」を、書きかけのファイルで綴ってはならない。**

### どの周回も、安全な状態で終わる

不完全であることは許される。**安全でないことは許されない。**そしてこの違いは程度の問題ではない。
**ファイアウォールが無いまま線だけ上がる周回が、あってはならない。**

ここでの「安全」は露出の話であって、可用性の話ではない。周回は線が落ちたまま終わってよい ——
上がらなかったセッション、まだ描画されていないトンネル。それは待機か失敗のホストであり、
そう言う。周回が終わってはならないのは、前にフィルタの無いままパケットを転送しているホストや、
宣言したことのない設定を持っているホストである。

**ADR 0004 のフェーズ順序は、1 周の中で保たれる。選ばれたときの理由のままに。**
ファイアウォールが最初なのは、パケットを動かせるものが、それを濾すルールより先に存在しては
ならないからであり、転送はその次のフェーズで有効になる。ループが足すのは、
**周回が途中で止まりうる**という条件である —— 失敗で、バックオフで、運用者が daemon を止めることで。
**しかも、走った半分を後から取り消しに来るものは無い。**だから順序は以前より厳しく読まれなければ
ならない。**周回の任意の途中経過が安全な状態でなければならず、「全部走り切った状態」だけでは
足りない。**ADR 0004 が選んだ順序は既にその性質を持っており、この記録はそれを
**幸運な帰結ではなく要件として**固定する。

**周をまたいで持ち越してよいのは「完全さ」であって、「順序」ではない。**描画できなかった
トンネルは次の周を待てばよい。テーブルを入れる前に転送を有効にすることは、先送りできない。
**先送りすることが、順序がまさに塞いでいる窓だからである。**

これは上の段の話を裏から見たものである。**段は、線を失いうる行為を誰が取ってよいかを言う。
順序は、1 周の中で、守る仕事が守られる仕事より先に来ることを言う。**どちらも回線が 1 本だから
存在し、どちらも他方の代わりにはならない。

### 収束したのか、何かを待っているのか

**辿り着いたホストと、詰まったホストが、同じに見えてはならない。**意図的にものを省く周回を持ち、
しかも終わらなかった提出を戻すものが無い以上、「最後の周回は走って、何も変えなかった」は、
以前と同じ意味を持たない。そこで周回は 3 つの状態のいずれかで終わり、どれであるかを言う。

| 状態 | 意味 |
|---|---|
| 収束済み（converged） | ホストは宣言をまるごと持っている。省いたものも、再試行中のものも無い |
| 待機（waiting） | できることはすべて行い、実行時の値が無いために何かを省いている。**何を待っているかを名指しする** |
| 失敗（failing） | 試して、うまくいかなかった。あるいは、違っているのにこの周回には直すことが許されていない。バックオフの下にあるか、人を待っている。**何が、なぜかを名指しする** |

**名指しすることが要点である。***AFTR 名の解決と DUID ファイルを待っている*は診断であり、
*収束していない*は気分である。Kubernetes のコントローラなら status の condition に入れるところで、
regied には API が無いので、持っている 2 か所 —— 最後の周回の報告と journal —— に出す。

**「何も変えなかった」は、この 3 状態に照らして読まれなければならない。**冪等なエンジンは
たいてい「変更なし」と答え、それは健全な答えである（ADR 0006）。**同じ言葉が、1 時間同じ名前を
待ち続けている周回から出たなら、意味はまったく別である。**その違いは、誰かが推論しなくても
見えていなければならない。

**提出も同じ 3 状態で報告し、終了ステータスはそれに従う。**周回が失敗で終わった適用は非 0 で
終わり、何が失敗したかを言う。待機で終わった適用は 0 で終わり、何を待っているかを言う。
待機は起動したばかりのホストの普段の状態であって、提出の欠陥ではないからである。

### 戻すのは人だけである

**ロールバックは無い。**ステップごとにも無いし、前の宣言へ向かう収束としても無い。周回が途中で
失敗した提出は、記録に提出された宣言を残し、ホストにできたところまでを残し、ループが残りへ向けて
バックオフの下で働き続ける。**戻るのは、人が前のファイルを適用することである。**ファイルは
バージョン管理にあり、`regied apply` で当てる —— 普通の宣言の普通の提出であり、ADR 0005 が
「1 回の適用より先に戻るとはこれだ」と既に書いたものである。

理由はユーザーのものであり、そして持ちこたえる。

- **人がそこに居る。**提出は誰かが打ったコマンドであり、失敗は同じ秒にその人のコンソールに、
  ADR 0005 と ADR 0006 が既に選んだ言葉で届く。その人は自分が何を変えたばかりかを知っている。
  もう一度試すのか、ファイルを直すのか、戻るのかについて、**ホストの上のどれよりもその人が
  よく知っている** —— そして 1 つのコマンドの失敗を証拠に「戻る」と決める機械は、その失敗が
  一過性だったときは必ず間違える。
- **ループの下では、「失敗」はたいてい「まだ」である。**上の節は、後で拾うためにものを省く
  周回を持っている。答えないリゾルバ、起動に 1 秒余計にかかったユニット。自動の巻き戻しは、
  1 分後に収束していたはずの宣言を取り消し、しかも提出された周回の全権限で —— 途中でセッションを
  再起動しながら —— そうする。
- **2 つではなく 1 つの機構。**いまエンジンの各ステップは自分の逆操作を持っており、その逆操作の
  集まりは系の中で最も実行されないコードでありながら、何かが既に壊れたときにだけ通る。
  それは消え、何も置き換える必要が無い。すべてのホストで毎分走る経路が仕事を終わらせ、
  人が対象を変える。
- **巻き戻しはただではない。**前の宣言へ戻る収束も他と同じ 1 周であり、同じフェーズを持ち、
  いま再起動したばかりのセッションをもう一度再起動しうる。それを手でやろうとしている運用者は、
  線が上がっているかを見て、タイミングを選べる。機構には選べない。

**ループが自分で終わらせる範囲は、前の節で線が引かれている。**失敗した提出の後、ループは
足りないものを書き、テーブルを入れ替え、宣言されているのに走っていないものを起動する ——
そして許されていないことを報告する。古いオプションで走っているセッションの再起動、もう宣言されて
いないものの停止。それらは人を待ち、頼み方は同じ `regied apply` をもう一度打つことである。
適用は冪等なので（ADR 0004）、打ち直せば残っている段だけを行い、他には何もしない。
**提出のうちループにできない半分の再試行は、提出そのものである。**

**変わらないことが 3 つある。**いずれも ADR 0005 から引き継いだものである。

- **前のファイルを適用しても、起きた出来事は無かったことにならない。**再起動されたセッションは
  新しいセッションである。新しい設定の下で dnsmasq が配ったリースは配られたままである。
  新しいルールセットが落とした接続は落ちたままである。networkd が外したアドレスは外された。
- **途中の失敗は、そのままの姿で報告される。**ADR 0005 の扱いは、undo を抜いた形で生き残る。
  失敗した段で止まり、いまホストが何を動かしているかを述べ、非 0 で終わる。回線が 1 本の
  ホストでは、正確な記述のほうが reload の輪よりましである。
- **前の宣言は、regied が所有したことのないものを戻せない。**ある宣言が設定したカーネルスイッチを
  次の宣言が言わなくなったとき、前のファイルを適用しても、regied を入れる前にホストが持っていた
  値までは戻らない。**これは ADR 0009 の所有の問いであり —— 印を持たない状態にとって回収とは
  何か —— この記録が生んだものではなく、先に在ったものである。**

ホストでの最初の提出には戻る先が無く、要りもしない。すべてを引き取る宣言とは空の宣言であり、
それを適用することが ADR 0009 の回収である。概念は既に在り、そしてループはそれを勝手にはしない。

### 周回が収束できないとき

**扱いは Kubernetes と同じである。ループでも提出でも、再試行し、バックオフし、報告する。**
求められた宣言に到達できないことは、報告して再試行する条件であって、別のどこかへ飛ぶ理由では
ない。そもそも記録の中に、飛ぶ先は無い。

バックオフは、洗練ではなく要件である。

- **対象ごとに持つ。全体で 1 つではない。**起動しない dnsmasq が、テーブルの修復を止めては
  ならない。
- **駆動するのは「差が消えなかった試み」であって、コマンドの終了ステータスではない。**
  起動してすぐ死ぬユニットは、起動した側には成功を返す。フラッピングとはまさにその形であり、
  終了ステータスを数えると取り逃がす。
- **上限つきの指数バックオフ。差が消えたらリセットする。**増え方より上限が効く。事業者が
  1 時間落ちているホストが、その 1 時間をコマンド発行に費やしてはならない。
- **提出された周回はレート制限されず、バックオフをリセットする。**運用者が求めており、
  その人はそこに居る。

周回の安い側 —— 描画し、ホストを読み、比べる —— は常に走る。**バックオフが抑えるのはコマンドで
あって比較ではない。**だから再試行が遅くなっても、何が壊れているかの報告は最新のままである。

### 期限つきで適用する

これが締め出しへの答えであり、運用者が EdgeOS / VyOS の `commit-confirm`、
JunOS の `commit confirmed` で既に形を知っている仕組みである。そして**「記録は提出時に書く」の
唯一の例外**であり、前の宣言が保たれる唯一の場所である —— 窓の長さのあいだだけ、それ以上は無い。

**`regied apply --confirm <時間>` は適用し、そのうえで「うまくいった」と告げられるのを待つ。**

| 段階 | 何が起きるか |
|---|---|
| 提出 | 他の提出と同じく検証しステージする。**記録は書かない。**宣言は「試行（trial）」として常駐プロセスに渡り、提出された周回がそこへ向けて走る |
| その周回が何を達成したにせよ | 時計が回り始める。待機で終わった周回でも、失敗で終わった周回でも同じである —— それを見るのが運用者がそこに居る理由であり、居なかったときを覆うのが時計である |
| 時計が回っているあいだ | ループの spec は試行である。周回はそこへ収束する。普段どおりに。2 度目の `--confirm` は試行を置き換え、記録には触れない |
| `regied confirm` | 試行が記録に書かれ、spec になる。時計は止まる |
| `regied cancel` | 試行は捨てられ、1 周がただちに記録 —— 前の宣言 —— へ収束する |
| 時計が切れたとき | cancel と同じ。ただし誰もそこに居なくてよい |

**2 つのうちどちらが一時的なのか。そしてなぜ試行のほうなのか。**記録は前の宣言を持ち続け、
常駐プロセスが試行をメモリに抱える。逆ではない。プロセスを失うあらゆる筋が、前の宣言の側へ
解決しなければならないからである。締め出された運用者はルーターの電源を入れ直す。試行が記録に
あって前の宣言がメモリにあれば、再起動は締め出しを持ち帰り、それを取り消すものは何も残らない。
前の宣言が記録にあれば、試行の最中に死んだ daemon は起き上がり、記録を見つけ、そこへ収束する ——
**期限切れが早く来ただけであり、向きは安全な側である。再起動を生き延びる試行は、誰も時間を
計っていない試行である。**

**試行は周回がどの状態にあっても確定でき、周回が何を達成したかを理由に確認が拒まれることは
ない。**期限が試しているのは 1 つ —— **運用者がまだホストに届くか** —— であり、確認はそれへの
答えであって、他の何への答えでもない。先に収束を要求すれば、この仕組みは**対象ではない場合に
発動する。**上流の DNS が遅くて AFTR 名を待っているだけの宣言が確認できなくなり、
**運用者がそこに居るのに期限切れで巻き戻る。**

代わりに daemon がするのは、**何を確定しようとしているかを言うこと**である。リビジョンと、
最後の周回の状態を返す。だから、まだ 2 つの成果物を待っている宣言や、1 つ失敗している宣言を
確定するときも、**事故ではなく承知のうえで**そうすることになる。収束を見てから確定したい運用者は、
単にまだ確定しなければよい。**期限は運用者自身の確認のための持ち時間であり、
その使い方は運用者のものである。**

**巻き戻しは提出された周回である。**ADR 0004 のすべてが使え、セッションの再起動も含まれる。
運用者が期限を設定した時点でそれを求めたからである。**この仕組みに価値があるのはここである** ——
運用者を締め出した変更こそ、まるごと取り消さなければならない変更であることが多い。
これはこの設計の中で**唯一の自動の巻き戻し**であり、ここでだけ許され他では許されない理由は、
前の節が他で拒んだ理由そのものである。**人がそこに居ない。**前の節が運用者に委ねたこと ——
失敗が一過性かの判断、タイミングの選択 —— は、締め出された運用者にはまさにできないことである。

**常駐プロセスが動いていないとき、`--confirm` 付きの適用は拒否される。**期限がこの約束の全部で
あり、時計を持つ者が居ないからである。黙って受け付けることは、誰かがそれに頼っているまさに
その瞬間につく嘘になる。拒否は代わりに何をすべきかを言う。regied を起動するか、`--confirm`
無しで適用して「何も取り消されない」ことを受け入れるか、である。代案 —— `apply` のプロセスが
時計を持つ何かを fork する —— は検討して退けた。運用者の ssh セッションより長生きしなければ
ならないものは、定義上 daemon であり、regied が自分のプロセスを監督しないことは ADR 0004 が
既に決めている。

2 つの verb は、`/run` の下の regied 自身のディレクトリに置かれた制御ソケット越しに daemon へ
届く。ファイルシステムのモードを持つ。ADR 0007 がソケットについて述べたとおりであり、理由も
同じである —— **ソケットはネットワークから届かない。**ポートを守るはずのファイアウォールを、
そのポートの向こうに居るものが入れている状況では、これは普段以上に効く。他に 2 つの経路を
量った。シグナルは、どの試行のことかを運べず、何を確定したかを返せない。daemon が見に行く
ファイルは、確認を tick まで待たせるうえ、**人と同じくらい容易にスケジュール実行が書ける唯一の
経路**である。ソケットは同期して答え、人が打つコマンドが書く。

**これは HTTP API ではなく、それを復活させない。**ソケットが運ぶのは 2 つの verb だけである。
apply のエンドポイントも、dry-run のエンドポイントも、status のエンドポイントも無い。
ADR 0007 の読み取り専用 API は保留のまま、未実装のままである。ADR 0007 が書き込みの口を
断ったのは 2 つの根拠によるが、**どちらもここで満たされている。**あそこが晒すことを拒んだ
鋭い行為は `apply` であり、それは依然として晒されていない。2 つめの根拠 ——
「ホスト上で `regied` を走らせられる者に対して、エンドポイントは何の能力も足さない」 ——
は、ソケット越しの確認が受け入れられる理由そのものである。

形から従う細部:

- **`--confirm` は既定ではなく、明示的に選ぶものである。**起動時のユニットにも、誰も見ていない
  適用にも、確認する者が居ない。誰も見ていないホストで期限切れが起きる既定は、
  問題なかった変更を毎回巻き戻す。
- **試行中の素の適用は、試行を終わらせる。**提出時に自分の宣言を記録に書くからである。
  以後、前の宣言はどこにも無く、時計も無い。それは**網を持たないことを運用者が選んだ**という
  ことであり、最初から `--confirm` を付けないのと同じ選択である。コマンドはそう言う。
- **`regied confirm` はリビジョンを名指さない。**試行は多くとも 1 つしか存在せず、
  daemon がどのリビジョンを確定したかを答える。

**この仕組みが依って立ち、regied には強制できない条件。確認は、締め出しが壊すのと同じ経路を
通らなければならない。**別の経路で確認が届くよう仕込んだ運用者 —— 一定時間待ってから確認する
スケジュール実行、シリアルコンソール上のスクリプト —— は、自分で仕組みを解除している。
**試されているのは設定ではなく、運用者がまだホストに届くかどうか**だからである。
変更の影響を受けないコンソールから作業している人は、そもそもこの失敗の危険に晒されておらず、
この仕組みを必要としない。**あってはならないのは、そういう経路から確認しておいて、
ネットワーク経路が試されたと信じることである。**

### 止める操作は 1 つで、止めても何も壊れない

**`systemctl stop regied` は収束を止め、他には何もしない。**ファイルは回収されず、テーブルも
外されず、セッションも止められず、スイッチも戻されない。ホストはいま載っているもので走り続ける。
**止まるのは収束であって、設定ではない。**

これが「障害のさなか、運用者が nftables を手で直し、その手直しがそのまま効いていてほしい」という
要件である。ループが走っていれば再同期の間隔のうちに巻き戻される。**daemon を止めることが
「いまは放っておけ」と言う手段になる。**もう一度起動すれば収束が再開し、手直しは巻き戻される ——
そしてそれが正しい振る舞いである。明示され、運用者の手の内に置かれた形で。

**したがって、ループは常駐プロセスの中だけに置き、パッケージは `regied apply` を走らせるタイマーを
配らない。**この停止レバーの価値は、**それが 1 つしか無い**ことにある。機構が 2 つあれば止めるものが
2 つになり、忘れられるほうが、いちばん悪いときに走る。しかもタイマーはそれ自身の理屈でも
間違った機構である。**設定ファイルを読んでしまう**からであり、それはこの決定の最初の節が
塞いだ危険そのものである。

ADR 0004 の「適用はタイマーから走らせても安全である」は依然として真であり、依然として持つ価値が
ある —— それは冪等性の性質であって計画ではない —— ので、そういうタイマーを置きたい運用者は、
それがファイルを読むと知ったうえで置ける。

試行の最中に daemon を止めることは、運用者が時計を自分で持つと選ぶことである。試行はプロセスと
ともに死に、次に周回を回すもの —— 起動し直した daemon か、起動時のユニット —— は記録、
すなわち前の宣言へ収束する。向きとして安全であり、試行の最中に daemon を止める運用者は
それを予期すべきである。

停止レバーは README の障害時手順に載る。手で触る前に止め、終わったら開始する。それを書くのは
運用手順を書く単位であって、この記録ではない。

### 起動時。そして、もうファイルを読むものは無い

ADR 0007 はユニットを 2 つと決め、起動時の適用は単独で立つと論じた。ルールセットはカーネルの
状態なので、再起動のたびに誰かが入れなければならず、その誰かはファイルではなく適用である、と。
**そのすべてが生き残る。変わるのは、それが何を読むかである。**

| ユニット | 何を走らせるか | 入力 |
|---|---|---|
| 起動時のユニット | 1 周だけ回して終了する | 記録 |
| 常駐プロセス | ループ | 記録 |

`/etc/regied/config.yaml` を読む起動時の適用は、ループが避けているのと同じ危険を
**次の再起動まで先送りしただけ**である。ファイルに書きかけで残った編集が、次に電源が落ちた
ときにホストの設定になる。記録を読むならそれが塞がる。
**この記録の後、regied の中で設定ファイルを読む自動の機構は 1 つも無い。**

`regied reconcile` がその 1 周の名前である。記録へ収束して終了し、失敗で終わったなら非 0 で終わる。
起動時のユニットのコマンドであり、人が「ホストをあるべき場所に戻せ」と言うとき —— 何も提出せずに ——
打つものでもある。3 つめの verb だが、**ファイルを読まない周回を頼む唯一の方法**であることで
その席に値する。

常駐プロセスも起き上がる途中で同じ周回を回すのに、起動時のユニットを別に残す理由は 2 つある。
**停止レバーは無効化のレバーでもある** —— 障害のあいだ daemon を切っていた運用者が再起動しても、
再起動後にはファイアウォールが要る。そして、一度走って終了するユニットは「ホストが設定された」
という定まった時点を起動に与えるが、走り続ける daemon はそれを与えない。

ADR 0007 が決めた順序は変わらない。両ユニットとも `systemd-networkd` の後、どちらも
`network-online.target` の前には置かない。常駐プロセスは起動時のユニットの後だが、それを
`Requires` しない。ディストリビューションの `nftables.service` がルールセットを flush することへの
ガードもそのままである。**常駐プロセスが起動時のユニットを必要としてはならない理由は、
ここでいっそう強くなる。**起動時の周回が失敗したときこそ、ループの再試行が欲しいときだからである。

**記録が無いホストは、何もせず、そう言う。**空の宣言へ収束するのではない。regied が所有する
すべてを回収すること —— 動いているルーターからファイアウォールを外すこと —— は、ファイルが 1 つ
無いことへの妥当な応答ではない。記録を見つけられない周回は、ホストがいまの姿になった経緯に
ついて何も知らない。そして、すべてを引き取る唯一の宣言は、人が意図して提出するものである。

**記録がもう検証を通らないときも、何もせず、そう言う。**これは regied を更新し、検証が、
古い版で受け入れられた宣言より厳しくなった場合である。半分しか理解できていない宣言へ収束するのは
収束しないより悪く、空へ収束するのはさらに悪い。周回は報告し、ホストは動いているものを動かし
続ける。**運用者の手元には、動いているルーターと、新しい版が受け入れる宣言を出せというメッセージが
残る。**

### ループに見えるもの、見えないもの

**ループに見えるのは、宣言と、regied が読めるものとの差だけである。**ファイル、カーネル
スイッチ、自分のテーブルとその中のセット、自分が宣言したユニットが enable されていて active か。
一覧はこれで全部である。

**健全性は差ではない。**pppd は走っているのに認証が通らない、セッションは上がっているのに出口の
経路が無い、DNS フォワーダが失敗しか返さない —— どれも、宣言は「セッションが在る」と言い、
実際に在る。**見つけるべき差が無い。**それらを報告するには別の観測が要り、そこには方針が付く ——
どれだけ経てば長すぎるのか、何をもって到達可能とするのか。そして行為が付く。回線が 1 本の
ルーターでそれは張り直しであり、**この記録がいま、ループが自分の判断で行ってはならないと決めた
唯一の行為である。**

だから線はここに引く。**宣言されていて active でないユニットは差であり、宣言されていて active な
ユニットは、中で何が起きていようと spec のとおりである。**この線は新しい観測を要求しない ——
systemd が既に答える —— し、方針も要求しない。

**これは落ちた線を放置するという意味ではない。**落ちたセッションは pppd 自身の `persist` と
LCP エコー（ADR 0014）、そして systemd の `Restart=`（ADR 0004）で戻ってくる。プロセスの監督は
systemd のものであり、最初からそうだった。ADR 0008 を一段上でやっているだけである。
作らないのは、**トラフィックが流れなくなったら張り直す到達性のウォッチドッグ**である。
それは本当に欲しくなりうるものであり、別の記録であり、書かれる前に上の問いに答えなければ
ならない（ADR 0002。撤回しにくいインターフェースとは、誰も必要としないうちに足されたものである）。

宣言の**一部**を描画できない周回は、上で決めたとおり、その部分を省いて待つ。
宣言の**全部**を描画できない周回 —— 受け入れられた宣言がもう parse できない、あるいはもう検証を
通らない —— は何も変えずに報告する。それは ADR 0004 のステージング段が既にやっていることである。
**最初のコマンドの前の失敗は何のコストも生まない。**

### 収束の失敗はどこに現れるか

HTTP API は無い。現れる場所は次のとおりである。

- **常駐プロセスのユニットの下、journal。**運用者が見るのは `systemctl status` と `journalctl`
  であり、ループを systemd のサービスにしているのは、まさにそれらが効くようにするためである。
- **個々の差は、現れたときと消えたときに記録される。**バックオフの段が上がったときも記録する。
  **毎周回ではない。**tick ごとに書くループは誰も読まないループであり、これは 1 分ごとに永遠に
  tick する。**状態の変化 —— 収束済み・待機・失敗 —— は変わるたびに記録され**、
  何を待っているか、何が失敗したかを伴う。規則は同じである。
- **最後の周回の報告。**言うことが変わるときに書き直されるので、daemon を再起動しても何が
  起きたかを失わない。
- **`regied apply` のコンソールと終了ステータス。**提出が回した周回について。
- **`regied reconcile` は周回が失敗で終われば非 0 で終わる。**起動時のユニットの失敗が systemd に
  届くのはこれによる。

**常駐プロセスは、収束できないことを理由に終了しない。**差があると死ぬ daemon は、その差を
報告する当のものを取り去り、ルーターの上で systemd に再起動の輪を渡す。上がったまま、比べ続け、
バックオフの下で再試行し続け、何が壊れているかを言い続ける。

## 採らなかった選択肢

**`regied apply` を走らせるタイマー。**考えうる最も安いループであり、この設計はここから始まった。
2 重に退けられる。**設定ファイルを読むので、書きかけの編集が、誰も居ないところで定期的に
ホストに載る。**そして収束を daemon 以外の場所に置くので、**要件が「1 つであること」を求めている
停止操作が 2 つになる。**

**ループに設定ファイルを読ませる。**より単純である。記録も要らず、提出という段も要らない。
だが**この設計全体が載っている性質** —— ホストは人が提出したものへしか動かされない ——
を手放す。しかも spec が、誰も「変えた」と決めていないのに変わる。**継続的な調整について人が
恐れる失敗の形はまさにこれであり、その恐れは正しい。**

**記録を「収束した周回のときだけ」書き、常に「最後にうまくいった宣言」にしておき、失敗した
提出は自動でそこへ戻す。**これはこの設計が草稿の大半のあいだ持っていた形であり、ユーザーの
3 つめの指摘が取り除いたものである。安全に見えるが、実は 2 つのことを同時にしている。
**1 つのコマンドの失敗を証拠に宣言を「悪い」と判定する機械** —— ループが「失敗」を「まだ」に
変えたまさにその時点で —— と、**提出が走っているあいだ必ずどこかに抱えていなければならない
2 つめの宣言**である。後者は「望ましいもの」と「最後にうまくいったもの」の対を裏口から戻す。
これが守ろうとするもの —— 提出した本人が戻れなくなること —— は起きない。**起きるのは
ホストに届かなくなった場合だけであり、その場合には固有の仕組みがある。**

**永続する記録を 2 つ持つ。望ましい宣言と、最後にうまくいった宣言。**同じ理由に加えて、もう 1 つ
の理由で退ける。あらゆる経路で、どちらが正であるかを何かが決めなければならず、
**1 か所でも間違えれば、一度も通用しなかった宣言へ巻き戻す。**

**ステップごとの undo をループと並べて残す。**1 つの仕事に 2 つの機構であり、しかも使われないほうが
障害のときに走るほうである。undo はループができるまで残し、そのあと消す。それは順序であって
設計ではない。

**`--confirm` を既定にする。**人が頼み忘れる場所に安全網を置くことになる。退ける理由は、
起動時の周回にも、誰も見ていない適用にも、確認する者が居ないからであり、
**誰も見ていないホストで切れる期限は、問題なかった変更を巻き戻す。**

**試行を記録に置き、前の宣言をメモリに抱える** —— 決めたのと逆の向き。「記録は提出時に書く」を
例外無しに保てる。退けるのは、試行の最中の再起動 —— 締め出された運用者がルーターにすることは
それである —— が試行を持ち帰り、それを取り消すものが何も残らないからである。

**帯域外の経路で確認を届ける** —— シリアルコンソールから、2 本目の回線から。**退けない。**
その位置に居る運用者は、この仕組みが対象とする失敗の危険にそもそも晒されていない。
ここに挙げたのは、**そういう経路から確認しておきながらネットワーク経路が試されたと信じることが、
誰にも気づかれずに仕組みを無効化する形だから**である。

**締め出しを直接検出する** —— 到達性を測る、あるいはルールセットを解析して運用者自身の経路が
残っているかを判定する。コストではなく原理で退ける。**宣言とホストを比べる機構はどれも、
宣言が間違っている場合に対して盲目である。**そして到達性の測定は運用者がどの経路に居るかを
知らなければならないが、regied はそれを知らないし、推測すべきでもない。**期限の仕組みが効くのは、
運用者自身の到達性をそのまま試験に使い、それをモデル化せずに済ませているからである。**

**実行時の値が無ければ適用を失敗させる、という ADR 0004 の扱いを残す。**試行が 1 回きりで
やり直しが無いなら、それが正しい答えである。代案は DUID 無しの prefix 委譲を書くことであり、
それは prefix を黙って変える。ループがあると答えが変わるが、**変わる理由は 2 つだけである。**
省くのが成果物まるごとの単位であること、そして誰かがそれを取りに戻ってくることである。
周回を失敗させるほうを採れば、**名前解決がまだ上がっていない起動が「起動時の周回の失敗」で
終わる。**1 分後にトンネルが出てくるのではなく。

**ADR 0015 の pppd フックを、ループができるようになったのだからループに畳む。**退ける。
**あれはループが走っていないときに効く経路**であり、あの記録が買ったのはその性質である。
**daemon が生きているあいだしか正しくない機構**は、両方の記録が避け続けてきたものである。

**すべての成果物をイベントで監視する** —— ファイルへの inotify、systemd の購読。
**正しさを損なう遅延改善**として退ける。信じられたイベントストリームは真実の出所になり、
イベントストリームは取りこぼす。再同期がすべてを覆っており、残す購読は
ADR 0015 が既に必要としていた 1 つだけである。

## 帰結

- **途中で失敗した提出は、人が動くまで失敗したままである。**これは自動の巻き戻しを持たない
  代償であり、本物である。pppd が拒むオプションでセッションを再起動する宣言は、運用者が前の
  ファイルを適用するかこのファイルを直すまで、線を落としたままにする。ループはバックオフの下で
  セッションを起動し続け、なぜ上がり続けないかを言い続けるが、**対象は変えない。**この代償を
  受け入れられるのは、提出が人の打つコマンドだからである。失敗したときその人はコンソールの前に
  居て、前のファイルはバージョン管理にあり、それを `regied apply` するのは 1 コマンドである。
  **その人が動けない場合とは締め出しであり、その場合には期限がある。**
- **系の中で最もテストされない経路が消え、何も置き換える必要が無い。**復旧は、自前の逆操作を
  持つ独立した機構であることをやめる。提出を終わらせるのはすべてのホストで毎分走るループであり、
  対象を変えるのは人である。
- **ループはホストを、人が提出したものへしか動かせない。**ファイルへの編集がどれだけ壊れて
  いようと、どれだけ書きかけであろうと、提出を経ずにホストへ届くことはない。
  **これは覚えておくべき規則ではなく、構造上の性質である。**
- **この記録の後、regied の中で設定ファイルを読む自動のものは 1 つも無い。**ループも、
  起動時のユニットも、regied が配るどのタイマーも。
- **受け入れられた宣言が、生き残らなければならない唯一の状態になる。**ADR 0004 が記録していた
  ルールセットのテキストはそこから導ける。そして**記録を失ったホストは自分を再構成しない。**
  報告して走り続ける。向きとして安全であり、直接テストする価値がある。
- **daemon が止まっている状態は、劣化ではなくサポートされた状態である。**ホストはいま載っている
  もので走り続け、手直しは残り、daemon を起動すれば収束が再開して手直しを巻き戻す。
  障害時に運用者がやることは、1 回の停止と 1 回の開始で括られる。
- **締め出しへの保護は常駐プロセスを要求し、それを求めたその瞬間にそう言う。**daemon が止まって
  いるホストでも適用はできる。できないのは期限つきの適用だけであり、
  **そう信じたまま進むことを許さずに理由を告げる。**
- **試行の最中に死んだ daemon は、起き上がる途中で巻き戻す。**試行は設計上一時的であり、
  前の宣言のほうが永続する側なので、daemon を失うあらゆる筋 —— クラッシュ、停止、電源の
  入れ直し —— が、**試行の前に効いていた宣言の方向へ**解決する。
- **ステージング段は大きくならず、単純になる。**ADR 0004 は実行時の値ごとに個別の判断を
  下さなければならなかった。無いことが致命的か、永久に無視してよいかの二択だったからである。
  ループの下では一般解が「その成果物を省いて待つ」になり、残る判断は**タイミングではなく
  正しさについてのもの**だけになる。
- **「変更なし」に 2 つ目の読みが生まれ、それを分けるのが 3 状態である。**収束したホストと、
  起動以来ずっと同じ名前を待っているホストは、どちらも毎周回で何も変えない。
  収束について報告するもの —— journal の行、報告、将来の readiness の答え —— は、
  **差分だけでなく状態を運ばなければならない。**
- **ループはエンジンと同じようにユニットテストできる。**ループがエンジンだからである。
  ファイルシステム・コマンドランナー・名前解決・リンクの読み手を差し替える同じインターフェース
  （ADR 0004）がそのまま効き、新しく加わるのは時計とロックだけである。`make test` は純粋なままである。
- **「このホストは何であるはずなのか」への答えはちょうど 1 つ**であり、それは人が読める
  ファイルであり、**かつて通用したものではなく、求められたものを言う。**ホストがそこに居るかは
  別の問いであり、報告が答える。
- **ADR 0007 の HTTP API は依然として保留であり、いっそう急がなくなった。**API が答えるはずだった
  2 つの問い —— 何が効いているか、何が失敗したか —— の後ろに、journal と報告があるからである。
  API が足すのはそれらへの遠隔からのアクセスであり、それは以前からそうだったし、
  依然として誰も求めていない。
- **この記録は、ADR 0007 が名指しした方向を塞がない。**カーネル以外の出所から来る実行時の状態 ——
  あの段落を書かせた例で言えば、ロードバランスされたアドレスの背後にある健全なバックエンド ——
  は、このループが、同じ場所に書くことになる。描画されるテキストは設定だけの関数のままである。
  **あそこに添えられた警告はそのまま、一語も変えずにここにも当てはまる。**回線のセットが安全なのは
  カーネルが答えを持っているからであり、出所がカーネルでない要素には、テーブルを入れ替えた
  ときの復旧が無い。

## この記録が置き換えるもの

- **[ADR 0005](0005-apply-rollback.md) を supersede する。**ステップごとに逆操作を持つ独立した
  機構としてのロールバックは消え、**自動のものは何も代わりに入らない。**ループは許された範囲を
  終わらせ、人が対象を変える。ADR 0005 が「そもそも戻せない」と書いたこと —— 再起動された
  セッション、配られてしまったリース、落とされてしまった接続 —— はそのまま生き残り、上で言い直して
  ある。**それは機構の性質ではなくホストの性質だからである。**そして同記録の最後の節 ——
  戻ることはバージョン管理にある古いファイルの普通の適用である —— は、例外であることをやめて
  **答えの全体になる。コードはループの実装時に削除された。**
- **[ADR 0007](0007-resident-process.md) のデーモンの半分を supersede する。**
  「常駐プロセスは決して適用しない」は覆る。**収束することが、それが存在する理由になる。**
  「設定ファイルを取らない」は保たれるだけでなく、設計の中心に格上げされる。あの記録が設計した
  記録は、受け入れられた宣言を得て、提出時に書かれ、周回の状態を運ぶ。**HTTP API とそのエンドポイント、
  および API の輸送路としてのソケットは保留のままであり**、ここの制御ソケットが運ぶのは
  2 つの verb だけである。
- **[ADR 0004](0004-apply-model.md) を 3 か所で補正する。**起動時の適用はファイルではなく記録を
  読む。あの記録が「適用はここから走らせても安全である」と挙げたタイマーは、ループを回すもの
  ではない。そして、実行時の値が無いときの扱いについての値ごとの判断は、
  **「その値に依存する成果物を省き、後の周回で拾う」という一般則になる。**
  **順序・フェーズ・2 段階・冪等性の規則・監督の決定は、どれも変わらない。**この記録はそれらの上に
  まるごと載っており、あの記録が指しているロールバックは ADR 0005 のもの —— 上で supersede
  した —— である。
- **[ADR 0015](0015-uplink-addresses-in-sets.md) を 1 か所で補正する。**回線セットの 3 つの書き手の
  うち、適用とデーモンは 1 つのもの —— 1 周 —— であり、pppd のフックはデーモンを必要としない
  経路としてその隣に残る。

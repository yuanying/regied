# ADR 0006: 何かが変わる前に、何が変わるかを見せる

- 状態: 決定（2026-09-03）

## 背景

このプロジェクトの元になったタスクは、dry-run を冪等性・ロールバックと同じ息で求めている。
理由も同じである。回線は 1 本しかなく、変更を当てる人はその回線を通って触っている。
完了条件も置かれている。設定から生まれる nftables のルール、dnsmasq の設定、そして
ルーティングが、適用せずに確認できること。

そこには 2 つの別の問いが隠れていて、1 つのコマンドで両方に答えると、どちらにもきちんと
答えられない。

- *この設定は何を意味するのか* —— ファイルを書きながら、手元のマシンで、まだ存在しない
  かもしれないホストについて訊く。[ADR 0012](0012-networkd-rendering.md) は、すべての
  レンダラを純関数にすることで、この問いに答えられる状態をわざわざ守った
- *このホストで、いま、何が変わるのか* —— enter キーの上に指を置いて訊く。答えは、ホストに
  既にあるものと、回線がいま持っているものに依存する

[ADR 0003](0003-secrets-out-of-configuration.md) は両方を縛る。regied が診断のために出す
ものに資格情報を載せてはならず、そこには dry-run の出力と差分が名指しで含まれている。
書かれるはずのものを印字するのが仕事である dry-run は、その規則を事故で破りやすい場所の
筆頭である。

## 決定

### コマンドを 2 つに分ける。分かれ目はホストを読むかどうか

**`regied render` はホストの状態を読まない。**設定を描画して印字する。適用時にしか存在
しない値はコマンドラインで与えるか、与えない。与えなかった値に依存するものは、適用時に
省かれるのと同じように省かれる。どこでも、どのホストについても走る。1 つ目の問いに答える
のがこれである。

**`regied apply --dry-run` はこのホストを読む。**ここで実行時の値を集め、適用が組み立てる
のと同じプランを組み立て、ホストにあるものと比べ、差を印字する。何かを変えるコマンドは
走らせず、ファイルも書かない。

### dry-run は、commit 段階で止めた適用の経路そのものである

適用がすることの 2 つ目の実装ではない。[ADR 0004](0004-apply-model.md) は適用を、何も
変えない staging 段階と、コマンドを走らせる commit 段階に分けた。**dry-run とは、ファイルを
書く代わりにメモリに置いた staging 段階と、走らせる代わりに印字した commit 段階である。**
見せるプランは適用が実行するプランであり、行う検査は適用が行う検査である。dry-run は通す
のに適用が同じ場所で当たる、という失敗の種類が存在しない。

dry-run が走らせうる唯一のコマンドが `nft --check` である。ルールセットを解析し、カーネルに
対して検証するが、何もインストールしない。これを例外にする価値があるのは、nft が受け付けない
ルールセットが、そもそも適用が失敗する理由として最もありそうだからである。nft が無い環境
—— 手元のマシンでの dry-run —— では検査を飛ばし、出力に「飛ばした」と書く。検証したかの
ように見せない。

### dry-run が印字するもの

- レンダラの警告を最初に、どの差分よりも前に。書かれたとおりに描画できなかった宣言
  （[ADR 0012](0012-networkd-rendering.md) に 2 つある）は、その下のどの 1 行よりも重要で
  あり、そもそも dry-run が存在する理由である
- 追加されるファイルと消えるファイルすべて、そして変わるファイルすべての unified diff。
  変わらないファイルは数えるだけで、並べない
- nftables のテーブル。最後の適用が入れたルールセットとの差分として。比べる相手が無ければ
  全文
- 変わるカーネルスイッチそれぞれ。いまの値と、後の値を添えて
- commit 段階が走らせるコマンドを順に、それぞれどのフェーズのものかを添えて
- 何か変わるのかどうかを述べる締めの 1 行。**「することは無い」は見間違えようがなくなければ
  ならない。**冪等なエンジンではそれが大半の答えであり、運用者がそこを読み飛ばすことが、
  変更が二重に当たる経路だからである

終了ステータスは dry-run が成功したかどうかを述べるのであって、差を見つけたかどうかでは
ない。差があるのは想定される結果であり、終了コードに 2 つの意味を持たせると、staging の検査
失敗と普通の仕事とが区別できなくなる。

### 秘密は 1 行になる。パス、モード、そして変わるかどうか

資格情報ファイルは中身としては決して現れないし、差分としても現れない。現れるのはパスと、
書かれるモードと、中身が変わるかどうかである。それは何も明かさないし、運用者に要るのは
まさにそれである。セッションが再起動されるかどうかを決めるのがそれだからである。

保証は「覚えておく規則」ではなく構造である。値は staging 段階の中で読まれ、使われ、捨てられ、
印字器が歩くプランには決して入らない（[ADR 0004](0004-apply-model.md)）。プランを印字する
ことから資格情報を印字することへ至るコード経路が無い。

DUID は ADR 0003 が既に論じた例外であり、全文が印字される。プレフィックス委譲について
訊かれる問いは「なぜプレフィックスが変わったのか」であり、それに答えるのがいま効いている
DUID だからである。

### dry-run に回線が上がっている必要はない

*[ADR 0015](0015-uplink-addresses-in-sets.md) により補正済み。同記録は実装された。
ルールセットはもう実行時の値に依存しない。いまはどちらの dry-run も同じルールセットを見せる
—— hairpin のルールは線が上がっていてもいなくても回線のセットにマッチする ——
違うのはその横の 1 行、この適用がそのセットに入れることになるアドレスである。線が上がって
いないホストにはそれが注記で伝えられ、要素は 1 つも出ない。この節の主旨は変わらない。
何かを待つ必要は無い。**以下の 2 つめの段落が書いているのは、その記録より前に dry-run が
見せていたものである。***

無い実行時の値は「無い」と報告され、それに依存するものは、適用が省くのと同じように省かれる。

まだ発呼していないホストでの dry-run は hairpin のルールが無いルールセットを見せ、線が
上がった後の dry-run はそれを見せる。この違いはノイズではない。ADR 0004 の最後のフェーズが
当て直しているのと同じ違いが、見える形になったものである。

ホストを一切読まない `regied render` が単体で完結するのも同じ理由である。ルールセットが
必要とする実行時の値が無いので、値が無いことを理由に省かれるものも無い。

## 帰結

- タスクの完了条件は、`config/example.yaml` に対して `regied apply --dry-run` を走らせる
  ことで満たされる。nftables のルールセット、dnsmasq の設定、ポリシーが生む経路が、すべて
  出力に含まれる
- 差分は regied 自身のものであり、自分が描画したテキストと自分が読んだテキストの間で計算
  する。外部の diff プログラムに依存せず、適用時にも要らない。差分では見せられないものが
  2 つあり、それは文章で述べる。末尾の改行だけの違い —— それでも書き換えであり、それを読む
  プロセスは再起動される —— と、モードだけの違いである
- 飛ばした `nft --check` に与えたのと同じ正直さは、その隣の問い合わせにも要る。nft の無い
  マシンは「regied のテーブルがカーネルに在るか」にも答えられない。そこで「無い」と答えれば、
  ホストから離れて取ったプレビューがすべて「ルールセットを丸ごと入れる」と報告することになる
- `regied render` は、netns のテストベッドにホスト無しで描画結果を確かめる手段を与え、
  レビュアーにスキーマ変更の効果をプルリクエストの中で見る手段を与える
- 「することは無い」を正しく印字できることは、ADR 0004 の冪等性の規則がすべての成果物で
  成り立っていることを要求する。2 つの決定が互いを検査する関係になる。誰も変えていない
  変更を報告し続ける dry-run は、比較が壊れていることの発見手段である
- 出力は障害中にコンソールの前にいる人間に向けて書く。したがって同じものを機械可読の
  インターフェースにはしない。構造化されたプランが欲しいものは、状態 API に訊くこと

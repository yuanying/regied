# ADR 0012: /etc/systemd/network に何を書くか

- 状態: 決定（2026-09-02）

## 背景

[ADR 0008](0008-delegate-to-existing-implementations.md) は、リンク・アドレス・MTU・
ブリッジ・静的経路・プレフィックス委譲・ルーター広告・ip6tnl トンネル、そして
ポリシールーティングの経路側を systemd-networkd に渡すと決めた。
[ADR 0011](0011-target-platform.md) は、それを受け取る側のバージョンを固定した。
検証済みの設定をそれらのファイルにする段になると、どちらの ADR も答えていない問いが出る。

そのうち 4 つはこのバックエンドの外にも影響する。networkd がファイルを選ぶときどれが勝つか、
レンダラは何を知ってよいか、リンクの名前が何になるか、そして networkd が作っていない
リンクを誰が設定するか。答えに他の部分が依存する。

## 決定

**リソース 1 つにつきファイル 1 つ。名前は `/etc/systemd/network/` 下の
`50-regied-<リソース名>` とする。** 接頭辞が所有の印である
（[ADR 0009](0009-ownership-boundary.md)）。これを持つものは regied が書き換えてよく
回収してよいもので、持たないものは他人のものである。数字は、どの `.network` がリンクを
取るかを決める。networkd は候補をファイル名順に並べ、最初に一致したものが勝つからである。
50 は両方向に余地を残す。systemd とディストリビューションが置く 80- 番台より前なので、
regied が宣言したリンクは regied の言うとおりに設定される。手書きの上書きや他のレンダラが
慣習的に使う 10- 番台より後ろなので、運用者は regied のファイルを編集せずに自分のファイルを
前に置ける。

**描画は、設定と「適用時にしか存在しない値」だけの純関数である。** その値 —— 事業者の
AFTR 名が解決したアドレスと、DUID ファイルの中身 —— は引数で受け取るものであって、
レンダラが自分で取りに行くものではない。おかげでテストは素の Go だけで通り、いま動いている
ホスト以外に向けた描画も同じ形で作れる。ファイルの書き出し、networkd の再読み込み、
既にあるものとの差分は適用エンジンの仕事である。

**リンクの名前は、それを宣言したリソースの名前にする。** `DSLiteTunnel` と
`PPPoESession` はインターフェース名を持たないので、リソース名がカーネル上の名前になる。
ファイアウォールとポリシールーティングはリンクを名前で参照する。それを成り立たせるのが
この決定である。

**PPPoE のリンクを networkd に渡すのは、そこから出ていく経路のためだけである。**
リンクを作り、名前を付け、アドレスを載せ、既定経路を入れるのは pppd である。しかし
経路は出ていくリンクの上にしか置けず、pppd のオプションファイルには経路を書けない。
そこで regied は、経路だけを持つ `.network` をそのリンクに書き、
`KeepConfiguration=yes` を添えて pppd が入れたものを networkd に落とさせない。
経路を 1 本も宣言せず、どのポリシーからも参照されないセッションにはファイルを作らない。
リンクは未管理のままになる。

2 種類の経路が同じ道を通る。`PPPoESession` が宣言する静的経路（`Interface` のそれと
同じものである）と、ポリシーの表に要る既定経路である。静的経路のもう一つの案は、
リンクが上がってから適用エンジンが netlink で入れるというものだった。しかしそれは、
自分で描画したリンクを regied が監視し、再接続のたびに経路を入れ直す形になる。
ADR 0009 が避けた構造であり、ADR 0008 が書かないと決めたライフサイクルそのものである。
さらに、経路の入れ方が回線の種類によって 2 通りに割れる。障害のときに覚えることが 1 つ増える。

**ルーティングポリシールールの優先度は、テーブル番号をそのまま使う。** どちらも一緒に
導出され、構成上一意である。割り当て範囲は、カーネルが local 表のために持つルールと
main のために持つルールの間にある。ルールが効くにはそこに居る必要がある。
`EgressRoutePolicy` の `priority` は nftables 側の照合順序であってカーネルのルールの
番号ではない。ここで使い回すと、運用者が書いた数字が「0 を書くと local 表を置き換える」
場所に入ってしまう。

**DHCPv6 クライアントは委譲と一緒にアドレスも要求する。** DHCPv6 からアドレスを取る
フィールドはスキーマに無く、最初の描画は「プレフィックスだけを求める」つもりで
`UseAddress=no` を書いていた。しかし networkd ではこの設定が、Solicit に IA_NA を載せるか
どうかまで決める。アドレスを要求することと、それを使うことが 1 つのスイッチである。
IA_PD だけの Solicit には一切答えない事業者が実在し、入れ替える側のルーターは IA_NA と
IA_PD を一緒に送ってその間ずっと委譲を保っていた。そこで上流の `.network` には
`UseAddress=yes` を書く。networkd の既定値だが、ファイルが意図を示すべきであって既定に
寄りかかるべきではないので明示する。普通の返事は IA_NA にアドレスが入らず IA_PD に
プレフィックスが入る。アドレスを出してくる稀な回線では上流リンクに付くが、害は無い。
インターフェース自身のグローバルアドレスは変わらずルーター広告から来る。トンネルの端点
アドレスが定まるのもこれによるままで、下位リンクが持つアドレスは `slaac` のものである。
これを露出するフィールドは作らない。アドレスの要求を止めたい回線が現れたら足すのは
`dhcpv6.requestAddress` である。IAID も同様に networkd の既定のままにする。委譲を IAID に
紐づける事業者が現れたら、定数ではなくフィールドで合わせる。

**そして、ルーター広告に誘われなくても要求する。** networkd は既定では、広告に M または
O フラグが立っているときにしか DHCPv6 クライアントを始めない。`WithoutRA=solicit` が
面倒を見るのは広告が一切来ない回線だけである。事業者は既定経路を広告しつつどちらの
フラグも立てず、それでも DHCPv6 でプレフィックスを委譲することがある。そういう回線では
クライアントは Solicit を一発も送らず、委譲は永遠に来ない。そこで上流の `.network` には
`WithoutRA=solicit` と並べて `DHCPv6Client=always` を書く。フラグは事業者が
そのリンク上のホストについて述べたものであって、委譲するかどうかの表明ではない。
regied はそれを委譲の可否として読まない。これは実回線で表面化したもので、netns
テストベッドでは見えなかった。テストベッドの WAN 側 IPv6 は静的に置かれ、広告を出さない。

**systemd 257 が描画できない宣言は、黙って落とさずに報告する。** 描画はファイルと一緒に
警告を返す。いま 2 つあり、どちらも [ADR 0011](0011-target-platform.md) が記録した
「まだ無い指定」から来ている。

- 下位リンク以外を指す `localAddressFrom`。代わりに下位リンク自身のアドレスで描画される
- 委譲されたプレフィックスだけを広告するインターフェースの `validLifetime` /
  `preferredLifetime`。その寿命は委譲そのものから来る

## 帰結

- 前回の適用が残したものの回収は、接頭辞に対する glob 1 つで済む。適用エンジンが
  「何を書いたか」の一覧を持ち歩く必要はない
- nftables のバックエンドと適用エンジンは、このパッケージに問い合わせずに
  リソース名からインターフェース名を組み立ててよい
- `regied render` と `--dry-run` に警告の置き場ができ、上の 2 件は適用の後ではなく
  前に運用者に届く。書いたとおりに動くことがどうしても必要な構成に当たったなら、
  それは ADR 0011 が既に与えた意味でプラットフォームを見直す理由であって、
  アドレスのライフサイクルをここで作る理由ではない
- `config/example.yaml` の描画結果全体を golden ファイルとして持つ。適用エンジンと
  統合テストはこの出力を扱う形の前提にするので、どこが変わっても差分に現れ、
  理由を述べる必要がある
- PPPoE のリンクに `.network` を与えることは、1 つのリンクに書き手が 2 人並ぶ唯一の場所である。
  意図的で、範囲も狭い（そのファイルが持つのは経路と `KeepConfiguration=yes` だけで、
  アドレスは決して持たない）が、再接続の後で経路が戻らないことがあれば最初に見る場所はここである

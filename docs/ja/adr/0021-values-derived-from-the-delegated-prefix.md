# ADR 0021: 委譲プレフィックスから導く値を、ターンのたびに解決する

- 状態: 決定（2026-10-23）
- [ADR 0015](0015-uplink-addresses-in-sets.md) と
  [ADR 0016](0016-converging-on-the-accepted-declaration.md) を拡張する
- 一連の記録の最初である。続きは [ADR 0022](0022-dslite-local-address-follows-the-delegation.md)、
  [ADR 0023](0023-downstream-hosts-derive-their-subnet.md)、
  [ADR 0024](0024-dns-records-inside-the-delegation.md)、
  [ADR 0025](0025-resolicit-after-the-pppoe-session-returns.md)、
  [ADR 0026](0026-no-uplink-failover-inside-regied.md)

## 背景

### プレフィックスが変わると何が壊れるか

委譲プレフィックスは借り物である。寿命があり、事業者が変えたいときに変わる。DUID と
IAID を保っておけば、事業者側の同じルーターは同じプレフィックスを返してくれる
（[ADR 0012](0012-networkd-rendering.md)）。だが事業者が回線を別のルーターに移した途端、
それは何も約束しない。DUID も IAID も変わっていないのに、違うプレフィックスが返ってくる。

そうなったとき、宣言の中で *導出* として書いたもの —— 下流インターフェースの
`fromDelegatedPrefix`、その後ろにいるホストの `fromRouterAdvertisement` —— は、networkd が
計算し直すので勝手に追随する。プレフィックスの中を *リテラル* で書いたものは、古い
プレフィックスを名指し続ける。記載例と同じ形のルーターでは、それは次のものである。

| 壊れるもの | いまの書き方 | 別の書き方ができない理由 |
|---|---|---|
| DS-Lite トンネルのローカルアドレス | `DSLiteTunnel.localAddress`。リテラル | `localAddressFrom` は systemd 257 では下位リンク自身のアドレスとして描画される（[ADR 0011](0011-target-platform.md)）。委譲を受け取るだけの上流インターフェースは、自分のグローバルアドレスを持たない |
| ルーターの後ろのホストに渡したサブネットへの静的経路と、その next hop | `Interface.routes[].destination` と `via`。リテラル | 導出の形が無い |
| 公開しているホストや、ルーターの後ろのサブネットを名指すアドレスセット | `IPAddressSet.addresses` と `networks`。リテラル | 導出の形が無い |
| 下流のホストが自分のブリッジに与え、広告するサブネット | もう一方のホストの `Interface` に書いたリテラル | そのホストは委譲プレフィックスを知らない（[ADR 0023](0023-downstream-hosts-derive-their-subnet.md)） |
| 公開しているホストの AAAA レコード | 表現できない。`DNSRecordSet` が持つのは A レコードだけ | [ADR 0019](0019-uplink-address-in-dns-records.md) が後の記録に回した（[ADR 0024](0024-dns-records-inside-the-delegation.md)） |

最悪なのはトンネルである。ルーターの IPv4 を運んでいるのはトンネルであり、ホストがもう
持っていないローカルアドレスのままだと、リンクは上がったまま IPv4 のパケットがすべて
捨てられる。エラーを報告するものは何も無く、収束の確認はどれも、ホストは宣言どおりだと
言う。

### regied にとって委譲プレフィックスとは何か

実行時の値である。[ADR 0016](0016-converging-on-the-accepted-declaration.md) がこの言葉を
使うのとまったく同じ意味で。宣言には持てず、このホストにしか答えられず、いまは無くても
次のターンには在るかもしれないもの。ターンが既に集めている 3 つの値 —— AFTR 名が解決する
アドレス、DUID ファイルの中身、各回線のリンクが持っているアドレス —— の隣に並ぶ。

いちばん近いのは 3 つ目である。[ADR 0015](0015-uplink-addresses-in-sets.md) は、回線の
アドレスがルールセットに設定として扱われている実行時の状態だと見抜き、ターンがカーネルから
埋めるセットに移した。委譲プレフィックスは、同じ種類の事実を 1 段上から見たものである。
リンクが持つアドレスではなく、導出されるアドレスすべての切り出し元になるブロックである。

### regied がなってはならないもの

[ADR 0011](0011-target-platform.md) は、トンネルのローカルアドレスを委譲から導くことが
必要だと分かったら、それは「プラットフォームを見直す理由であって、アドレスのライフ
サイクルを自前で作る理由ではない」と述べた。上の障害がそれを必要にし、プラットフォームは
動いていない。だからこの記録が決めることは、その線の手前に留まらなければならない。
**regied はプレフィックスから値を計算する。リース、更新、失効、割り当てるアドレスは
networkd が持ち続ける。**regied が寿命を数え下ろしたからリンクにアドレスが現れる、という
ことは起きない。

[ADR 0009](0009-ownership-boundary.md) と、`aftrHost` フィールドがそこから組み立てる論は、
これが間違った方へ行くもう 1 つの道を塞いでいる。regied が自分で描画したものを監視し、
見えたものから作り直すことである。

## 決定

### 委譲プレフィックスは実行時の値であり、ターンのたびに networkd から読む

**PD クライアントを走らせている `Interface` ごとに、ターンはそのクライアントがいま持って
いるプレフィックスを、networkd 自身によるリンクの説明から読む。**networkd はそれを、
`networkctl status --json` が印字し、D-Bus の `Describe` 呼び出しが返す説明の中で公開して
いる。systemd 257 では、リンクの `DHCPv6Client` オブジェクトが `Prefixes` を持ち、
それぞれにプレフィックス、その長さ、推奨寿命と有効寿命が入る。実際の回線でこれが何を
報告するかは、最初の実装単位がまず確かめることである。

*最初の実装単位が systemd 257.13（Debian 13）で、/56 を委譲する DHCPv6 サーバーに対して
確かめた。`networkctl status --json` はリンクの `DHCPv6Client` に `Prefixes` を持たせ、
それぞれが `Prefix`（文字列ではなく 16 バイトの配列）、`PrefixLength`、2 つの寿命を持つ。
まだ何も持っていないクライアントは `Prefixes` を持たないか、`DHCPv6Client` そのものが
無い。netlink の購読は、もともと回線だけでなくすべてのリンクのアドレスイベントを受けていた。
ターンが購読するマルチキャストグループはリンクで絞られていないので、広げるものは無かった。*

情報源は 3 つ比べた。

| 情報源 | 判定 |
|---|---|
| networkd によるリンクの説明 | **採る。**リースを持っている当事者であり、委譲から導いたものではなく委譲そのものを説明し、networkd が実際に従うのもこれである |
| アドレスが `fromDelegatedPrefix` であるリンクのカーネル上のアドレスを、委譲の長さでマスクし直したもの | 主たる情報源としては退ける。*regied が書いたファイルのせいで* networkd が置いたアドレスを読み戻すことになり、それは ADR 0009 が避けている形である。導出されたアドレスがどこかに在る必要がある。そして委譲の長さを要求から推測するが、事業者は求められたのとは違う長さを委譲することがある |
| `/run` の下にある networkd のファイル | 退ける。networkd の私的な状態であってインターフェースではなく、その上に組むのは networkd が一度も約束していないものの上に組むことである |

これは ADR 0009 が避けた構造ではない。regied が読むのは自分が描画した成果物ではなく、
そこから networkd が導いたアドレスでもない。事業者が委譲したものであり、regied がどんな
ファイルを書いても変えられない。AFTR 名の答えと同じく、入力である。

**ターンを起こすものは既にある。**委譲が変わると、networkd はそこから導くアドレスを
すべて割り当て直し、アドレスイベントはターンを起こす
（[ADR 0016](0016-converging-on-the-accepted-declaration.md)）。購読の対象を回線のリンク
からすべてのリンクに広げ、割り当て直された下流のアドレスが、回線のアドレスと同じように
ターンを起こすようにする。床は定期の再同期のままであり、他には何も監視しない。

### 語彙は 1 つ。プレフィックスの中のアドレスを書くところでは、どこでも `fromDelegatedPrefix`

**スキーマがインターフェースのアドレスのために既に持っている導出を、構成が委譲
プレフィックスの中のアドレスやサブネットを必要とするあらゆる場所での書き方にする。**
同じ 3 つのフィールドで、意味も同じである。

| フィールド | 意味 |
|---|---|
| `interfaceRef` | このホストが委譲プレフィックスを知る経路となるインターフェース。ルーターでは PD クライアントを走らせているもの |
| `subnetID` | 委譲のどのサブネットか |
| `token` | ホスト部。あればアドレス。サブネットを書く場所で無ければ、/64 としてのサブネット |

受け付ける場所と、置き換えるリテラルを並べる。

| フィールド | いま | 提案 |
|---|---|---|
| `Interface.addresses[]` | リテラル、`fromDelegatedPrefix`、`fromRouterAdvertisement` | 変わらない |
| `Interface.routes[].destination` | CIDR | CIDR、またはトークン無しの `fromDelegatedPrefix`。これは /64 である |
| `Interface.routes[].via` | アドレス | アドレス、またはトークン付きの `fromDelegatedPrefix` |
| `IPAddressSet.addresses[]` | アドレス | アドレス、またはトークン付きの `fromDelegatedPrefix` |
| `IPAddressSet.networks[]` | CIDR | CIDR、またはトークン無しの `fromDelegatedPrefix` |
| `DSLiteTunnel.localAddressFrom` | インターフェースの参照 | [ADR 0022](0022-dslite-local-address-follows-the-delegation.md) |
| `DNSRecordSet.records[]` | `egressRef` | [ADR 0024](0024-dns-records-inside-the-delegation.md) |

トークンは `via` と `addresses[]` では必須、`destination` と `networks[]` では拒む。
アドレスを求めるフィールドにサブネットを渡せないようにするためである。サブネットは常に
/64 である。委譲されたサブネットはその単位で配られるものであり、別の長さのための
フィールドは、それを必要とする構成が現れるまで待つ（[ADR 0002](0002-configuration-schema.md)）。
事業者が実際に配った委譲に収まらない `subnetID` は、検証エラーではない —— 長さはターンに
なるまで分からない。後で述べるとおり、理由を添えて、何にも解決されない。

**他のものにはいまはこの形を与えない。**`FirewallPolicy.rules[].destinationCIDRs`、
`DNSForwarder.staticHosts[].address`、`ipv6.advertise.dnsServers` と `DHCPServer.ipv6` の
リゾルバ、IPv6 の `EgressRoutePolicy` の送信元範囲は、リテラルのままである。
プレフィックスの中のホストを名指さなければならないルールは `IPAddressSet` を名指す。
セットはそのためにある。残りは、求められたことが無い。

### 導いた値がどうホストに届くか

ターンは解決できる `fromDelegatedPrefix` をすべて解決し、それぞれの消費者は、既に実行時の
値を受け取っているのと同じやり方で結果を受け取る。

| 消費者 | 解決した値の行き先 |
|---|---|
| ルーター自身のインターフェースのアドレス | 変わらない。networkd が `[DHCPPrefixDelegation]` から導き、regied が描画するのはアドレスではなく導出である |
| 経路の宛先や next hop | `.network` ファイルにリテラルとして描画する。プレフィックスが変わればファイルが変わり、ターンは変わったファイルと同じようにそれを書いて networkd を reload する |
| `IPAddressSet` の要素 | **ルールセットには描画しない。**セットはテーブルの中で宣言し、要素は [ADR 0015](0015-uplink-addresses-in-sets.md) が回線のセットを書くのと同じやり方でターンが書く |
| トンネルのローカルアドレス | [ADR 0022](0022-dslite-local-address-follows-the-delegation.md) |
| DNS レコード | [ADR 0024](0024-dns-records-inside-the-delegation.md) |

ファイルとルールセットの分け方は、それぞれが既に何であるかに従う。networkd のファイルは
宣言 *と* 実行時の値 —— AFTR のアドレス、DUID —— の関数であり、最初からそうだった
（[ADR 0012](0012-networkd-rendering.md)）。ルールセットは宣言だけの関数であり、そうした
のは ADR 0015 である。そのテキストにプレフィックスを入れれば、あの記録が挙げたのと同じ
理由でそれが崩れる。**導出の要素を 1 つでも持つセットは、リテラルの要素も含めてすべての
要素をターンが書く。**1 つのセットが 2 か所から埋められることが無いようにするためである。

*第 3 の実装単位が systemd 257.13 と nftables 1.1.3（Debian 13）で、DHCPv6 サーバーに委譲を
別の /56 へ移させて確かめた。委譲から解決した経路を持つ `.network` をターンが書き直して
networkd を reload すると、旧いサブネットへの経路は消え、新しいサブネットへの経路が入る。
`networkctl reconfigure` は要らない。同じターンで、テーブルを入れ替えずにセットの要素だけが
入れ替わる。nft は interval set のネットワークを文字列ではなく prefix オブジェクトとして
出力する。ターンはそれを CIDR として読み戻すので、ターンが書くはずのものを既に持つセットを
書き直すことは無い。*

`regied render` と `--dry-run` は、読んだプレフィックスと、そこから解決したすべての値を、
ターンが書くはずのファイルとセットの要素の隣に見せる。どちらも秘密ではなく、効いている
プレフィックスは診断がまず必要とするものである。DUID と AFTR のアドレスが既に受けている
扱いと同じである（[ADR 0003](0003-secrets-out-of-configuration.md)）。

### 委譲が無い間

起動したばかりのホスト、リースが失効した回線、クライアントがまだ要求を繰り返している間には、
解決に使うプレフィックスが無い。規則は、値を持っているものの種類で分かれる。

**委譲が無い間、要素は存在しない。**宛先が委譲されたサブネットである経路、プレフィックスの
中のセットの要素。どれもその要素抜きで描画する。委譲が無い間は networkd 自身も導出した
アドレスを持たないのと同じである。その要素の無いファイルやセットは宣言の劣化版ではない。
名指すサブネットが存在しないのだから、それがまさにその時点での宣言の意味である。これは
[ADR 0016](0016-converging-on-the-accepted-declaration.md) が警告する、DUID 無しで書いた
prefix 委譲が *別の設定* になる場合とは違う。存在しないサブネットへの経路は、そもそも
設定ではない。

**値が無ければ存在できない成果物は、そのままにしておく。**トンネル —— ローカルアドレスは
リンクの成り立ちの一部である —— と、DNS 事業者にあるレコード —— このホストの上には
無い —— は、どちらも手を付けない。前のトンネルは前のまま、レコードは持っていたものを
持ち続け、ターンは何を待っているかを言う。AFTR の規則と ADR 0019 の規則のままである。

どちらの場合も、ターンは**待機**で終わり、委譲を待っているインターフェースを名指す。
委譲プレフィックスが同時に 2 つ以上あること、届いた委譲に収まらない `subnetID` も、
値の解決を止めているものとして同じように報告する。

## 採らなかった選択肢

**消費者それぞれにプレフィックスを自分で読ませる。**トンネルの描画、経路の描画、セットの
書き手、DNS の書き手が、それぞれプレフィックスを引く。退ける。1 つの事実を 4 回、ことに
よると 4 つの時点で読めば、1 つのターンの中で食い違いうる。ターンが 1 回読めば、描画する
ものはすべて一致する。

**プレフィックスをルールセットのテキストに描画する。**セットについては、実行時に書くより
単純である。ADR 0015 の理由で退ける。理由はそのまま当てはまる。テキストが宣言の関数で
なくなり、同じ宣言がリースの前後で違う描画になる。

**委譲を持つ新しい kind を作り、すべての導出がそれを参照する。**「委譲プレフィックス」に
名前が付く。ADR 0002 の試金石で退ける。クライアントは既に上流インターフェースの属性で
あり、`interfaceRef` が既にそれを名指している。中身が別のリソースへのポインタだけの kind
は、ADR 0002 が畳む形である。

**systemd 258 を待つ。**258 が覆うのはルーターのトンネルのローカルアドレスだけで、上の表の
他のものは覆わない。しかもプラットフォームに無い（[ADR 0011](0011-target-platform.md)）。

**設定リポジトリのツールに任せる** —— 提出する前に宣言にプレフィックスを代入する。
誰かが変化に気づき、ツールを走らせ、提出する必要があり、それはこの記録が取り除こうと
している手作業そのものである。しかも提出のたびに、同じ意図に対して違う宣言になる。

## 帰結

- **委譲プレフィックスは、ターンが集める実行時の値に加わる。**それが無いことはターンの
  失敗にはならず、待つ理由になるだけで、報告は待っているインターフェースを名指す。
- **networkd が読むファイルは、プレフィックスが変わると変わる。**ターンは、変わった他の
  実行時の値のときと同じように、それを書いて reload する。
- **導出の要素を持つ `IPAddressSet` は、要素が実行時に書かれる。**ルールセットのテキストは
  宣言の関数のままであり、セットの中身は、回線のセットが既にそうであるように、dry-run が
  その隣に見せるものになる。
- **回線のリンクだけでなく、すべてのリンクのアドレスイベントがターンを起こす。**することが
  無いと分かったターンはコマンドを 1 つも走らせないので、費用は比較だけである。
- **スキーマに kind は増えない。**既に知られている形が 1 つ、あと 4 か所に増える。
- **regied は依然としてアドレスのライフサイクルを持たない。**リースとアドレスは networkd が
  持ち、regied は networkd が持っていると言うものから値を計算する。networkd がそれ以外では
  持たないはずのアドレスを regied が書く唯一の場所は
  [ADR 0023](0023-downstream-hosts-derive-their-subnet.md) の下流のホストであり、その理由は
  あの記録が述べる。

## 実装単位

この一連の記録は次の順で入る。各単位は 1 つの pull request で、テストを先に書き、
`docs/spec/` の spec はコードと同じ pull request で直す。

| # | 単位 | 記録 |
|---|---|---|
| 1 | networkd から委譲プレフィックスを読み、ターンの中で `fromDelegatedPrefix` を解決し、その両方を `render` と `--dry-run` に見せ、アドレスの購読を広げる。最初の消費者である単位 2 と一緒に入る | 0021, 0022 |
| 2 | トンネルのローカルアドレスが委譲に追随する | 0022 |
| 3 | 導出した経路の宛先と next hop。導出した `IPAddressSet` の要素を実行時に書く | 0021 |
| 4 | ルーターが保つ、自分の委譲の中の AAAA レコード | 0024 |
| 5 | 下流のホストが、広告されたプレフィックスから自分のサブネットを導く | 0023 |
| 6 | 下流のホストが保つ、自分自身とコンテナの AAAA レコード | 0024 |
| 7 | netns のテストベッドに、プレフィックスを委譲する DHCPv6 サーバーを加え、プレフィックスの変化を端から端まで再現できるようにする。単位 8 より先に入る | 0021, 0025 |
| 8 | PPPoE セッションが別の上流から戻ったあとに要求し直す | 0025 |

単位 1 と 2 が最初なのは、ルーターの IPv4 を落とすのがトンネルだからである。単位 5 が
3 の後なのは、下流のホストのサブネットを導く価値が出るのは、そこへのルーターの経路も
プレフィックスに追随するようになってからだからである。片側だけを導けば、また 2 か所に
なる。単位 6 が 5 の後なのは、下流のホストは自分のレコードを自分で保ち
（[ADR 0024](0024-dns-records-inside-the-delegation.md)）、そのためには自分のプレフィックスが
要るからである。

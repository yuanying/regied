# ADR 0020: リンクの NIC の設定は .link ファイルに書き、udev に当てさせる

- 状態: 決定（2026-09-13）

## 背景

リンクの属性には、ネットワークの設定ではなく NIC に属するものがある。スキーマに入る最初の
1 つが Wake-on-LAN のモード `Interface.spec.wakeOnLan` である
（[`docs/ja/spec/kinds.md`](../spec/kinds.md#wakeonlan)）。別のツールからリンクを引き取った
ホストでは、regied が書かなければ次の起動でこの設定が消える。気づくのは、ホストが落ちていて
起こせないときである。

systemd はこれを `.link` ファイルの `WakeOnLan=` として受け取り、`.link` ファイルは
systemd-networkd のものではない。読むのは systemd-udevd で、その `net_setup_link` ビルトインが、
ネットワークデバイスのイベントを udev が処理するときに当てる。`networkctl reload` はこれを
読まない。regied はこれまで `.link` を 1 枚も書いていないので、[ADR 0004](0004-apply-model.md)
と [ADR 0012](0012-networkd-rendering.md) が networkd のファイルについて決めたことのうち 3 つを、
このファイルについて決め直す必要がある。何に一致させるか、すでに上がっているリンクに適用で
どう効かせるか、ファイルを取り去ることが何を意味するか。

以下は [ADR 0011](0011-target-platform.md) が対象とする systemd 255（Ubuntu 24.04）と
257（Debian 13）のソースで確かめた。下に挙げる点では、どちらも同じように動く。

- udev が `.link` ファイルを当てるのはデバイスの `add`、`bind`、`move` イベントのときだけで、
  それ以外では当てない。名前付け —— `Name=`、`NamePolicy=`、別名 —— は `add` でしか行わない。
- **ディレクトリをまたいで字句順に並べ、最初に一致した `.link` ファイルだけを当て、それより
  後ろはすべて無視する。** ディストリビューションの `99-default.link` も例外ではない。NIC に
  予測可能な名前を付ける名前付けの方針は、このファイルにある。
- `.link` ファイルの `[Match]` セクションに `Name=` は無い。いちばん近いのは
  `OriginalName=` で、処理中のイベントの時点でデバイスが持っている名前に一致する。
- systemd-networkd も同じイベントを受け取る。すでに管理しているリンクを再設定するのは、
  そのリンクに一致する `.network` ファイルが前と違うものになったときだけである。
- udevd が自分の設定ファイルの変化を確かめるのは、イベントが来たときに、最短でも 3 秒おきで
  ある。

## 決定

### NIC の設定を宣言する Interface ごとに `.link` ファイルを 1 つ

**`50-regied-<リソース名>.link` を `.network` の隣に置く。Interface がこのファイルに入る設定を
宣言したときだけ書く。** 接頭辞が同じなので、ADR 0012 がこのディレクトリに与えた規則により
regied が書き換えてよく回収してよいもので、回収も同じ glob で済む。数字の意味は `.network`
より重い。`99-default.link` より後ろの `.link` は、そもそも一度も考慮されない。

### `[Match]` には宣言したインターフェース名を `OriginalName=` で書く

| 候補 | 採らない理由 |
|---|---|
| `MACAddress=`、`PermanentMACAddress=` | 宣言は MAC を持たない。足せばハードウェアの事実を 2 か所目に書くことになり、NIC を交換すれば古くなる |
| `Path=`、`Driver=` | これもハードウェアの事実で、宣言は持たない |
| `Name=` | `.link` ファイルにこの一致条件は無い。`[Link]` の `Name=` はデバイスに名前を付ける指定である |
| **`OriginalName=`** | udev がイベントを処理する時点でデバイスが持っている名前に一致する。宣言が言えるのはこれである |

`OriginalName=` はカーネルがデバイスに付けた名前だと説明されており、`add` イベントの時点では
実際にそうである。NIC はたとえば `eth0` として現れ、宣言した名前はこれから付く予測可能な
名前のほうである。だから `add` では regied のファイルは一致せず、ディストリビューションの
既定のファイルが一致し、デバイスは改名される。**改名はそれ自体がイベントである。** カーネルは
`move` を送り、udev はデバイスがすでに宣言した名前を持った状態でそれを処理する。このとき
regied のファイルが最初の一致になり、その設定が当たる。名前は `add` でしか付けないので、
`move` は名前について何も変えず、既定のファイルが与えたものを何も失わない。

これが、宣言した名前で一致させることを、適用したときだけでなく起動時にも正しくしている。
この設定が防ごうとしている失敗はまさにそれで、適用では一致して次の起動では一致しないファイルは、
ホストが落ちるまで正しく見えてしまう。

書き留めておくべき帰結が 2 つある。

- **カーネルの名前がすでに宣言した名前であるリンクは `add` で一致する。** 予測可能な名前付けを
  切ったホストがこれに当たる。このときファイルはそのデバイスについてディストリビューションの
  既定の代わりになる。名前付けの方針は走らず、デバイスには宣言どおりの名前がそのまま残り、
  別名は足されない。udev はカーネルが付けた名前に一致させたことをログに出す。そういう名前は
  起動をまたいで安定しないという警告である。
- ファイルは名前付けの方針を持たない。ディストリビューションの既定を写せば、宣言したすべての
  NIC の名前の付け方の作者に regied がなってしまう。regied はそうではないし、そのファイルに
  ディストリビューションが入れる変更を追いかけ続けることにもなる。

### 適用は、上がっているリンクにファイルを当てるよう udev に頼む

ファイルを書くことは効果ではない（[ADR 0004](0004-apply-model.md)）。そしてここでは、networkd の
再読み込みもそれを効果にしない。効果にするのは systemd.link(5) が示す手順である。

1. `udevadm control --reload` で、udevd にいまファイルを読ませる。udevd 自身の確認は最短でも
   3 秒おきで、書いた直後のイベントが古いファイルのまま処理されうる。
2. `udevadm trigger --settle --action=add /sys/class/net/<ifname>` で、デバイスに合成の `add`
   イベントを与え、udev がそれを処理し終えるのを待つ。

systemd.link(5) の例では、先にリンクを落としている。regied は落とさない。それは名前や MAC の
ように、上がっているデバイスが受け取れない設定のためのもので、この記録が扱う設定は上がった
ままの NIC が受け取る。合成イベントが上がっているリンクに何をするかは、ソースによれば次の
とおりで、それ以外は無い。

- udev は regied のファイルをいまの名前 —— 宣言した名前 —— で一致させ、書いてあることを当てる。
- デバイスを改名しない。デバイスはすでにユーザー空間が付けた名前を持っており、どのみち
  regied のファイルは名前付けの方針を持たない。
- networkd はイベントを受け取り、同じ `.network` がリンクに一致すると確かめて、再設定しない。

**だから何も落とさず、無人のターンも実行してよい**（[ADR 0016](0016-converging-on-the-accepted-declaration.md)）。
他のコマンドと同じくバックオフの下で走る。

2 つのコマンドは ADR 0004 の順序のフェーズ 3 に、networkd の再読み込みの後に置く。どれも、
それが扱うものが変わったときだけ走る。

| 変わったもの | 走るもの |
|---|---|
| `.network` か `.netdev` のファイル | これまでどおり `networkctl reload`。`.link` だけの変化は理由にならない。networkd はそれを読まない |
| `.link` ファイル（書いた、または回収した） | `udevadm control --reload` |
| `.link` ファイルを書き、そのリンクがホストにある | そのリンクに `udevadm trigger` |

**ホストに無いリンクには trigger しない。** イベントを与えるデバイスが無く、頼めば失敗する。
ファイルは置いてあり、デバイスが現れたときに udev が当てる。計画はこれを、待っているもの
としてではなく注記として述べる。ホストが保てる範囲では、宣言は保たれているからである。

### ファイルを取り去っても設定は切れない

ファイルを回収すると、次にデバイスが現れたときに udev が当てるものが変わる。NIC の設定を
元に戻すことはしないし、誰にもできない。regied より前に NIC が何を持っていたかは分からない。
これは印を持たない状態についての [ADR 0009](0009-ownership-boundary.md) の問いである。NIC は、
デバイスがもう一度追加されるまで —— 典型的には次の起動まで —— いまのモードを保ち、その後は
ドライバかファームウェアが与えるものになる。宣言されなくなったリンクについて ADR 0004 が
引いた線と同じである。**Wake-on-LAN を切るには、宣言に `off` と書く。**

だから回収では udevd を再読み込みし、何も trigger しない。足すべきロールバックも無い。
[ADR 0016](0016-converging-on-the-accepted-declaration.md) にはロールバックが無く、戻すとは
人が前の宣言を適用することであり、それは上のとおりファイルを回収するか、書き直して trigger する。

## 帰結

- regied は `/etc/systemd/network/` に 3 種類目のファイルを書く。回収の glob、所有の印、
  golden の描画は、どれも変更なしでこれを覆う。
- **この設定についてループに見えるのはファイルである。** 人が NIC のモードを手で変えても、
  ターンは戻さない。カーネルが NIC をどう見ているかは、ターンが読むものではないからである。
  ファイルは読むので、人が編集したり消したりしたファイルは元に戻され、もう一度当てられる。
  [ADR 0016](0016-converging-on-the-accepted-declaration.md) が「ループに何が見えるか」について
  引いた線である。
- **ブリッジのメンバーも同じように `.link` ファイルを持つ。** メンバーが NIC であり、その上の
  ブリッジは NIC を持たないので、LAN がブリッジであるホストではこの設定をメンバー自身の
  Interface に宣言する。従属していても、イベントの時点で udev が出会う名前も、networkd がその
  リンクに一致すると見る `.network` も変わらないので、上の一致と trigger はそのまま当てはまる。
- 次にスキーマに入る NIC の設定も同じファイルに入る。`[Match]` と trigger についての理屈が
  それにも当てはまるのは、上がったままの NIC が受け取る設定の場合だけである。リンクを落とす
  必要がある設定は別の記録になる。
- 同じデバイスに対して別のツールがもっと小さい番号の `.link` ファイルを書くホスト —— netplan は
  `/run/systemd/network/` に `10-` で自分のものを書く —— では、そちらが勝ち、regied のものは
  無視される。そういうツールからリンクを引き取るとはその設定を取り除くことで、引き取りでは
  どのみちそうする。

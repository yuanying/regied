# ADR 0007: 常駐プロセスは、問いに答え、アドレスを追う。適用はしない

- 状態: API については保留（2026-09-04）。**デーモンの半分は
  [ADR 0016](0016-converging-on-the-accepted-declaration.md) に置き換えられた**（2026-09-04）。
  ここにあるものは作られていない。

> **この記録の題は、いま半分が間違っている。そして間違っているほうが重要な半分である。**
> 結局ホストは常駐する何かを必要とすると分かり、しかも**収束するために**必要としている。
> ADR 0016 は常駐プロセスに調整ループを持たせるので、**「適用はしない」は覆る。**
> 生き残り、しかもあの設計の中心に格上げされるのはもう半分 ——
> **`serve` は設定ファイルを取らない**である。入力は適用の記録であり、
> それが書きかけの編集をホストに届かせない仕掛けになる。
>
> 以下は、ADR 0016 による 3 つの補正を頭に置いて読むこと。
>
> - **下で設計している記録は、ダイジェストだけでなく受け入れられた宣言そのものを持つ**ように
>   なり、終わりではなく提出時 —— 宣言が検証とステージングを通った、最初のコマンドの前 ——
>   に書かれる。その隣に、最後の周回が何をしたかの報告が、周回の状態を伴って置かれる。
>   ここに書かれている扱いは、その報告の側に当たる。
> - **起動時のユニットは、設定ファイルではなくその記録を読む。**ユニット 2 つについて論じた
>   他のこと —— 順序、`nftables.service` へのガード、regied が描画せずパッケージが配ること ——
>   は変わらない。
> - **アドレスの監視は独立した機構であることをやめる。**カーネルのアドレスイベントはループの
>   1 周を起こし、1 周は既にすべてのセットをカーネルから播く。
>
> **HTTP API は影響を受けず、保留のままである。**いまも要らず、ADR 0016 もそれを欲しがって
> いない。あの記録が足す制御ソケットが運ぶのは confirm と cancel の 2 つの verb だけで、
> エンドポイントは 1 つも無い。以下のエンドポイント・readiness・conntrack のサマリ・
> リース一覧の話は、**誰も作っていないものをどう作るかの決定**のままである。

> **いまホストに常駐プロセスは無い。***（ADR 0016 は、この記録が持たなかった理由によって
> 常駐プロセスが在ることを決めた。そちらも作られていない。）***`regied` のコマンドは `render`
> と `apply` の 2 つであり、`serve` も、待ち受けも、起動時に何かを走らせるユニットも無い。
> 適用が残すものは、入れたルールセットのテキスト 1 つだけである
> （[ADR 0004](0004-apply-model.md)）。成功したときにだけ、regied の状態ディレクトリの下に
> 書かれる。以下に書かれているものは 1 つも無い。適用の記録も、エンドポイントも、
> ソケットも、ユニットも、アドレスの監視も無い。
>
> **したがって以下はすべて「作るときにどう作るか」の決定であって、動いている何かの記述では
> ない。**書かれた時点で未決だった 2 点 —— どこで待ち受けるか、書き込みの口をそもそも持つか
> —— もそこに含まれる。**作る時点で、そのときに真であることに照らして確定する。**いまでは
> ない。
>
> **この記録は取り下げずに残す。理由は 2 つある。**1 つは、常駐する何かが要るとホストに
> ついて分かったとき、白紙からではなく**議論する相手のある設計**から始められるようにする
> ため。もう 1 つは、これを書く過程で適用エンジンについて分かったことが、**二度探さずに済む
> だけの価値がある**ためである。**適用が記録するのは、入れたルールセットのテキストだけで
> ある。**リビジョンも、時刻も、結果も、ロールバックしたという痕跡も無い。だから、どの宣言が
> 動いているのか、最後の試みが成功したのかを、ホストは誰も言えない。**この穴は、それを
> HTTP で提供するものが在ろうと無かろうと実在する。**
>
> **ここにある決定のうち 1 つは、他を待たない。**起動時に適用を走らせるユニットであり、
> regied を導入するホストならどれでも必要とする。下にそれ自身の節で論じてあり、そこの
> 論拠は常駐プロセスが存在することに依存していない。
>
> デーモンの半分が依って立つ [ADR 0015](0015-uplink-addresses-in-sets.md) 自体が、
> 決定済みであって未実装である。どちらも「これから在るもの」として読むこと。

## 背景

このプロジェクトの元になったタスクは、読み取り中心の HTTP API を求め、何に答えるべきかを
挙げている。どの宣言が適用されていて、最後の適用が失敗していないか。PPPoE と DS-Lite の
回線の状態。DHCP のリース。conntrack のサマリ。health と readiness。同時に線も引いている。
書き込みは reload か apply までで、それより先は無い。リソースの CRUD は作らない。宣言を
書いたファイルこそが正であり、それを書き換える API は正を 2 つにするからである。

先の 2 つの記録が、ここに仕事を残している。

[ADR 0004](0004-apply-model.md) は、**起動時の nftables は適用である**と決めた。
ルールセットはカーネルの状態であり、ディストリビューションの `/etc/nftables.conf` は
regied のファイルでもなければ、regied が描画するものを収められもしないからである。
そのうえで「それを走らせるユニットはデーモンの作業単位に属する」と書いて止まっている。
そのユニットをここで決める。

[ADR 0015](0015-uplink-addresses-in-sets.md) は回線のアドレスをルールセットから追い出し、
回線ごと・ファミリごとのセットに置いた。そしてセットの書き手を 3 つ挙げた。カーネルから
播種する適用、IPv4 の張り直しを拾う pppd のフック、そして「デーモン。カーネルのアドレス
イベントから、全回線・両ファミリについて」である。同記録はこれを、他の 2 つが代行している
一般的な仕組みだと述べている。そのデーモンをここで決める。**そもそもこのプロセスなのか**
を含めて。

適用エンジンを作ったことで、もう 1 つの穴がはっきりした。**状態エンドポイントが適用に
ついて訊かれることを、ホストは何ひとつ答えられない。**エンジンが記録するのはルールセットの
テキスト 1 つだけであり、しかも成功したときにしか記録しない。リビジョンも、時刻も、
結果も、ロールバックしたという事実も、どこにも無い。適用中にコンソールの前にいる運用者は
それを全部見ている（[ADR 0006](0006-dry-run-and-rendering.md)）。5 分後、ホストの上には
何も残っていない。これは API の制約ではない。**成果物が 1 つ足りていない**のであり、
その形を決めることがこの記録の大半である。

## 決定

### 常駐プロセスは 1 つ、コマンドは `regied serve`

状態 API とアドレスの監視は同じプロセスに置く。どちらも欲しいものが同じ 2 つ ——
最後の適用が何をしたかと、どのリンクが回線か —— であり、どちらも小さい。分ければ監督する
ものが 2 倍になり、回線が 1 本のホストに regied のデーモンが 2 つ載って、片方が死んで
いることに誰も気づかない、という形ができる。

**読み取りしかしない**ことも分ける理由にはならない。conntrack のカウンタを読むのにも、
nftables のセットを書くのにも権限が要るので、権限を落とした API プロセスには読むものが
残らない。プロセスは root で動かす。`CAP_NET_ADMIN` だけを持つ専用ユーザーに絞るのは
パッケージングの洗練であって、この記録が決めなければならないことではない。

**`serve` は設定ファイルを取らない。**入力は状態ディレクトリとソケットのパスである。
宣言について知る必要があることは、**適用の記録**から読む（後述）。維持するセットは、
いまファイルに書かれているものではなく、**いま効いている**設定に従わなければならない
からである。宣言を編集している最中の誰かが、ルーターのセットを動かしてはならない。
ファイルと適用済みのものの差は、`regied apply --dry-run` が答えるために存在する問いである
（ADR 0006）。

### 適用は自分が何をしたかを書き留め、その記録が接点になる

適用は、regied の状態ディレクトリの下に、記録したルールセットの隣に 2 つ目の成果物を
持つ。**その適用自身の記録**である。**結果がどうであれ、すべての適用の最後に書く。**
ロールバックしたものも含む。「最後の適用は失敗し、ホストはそれ以前の設定を動かしている」
—— これこそ、いまのホストが何ひとつ言えないことだからである。

持つものは次であり、それ以上は持たない。

| 項目 | 何を言うか |
|---|---|
| リビジョン | 適用された宣言のダイジェスト |
| 出所 | それを読んだパス |
| 開始・終了 | 適用が走った時刻 |
| 結果 | 適用した / することが無かった / ロールバックした / 混ざったまま止まった |
| 失敗 | 止まった適用について、フェーズ・手順・原因と、ロールバックが何をできたか（ADR 0005） |
| フェーズ | 6 フェーズのどれが走り、それぞれ何を変えたか（ADR 0004 の最後の帰結） |
| 注記 | commit 段階が成功した後に失敗したこと（ADR 0005） |
| 警告 | レンダラと検証が宣言について言ったこと（ADR 0006） |
| 回線 | 宣言が挙げた回線ごとに、リソース、そのリンク名、ファミリごとのセット |
| 実行時の値 | 適用が集めた秘密でない値。AFTR 名が解決したアドレスと、いま効いている DUID |

**資格情報はここに現れえない。**記録はプランから導かれ、資格情報はプランに入らない ——
staging 段階の中で読まれ、使われ、捨てられる（ADR 0004）。ADR 0003 が求める規則は、
dry-run の出力についてそうであるのと同じく、ここでも構造として成り立っている。

回線の行があることが、`serve` に宣言が要らない理由である。監視が働きかける対象はそれで
全部であり、それは**実際に入っている設定**を述べており、ここに置けばデーモンは実行時に
YAML を解析しないで済み、2 つの半分が「どのリンクが回線か」で食い違うことがありえなくなる。

**記録を書くことは帳簿づけであり、帳簿づけは何もロールバックさせない。**記録を書けなかった
成功した適用は、注記の付いた成功した適用である。ADR 0005 がルールセットの記録に与えたのと
同じ扱いである。ホストが新しい設定を動かしているのに「適用は失敗した」と運用者に伝える方が、
「書き留められなかったものがある」と伝えるより悪い。記録を書けなかった失敗した適用は、
コンソールと終了コードで既にすべてを述べている。記録が古いまま残るだけであり、
それを返すエンドポイントが「どれだけ古いか」を言う。

### リビジョンは宣言のバイト列のダイジェストであって、パスと mtime ではない

mtime は何も変わっていなくても動く。同じ内容の書き直し、チェックアウト、rsync。そして
マシンをまたいで比べられない。エンジンは時刻ではなく内容について冪等に作られており
（ADR 0004）、リビジョンは「2 つの設定が同じものか」についてエンジンと一致していなければ
ならない。

ダイジェストは、障害のときに運用者が実際に訊く問いにも答える。**いまルーターが動かして
いるのは、目の前にあるこのファイルか。**手元のどのコピーからでも同じダイジェストを計算
できる。パスも別の項目として記録する。同じバイト列はどこからでも適用できるからである。
パスは出所であり、ダイジェストは同一性である。

ダイジェストが覆うのは、読んだ宣言の文書だけであって、それが指している先ではない。
PPPoE のパスワードを変えてもリビジョンは変わらないし、**変わってはならない** ——
秘密とともに動くダイジェストは、秘密の通り道になる。適用はその変更をちゃんと当てる。
資格情報ファイルについて適用が比べるのはリビジョンではなく、自分が書くファイルだからで
ある（ADR 0004）。1 回の適用に文書が 2 つ以上入るようになったら、リビジョンはそれら全部を
パス順に取ったものになる。

### エンドポイント

| メソッド | パス | 何を答えるか |
|---|---|---|
| GET | `/healthz` | プロセスが動いて応答しているか。何も読まない |
| GET | `/readyz` | このホストで設定が効いているか |
| GET | `/api/v1/status` | 最後の適用の記録。リビジョン、出所、時刻、結果、フェーズ、警告、そして記録がどれだけ古いか |
| GET | `/api/v1/uplinks` | 宣言された回線ごとに、リンクが在るか、ファミリごとに持っているアドレス、MTU、セットの中身、DS-Lite トンネルなら AFTR 名と解決したアドレス |
| GET | `/api/v1/dhcp/leases` | dnsmasq が配ったリース |
| GET | `/api/v1/conntrack/summary` | 接続追跡のカウンタ。テーブルではない |

`/healthz` と `/readyz` にバージョンの接頭辞は付けない。これらはこの API のものではなく、
それを叩く側の慣習に属する。

**`/api/v1/wan` ではなく `/api/v1/uplinks`。**タスクの付録は前者を素描していた。
[ADR 0009](0009-ownership-boundary.md) は、このシステムで `wan` と `lan` は固有名詞では
ないと決めている —— 運用者がインターフェースの集合に付けうる名前にすぎない —— し、
スキーマが語るのは回線（uplink）であり、`egressRef` が名指すのもそれである。`wan` と
書いたパスは、語彙が破れる唯一の場所になり、しかも後から最も変えにくい場所になる。

**readiness が言うのは「設定が効いているか」であって、直近の試みが成功したかではない。**
ロールバックした適用は、ホストにそれまで動かしていた設定を動かしたまま残す。そのホストは
無事であり、それを ready でないと呼ぶプローブは、回線が 1 本のルーターの上で、
まずい編集に対して「何かを再起動する」という反応を引き起こす。したがって `/readyz` が
「いいえ」と答えるのは 2 つの場合だけである。このホストで regied が一度も適用に成功して
いない場合と、最後の適用がロールバックしきれずに混ざったまま止まった場合 —— そのときは
何が効いているのか誰も知らないからである。**直近の**試みが成功したかは `/api/v1/status`
が答える。そこでなら理由も一緒に読める。

**readiness は探りを入れない。**regied のテーブルがまだカーネルに在るかを nft に訊いたり
しない。探りは 1 リクエストにつきプロセス 1 つの代償であり、readiness は叩かれ続ける。
「最後の適用から何かがずれたか」は、適用を走らせれば答えが出る。冪等であり、何も変わって
いなければ何もしない。あるいは何も触らずに見せる `apply --dry-run` が答える。

**conntrack のサマリはカウンタであり、テーブルを歩くことは決してしない。**返すのは
カーネルが既に持っているもの —— 現在数と上限、そしてその隣の統計（found、invalid、
挿入失敗、drop、early drop、search restart）である。接続を列挙すれば、叩かれ続けることが
存在理由のエンドポイントに、ルーターが運んでいるトラフィックに比例した時間がかかり、
しかも答えが巨大になるのは、まさに誰かが訊きたくなる忙しいルーターの上である。
接続 1 本ごとのエンドポイントは作らない。

**訊かれたことの一部に答えられないエンドポイントは、その部分でそう言う。**リクエスト自体を
失敗させないし、ゼロと答えない。これは ADR 0004 の 3 値の問い合わせを API に当てたもので
ある。**在る・無い・訊けなかった**は別の答えであり、3 つめを 2 つめに畳むことが、壊れた
出所から取った値を事実に見せかける経路である。在らないリンク、まだ存在しないリースファイル、
読めなかった conntrack のカウンタ —— それぞれをそれとして報告する。存在しないものへの
リクエストは普通に 404 であり、`/readyz` は ready でないとき失敗するステータスで答える。
どちらもプローブとクライアントが読むものだからである。

リースは、ネットワークとともに伸びる唯一のリストである。まるごと返す。それが無理になったら、
答えはエンドポイントの絞り込みであって、全エンドポイントを包む封筒ではない。

### それぞれの答えがどこから来るか

| 答え | 出所 |
|---|---|
| health | プロセス自身 |
| readiness、リビジョン、結果、失敗、フェーズ、警告 | 適用の記録 |
| どのリンクが回線か、どのセットがどれに属するか | 適用の記録 |
| リンクの有無、アドレス、MTU | カーネル（netlink） |
| 回線のセットの中身 | カーネル（nft 経由） |
| セッションのプロセスがどれだけ上がっているか | systemd（そのセッションのユニット） |
| アドレスをどれだけ保持しているか | 監視自身が見た事実 |
| AFTR 名と解決したアドレス | 宣言と適用の記録 |
| DHCP のリース | dnsmasq のリースデータベース（regied の状態ディレクトリの下） |
| conntrack のカウンタ | `/proc` |

このうち 2 つは理由を書き留めておく価値がある。

**リースデータベースは regied 自身のパスであって、ディストリビューションのものではない。**
dnsmasq の設定を書くのは regied であり、その設定がリースの置き場所を —— regied の状態
ディレクトリの下だと —— 名指している。API が同じパスを読むのは、適用がそこに書いたのと
同じ理由である。それが regied のファイルだからである。dnsmasq が一度もリースを配って
いないホストにそのファイルは無く、それはエラーではなく空のリストである。まだ何も書かれて
いないディレクトリに対してエンジンが取る扱いと同じである。

**稼働時間は 2 つの問いであり、1 つとして答えると嘘になる。**pppd がどれだけ走っているかは、
そのセッションがこのアドレスをどれだけ保持しているかではない。張り直しは後者だけを
置き換え、前者には触らない。だから両方を返し、どちらも「稼働時間」とは呼ばない。プロセス
側は systemd から来る。既に監督者であり（ADR 0004）、ユニットが最後に active に入った時刻を
既に知っている。アドレス側は、このプロセスが監視を始めて以降しか分からない。監視が
立ち上がった時点で既に在ったアドレスは、「保持している、ただし経過時間は不明」として返す。
そこに時間をでっち上げれば、回線の障害のときに運用者が読むただ 1 つの数字が、
ただ 1 つの間違った数字になる。

### 待ち受けは unix ドメインソケット、認証は持たない

ソケットは `/run` の下、regied 自身のディレクトリに置き、root と 1 つのグループが読める
モードを与える。

API は読み取りしかしないので、**誰が接続できるか**がアクセス制御のすべてであり、
ファイルシステムのモードがまさにそれである。カーネルが強制し、書くコードは要らず、
保管するトークンも、更新するものも無い。そしてソケットはそもそもネットワークから届かない。
ここではそれが普段より効く。**TCP のポートを守ることになるファイアウォールは、regied 自身が
入れるもの**である。それに依存する待ち受けは、自分が報告するためにある当のものに依存する
待ち受けである。

API が返すものは無害ではない。リースの一覧と conntrack のサマリは、ルーターの内側に居る
ホストを描いている。LAN 側のアドレスでポートを開けば、その眺めを、ファイアウォールが
遠ざけるためにある機器すべてに渡すことになる。ループバックに開けば、権限の検査なしに
ローカルのすべてのプロセスに渡すことになる。ソケットより弱く、強くはならない。

離れた場所にいる人間は、ssh 越しにソケットを転送して届く。メトリクスの収集器は、
あるならローカルで届く。**別のマシンから scrape したい**というのがポートを欲しがる本当の
場合であり、それが本当になったときの答えは、**露出と認証を一緒に決める記録**であって、
露出だけを決めるフラグではない。だからこの記録はそれを足さない。後から足しても、
スキーマは変わらず、既存のクライアントも壊れない。

socket activation は検討して採らない。このプロセスは、誰も接続してこなくても自分の仕事が
ある —— セットを播き、追わなければならない —— ので、最初のリクエストまで起動を遅らせるのは、
肝心な半分を遅らせることである。

### 書き込みのエンドポイントは持たない

reload も、apply も、dry-run も。

タスクは reload だけを候補として許していた。それを採らない理由は、**適用とは何か**である。
適用は regied がすることの中で最も鋭い。1 本しかない回線を再起動しうるし、ロールバック
しうる（ADR 0005）。それを HTTP の動詞の後ろに置くことは、「ソケットに届くこと」と
「それを走らせること」を同じにすることであり、待ち受けのアクセス制御を、使い勝手の問題から
安全の問題に変えてしまう。この記録はいま、**API は読み取りしかしない**という根拠で
その問題を決めたばかりである。

しかも能力は 1 つも増えない。適用は、ホスト上で `regied apply` を叩ける者には既に可能で
あり、それはソケットに有意義に届ける者と同じである。エンドポイントが足すのは、
同じ効果への 2 本目の経路を、別のアクセス制御の下に置くことだけである。持つものではなく、
間違えるものが増える。

dry-run を提供するのは、さらに弱い。ADR 0006 は、dry-run の出力は障害中にコンソールの前に
いる人間に向けて書くと決め、意図して機械可読のインターフェースにはせず、構造が欲しいものは
この API に訊けと書いた。それを返すエンドポイントは、あの記録が断った「構造化されたプラン」を
裏口から作ることになる。

**常駐プロセスは決して適用しない。**シグナルでも、タイマーでも、ずれに気づいたときでも。
ルーターの唯一の回線を再起動すると決めることは、ロールバックの付いた行為であり、
運用者か起動時のユニットに属する。問いに答えるのが仕事のプロセスの判断に属さない。

### ユニットは 2 つ、そして regied はそれを描画しない

**`regied-apply.service`** は起動時に `regied apply` を 1 度走らせ、完了したまま留まる。
ADR 0004 の決定が着地する場所である。ルールセットはカーネルの状態なので、再起動のたびに
誰かが入れ直さなければならず、それはファイルではなく適用である。適用は冪等であり、
他人のルールセットを flush せずに自分のテーブル 1 つを入れるからである。何も変わって
いない起動では、ファイルを 1 つも書かず、コマンドを 1 つ走らせる。

**`regied.service`** が常駐プロセスである。

どちらも systemd-networkd の後ろに順序付ける。適用が networkd を再読み込みするし、pppd が
発呼に使うイーサネットを設定するのは networkd だからである（ADR 0004）。そして
`network-online.target` の**前**には置かない —— あの目標はネットワークが設定されるのを
待つものであり、それを設定するのがこのユニットである。適用をその前に順序付けると起動が
デッドロックする。

常駐プロセスは適用の後ろに順序付けるが、**要求しない**。起動時の適用が失敗したときこそ、
誰かが何が起きたかを訊きたいときである。適用が失敗したから起動しないデーモンは、
答えが最も要る瞬間に答えを取り上げる。

ホストでディストリビューションの `nftables.service` が有効なら、適用はその後ろに順序付ける。
あのユニットのファイルはルールセット全体を flush することから始まり、regied のテーブルも
一緒に持っていくからである。順序付けることで、生き残る状態が正しいものになる。これは
防護であって承認ではない。regied を動かすホストでは、ADR 0011 が `/etc/network/interfaces`
を空にすることを求めているのと同じ意味で、そのユニットを有効にしておくべきではない。
運用側が満たす前提であって、regied が強制することではない。

**どちらのユニットもパッケージが配る。regied は描画しない。**

- 最初の適用を走らせるユニットは、適用が作ることはできない
- ADR 0009 の所有の印は、regied がもう要らなくなったものを回収するためにある。
  **regied を走らせるユニットを回収できる立場に、regied を置いてはならない**
- これらのユニットが述べているのは「regied 自身がどう走るか」であり、それはパッケージング
  である。宣言の中身は何も変えない。regied が**書く**ユニットは、まさにその点で違う。
  pppd のテンプレートが在るかどうか、どのセッションがそれをインスタンス化するかは、
  何が宣言されたかから従う（ADR 0004）
- 有効化するのは運用者であり、それは regied を導入するのと同じ行為である

置き場所は、ディストリビューション自身のユニットが居るディレクトリである。そうすれば
`/etc/systemd/system` は、運用者の上書きと、regied がそこに書くユニットのために残る。
ADR 0012 がファイル名の接頭辞で作ったのと同じ分離である。

**起動時の適用のユニットについての決定は、それ自体で立っている。**ここでその根拠として
挙げたもの —— ルールセットはカーネルの状態であり再起動のたびに誰かが入れ直さねばならない
こと、それがファイルではなく適用であること、networkd と `network-online.target` に対する
順序、`nftables.service` の危険、そしてパッケージが配り regied が描画しないこと ——
はすべて ADR 0004 から従っており、**regied を動かすホストなら、隣に常駐プロセスが在ろうと
無かろうと成り立つ。**regied を導入して何も提供しないホストにも、このユニットは要る。

### デーモンの半分 —— セットを追う

監視は、カーネルのアドレス通知を両ファミリについて購読し、各回線のセットを、その回線の
リンクが持っているグローバルアドレスと等しく保つ。それで全部である。ADR 0015 が 3 つめの
書き手として挙げたものであり、他の 2 つが自分の担当範囲でやっていることの一般形である。

- **グローバルアドレスだけ。**リンクローカルをセットに入れてはならない。pppd の IPv6 の
  フックに渡されるのはリンクローカルであり、グローバルは networkd 経由で来ると
  ADR 0015 が既に書いている。リンクローカルにマッチする hairpin ルールは、外側の
  クライアントが解決しうるものに何もマッチしないし、入れればセットが偽を主張することになる
- **起動時に、イベントだけでなく突き合わせる。**イベントが述べるのは変化であり、プロセスは
  アドレスが現れた後に始まったかもしれないし、再起動されたかもしれない。だから宣言された
  回線すべての現在のアドレスを読み、セットを一致させる。足りないものを足し、どのアドレスも
  裏付けない要素を消す
- **突き合わせが安全なのは、3 つの書き手が同じ関数を計算しているからである。**セットの中身は
  「その回線のリンクが持っているグローバルアドレス」ちょうどである。適用はカーネルから
  播き、pppd のフックは pppd が渡したものを足し引きし、監視はカーネルを追う。
  互いを知る必要が無く、**どれか 1 つが動いていれば答えは正しくなる**
- **テーブルが無いのは普通のことであって、致命的ではない。**最初の適用より前、あるいは
  誰かが flush した後は、要素を足す先が無い。監視はそれを状態として報告し、監視を続ける。
  テーブルは入れない。テーブルを入れることは適用することである
- **記録が変わったら読み直し**、回線の行をそこから取る。回線を足した・外した `regied apply`
  が、誰の合図も無しに監視に届くのはこれによってであり、監視に届くのが「編集中のもの」
  ではなく「適用された設定」なのもこれによってである

### デーモンが死んでいる間、ホストは正しいままである

ADR 0015 が組み立てた関係を、こちら側から述べたものである。

適用は走るたびにすべてのセットをカーネルから播き直し、pppd のフックはセッションの出入りに
合わせて PPPoE のリンク上で足し引きする。どちらもこのプロセスを必要としない。だから
デーモンが一度も起動していないホストも、落ちたホストも、動いていたポートフォワードを
保ち、それ以降変わっていないアドレスに依存するルールをすべて保つ。

デーモンが足すのは、その 2 つが届かない場合である。PPPoE リンク上の IPv6 グローバル ——
networkd 経由で来るので、走らせるフックが無い。DS-Lite トンネルの端点アドレスが足元で
変わる場合。そして回線として使う普通のインターフェースのアドレス変更。デーモンが死んで
いれば、それらのセットは最後の適用かフックが置いたものを、次の適用まで持ち続ける。
**デーモンの死はセット 1 つの新鮮さを落とすだけである。ホストを落とさない**し、
復旧は起動し直すこと以上のものではない。立ち上がりざまにカーネルから突き合わせるからである。

### これが何にならないか

多ノードの管理と、他のホストへの設定の配布。ADR 0009 が既に線を引いており、1 台より多くに
ついて答え始める API は、その線を越えて滑る形そのものである。Web コンソール。リソースの
CRUD。メトリクスのエンドポイント —— 露出を決める記録ができるまでは。dry-run の機械可読な
表現。conntrack の接続 1 本ごとの眺め。ログの配信、これは `journalctl` のものである。
適用するデーモン。

**この線はホストについての線であって、出所についての線ではない。**ADR 0009 が拒むのは、
regied が他のマシンを管理すること、そこへ設定を配ることである。**このホスト**が何をすべきかを
他所から学ぶことを拒んでいるのではない。あの記録は既に regied を、クラスタ自身の書き手の
隣に置いている —— 学習した経路をカーネルに入れる BGP デーモンの隣、kube-proxy や Cilium が
既に nftables の状態を持っているホストの上。**他のシステムの API を読んで、このホストが
何をすべきかを知ることは線の手前にあり、他のホストに何をすべきかを告げることが線の向こうに
ある。**

理由は、ADR 0002 が「kind を先回りして増やさない」に与えているのと同じである。エンドポイントは
インターフェースについての約束であり、取り下げにくいのは、誰も必要としないうちに足した
ものである。

## 帰結

- **エンジンには成果物 1 つと規則 1 つが増える。**記録はすべての適用の最後に書かれ、その
  失敗はロールバックではなく注記になる。適用モデルの他の部分は変わらない
- **状態 API が答えられるのは、エンジンを通った適用についてだけである。**誰かが手で入れた
  ルールセット、誰かが編集したファイル、誰かが再起動したセッションは見えない。ADR 0004 が
  「`nft list` の出力を解析せず、regied が描画したテキストと regied の記録を比べる」と
  決めたときに既に受け入れた制約と同じものである
- **常駐プロセスは root もネットワークも無しでユニットテストできる。**記録はファイル、
  リースデータベースはファイル、conntrack のカウンタもファイルであり、netlink・systemd・nft は
  エンジンのホストと同じようにインターフェースの向こうに置く。だから `make test` は純粋な
  ままであり、本物の netlink 側は、実カーネルが元から要るテストベッドが動かす（ADR 0010）
- **記録は regied 自身のディレクトリにある regied 自身のファイル**なので、ADR 0009 の
  所有の印は当たらない。あれは regied が他の書き手と共有するディレクトリのためにある
- **ユニットが 2 つあるということは、片方だけが有効なホストがありうるということであり、
  どちらの状態も読み解ける。**適用だけ有効: ホストは設定されており、適用と適用の間で
  セットが古びていき、問いには誰も答えない。デーモンだけ有効: 問いには答えられ、セットも
  追われるが、再起動の後にテーブルを入れるものが無いので、誰かが適用するまで追い込む先が無い
- **API の答えはコンソールの出力と重なるが、同じテキストではない。**ADR 0006 はコンソールを
  障害中の人間のために残し、構造はここへ向けた。この記録は、構造化されたプランを提供しない
  ことで、その決定を指し返している
- **リビジョンはホストの外でも比べられる。**宣言のコピーを持っている者なら誰でも、
  regied 無しに、ssh 無しにダイジェストを計算して `/api/v1/status` の答えと突き合わせられる。
  1 台しかない群れでこの項目が持つ価値はそこにある
- **この形は回線のアドレスを超えて一般化する。**ADR 0015 がこの形を選んだのは実行時状態の
  1 種類 —— 線が保持しているアドレス —— のためだったが、形そのものはアドレスについて何も
  言っていない。描画されるテキストは設定だけの関数のままであり、要素を書くのは常駐プロセスで
  あり、適用はその要素に依存も待機もしない。まったく別の出所から来る実行時状態 ——
  この段落を書かせた例を挙げるなら、Kubernetes のクラスタが求めた負荷分散アドレスの背後に
  ある健全なバックエンド —— も、同じ場所に座り、同じプロセスの同じ半分が書き、描画される
  テキストには手を触れない。これは ADR 0015 から受け継いだ性質であって、ここで立てた計画では
  ない。**エンドポイントも kind もフィールドも約束しない。**何かがそれを必要としたときに
  足すのであって、その前に足さない（ADR 0002）
- **回線のセットを平気にしているものは、実行時状態一般には成り立たない。**ADR 0013 は
  regied のテーブルを 1 トランザクションで置き換えており、置き換えればその中のセットは
  すべて空になる。回線のセットにとってそれが無代償なのは、**適用が通りがかりにカーネルから
  播き直すから**である（ADR 0015）。カーネルが答えを持っているので、どの書き手もいつでも
  計算し直せる。**出所がカーネルでない要素には、その復旧が無い。**訊けないものを適用は
  播き直せないので、テーブルを置き換えるたびに、答えを知っている何かが気づいて書き直すまで
  暗いままの窓が開く。この記録はそれを解かないし、解く必要もない —— まだ存在しない要素に
  ついてしか成り立たない話であり、解くのはそれを足す記録の仕事である。ここで名指しするのは
  条件をはっきりさせるためである。**回線のセットが平気なのは、カーネルがその答えを持って
  いるからである。**それを「この問題は既に片付いている」という証拠として読むのは、
  読み違えである

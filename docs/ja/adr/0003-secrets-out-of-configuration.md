# ADR 0003: 秘密情報を設定から追い出す

- 状態: 決定（2026-08-30）

## 背景

移植元の設定は、PPPoE のユーザー ID とパスワード、パスワードハッシュ、SSH 公開鍵を、
ルーティングやファイアウォールと同じファイルに持っている。設定ファイルを人に渡す前提が
無いベンダーのルーター OS では、それが普通である。

regied の設定はそうではない。**バージョン管理に入れ、ルールが当たらない理由を尋ねるときに
issue に貼り、同僚に渡すファイル**である。そのどれもが認証情報の漏れ口であり、
しかも漏れ方が静かである。何も失敗しないので、誰も気づかない。

これは仮定の話ではない。このプロジェクトの準備では実物の設定ファイルを読む必要があり、
「どの行なら引用してよいか」を何度も思い出しながら作業することになった。

## 決定

**秘密情報を入れられるフィールドをスキーマに 1 つも作らない。**

- 認証情報は、それを収めたファイルのパスで名指す（`passwordFile`、`userIDFile` など）。
  `password` のようなフィールドは存在しないので、**急いでいるときの近道が無い**
- PPPoE の**ユーザー ID は識別子ではなく認証情報として扱う。** 事業者と加入者を含んでおり、
  回線を騙るのに必要なものの半分である
- 参照するファイルはリポジトリの外に置く。`config/` の設定は `/etc/regied/secrets/` の下を
  指す。そのパスの下にあるものはこのプロジェクトの一部ではない
- regied は適用時に参照先を読み、バックエンドの設定を生成するあいだだけ値を保持し、
  **診断のために出すものには決して書かない。** `--dry-run` の出力にも、差分にも、
  ログ行にも、状態 API にも出さない
- 秘密情報を含まざるを得ないバックエンドの設定（pppd の secrets ファイルなど）は、
  権限を絞って書き、`--dry-run` の出力には含めない。`--dry-run` は
  「このファイルをこのモードで書く」ことを報告し、中身は出さない
- 参照先が無い・読めない場合は**警告ではなく検証エラー**にする。
  認証なしで回線を上げるのは「劣化した成功」ではない

## DUID だけが例外であり、例外にするのは診断のためである

`Interface.dhcpv6.prefixDelegation.duidFile` は認証情報のフィールドと同じ形をしている。
なぜそうなのかを書いておく。**DUID は認証情報ではない。** 何も認証しない。
DHCPv6 のやりとりを見れば、同じセグメントにいる誰にでも見える。

それでもファイル参照にするのは、上の理由の残り半分による。DUID は MAC アドレスを含み、
送り出したホストを同定する。そしてこの決定の目的は「秘密を隠すこと」ではなく、
**設定ファイルを検閲なしで公開できること**である。その目的は DUID にもそのまま当てはまる。
だから文書の中ではなく、認証情報の隣に置く。

**違うのは診断上の扱いであり、これが本 ADR の唯一の例外である。** DUID は `--dry-run` の
出力にも、差分にも、状態 API にも出す。理由は運用にある。プレフィックス委譲について
実際に問われるのは「なぜ委譲プレフィックスが変わったのか」であり、
**いま効いている DUID が見えることが、まさにその答えになる情報**である。
パスワードと同じに隠せば、その問いに regied 自身の出力で答えられなくなる。

参照先の DUID ファイルが無い・読めない・空である場合は、認証情報と同じく検証エラーにする。

## 帰結

- 設定ファイルを検閲なしで公開できる。`config/` に例を置けるのはこのためであり、
  利用者が実物をバグ報告に貼れるのもこのためである
- 秘密情報の配布は別の仕組みの問題になる。これは正しい。設定ファイルをホストに届ける
  問題と同じものであり、ADR 0009 が配布を regied の外に置いている
- 手元では少しだけ手間が増える。回線を上げるのにファイルが 1 つではなく 2 つになり、
  初回の設定で忘れうる手順が 1 つ増える。忘れたときは検証エラーが拾う
- **認証情報の更新が設定ファイルを変えない。** 差分が出ず、適用も要らない。
  読んでいるプロセスの再起動だけで済む
